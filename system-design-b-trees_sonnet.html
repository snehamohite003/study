Why B-Trees Exist

The fundamental problem of efficient data retrieval from disk-based storage

Disk I/O ModelFan-out Block StorageRandom vs Sequential BST Limitations

The Disk Access Problem

Computers have two tiers of storage with vastly different access characteristics. B-Trees were designed in 1970 by Rudolf Bayer and Edward McCreight at Boeing specifically to minimize disk I/O — the dominant bottleneck for database performance:

Storage Hierarchy Latencies (2024) L1 Cache: ~1 ns │█ L2 Cache: ~4 ns │████ L3 Cache: ~12 ns │████████████ RAM: ~80 ns │████████████████████████████████████████ NVMe SSD: ~100 µs │█████████████ 100,000 ns (1000× RAM) SATA SSD: ~500 µs │████████████████████████████████████████ 500,000 ns HDD (7200 RPM): ~10 ms │ 10,000,000 ns (seek + rotational latency) │ └──── Each disk seek = ~125,000 L3 cache hits Key insight: Reading 4KB from disk costs same time as reading 4 bytes. → When you pay for a disk I/O, read as much useful data as possible! → This is why B-Trees use large nodes (pages) = 4KB–64KB each → Fan-out: pack hundreds of keys per node = minimize tree height = minimize I/Os

Why Not Binary Search Trees (BST)?

// Binary Search Tree — why it fails for disk-based storage:

// BST properties:
// Each node stores 1 key, 2 children pointers
// Height = O(log₂ n) for balanced tree

// For 1 billion records (n = 10^9):
BST height = log₂(1,000,000,000) ≈ 30 levels
// = 30 disk I/Os per lookup (each node likely on different disk page!)
// At 10ms per HDD seek: 30 × 10ms = 300ms per lookup → unusable

// BST node size: 1 key (~8 bytes) + 2 pointers (~16 bytes) = ~24 bytes
// Page size: 4096 bytes
// Keys per page: 4096 / 24 = 170 keys → but BST only uses 1 key per node!
// 169 keys wasted per page fetch → terrible cache efficiency

// B-Tree node: fills the entire page
// Page size: 16384 bytes (PostgreSQL default)
// Key size: 8 bytes (bigint), pointer: 6 bytes
// Keys per internal node: ~1000

// For 1 billion records:
BTree height = log₁₀₀₀(1,000,000,000) = 3 levels
// = 3 disk I/Os per lookup!
// 300ms → 30ms (10× improvement on HDD, even better on SSD)
📐 The Fan-out Principle B-Tree performance is governed by fan-out — the number of children per internal node. Higher fan-out = shorter tree = fewer I/Os. Fan-out = ⌊(page_size - header) / (key_size + pointer_size)⌋. A 16KB page with 8-byte keys achieves fan-out ≈ 1000, giving a 3-level tree for billions of rows.

Formal B-Tree Definition (Knuth / CLRS)

A B-Tree of minimum degree t (also called order t) satisfies these invariants at ALL times — violations are impossible by construction of the algorithms:

🔒 B-Tree Invariants (minimum degree t)
  1. Key bounds: Every node (except root) has at least t-1 keys and at most 2t-1 keys.
  2. Root bounds: Root has at least 1 key (unless tree is empty) and at most 2t-1 keys.
  3. Child count: Internal node with k keys has exactly k+1 children.
  4. Ordering: For internal node with keys [k₁, k₂, ..., kₙ] and children [c₀, c₁, ..., cₙ]: all keys in subtree cᵢ lie in range (kᵢ₋₁, kᵢ).
  5. Leaf depth: ALL leaves are at the SAME depth (perfectly balanced by construction).
  6. Key ordering: Keys within each node are stored in sorted (non-decreasing) order.

// Leaf nodes contain the ACTUAL ROW DATA (not just a pointer)
// Table is physically stored in primary key order
// Each table can have ONLY ONE clustered index

// InnoDB clustered index leaf structure:
Leaf Page:
┌──────────────────────────────────────────────────────────┐
│ key=1001 │ col1="Alice" │ col2=30 │ col3="NYC" │ ...full row │
│ key=1002 │ col1="Bob"   │ col2=25 │ col3="LA"  │ ...full row │
│ key=1003 │ col1="Carol" │ col2=35 │ col3="SF"  │ ...full row │
└──────────────────────────────────────────────────────────┘
// Range scan on PK: pure sequential I/O → very fast
// INSERT in PK order: always appends to rightmost leaf → minimal splits
// INSERT random PK (UUID v4): splits everywhere → fragmentation nightmare

// NON-CLUSTERED (SECONDARY) INDEX:
// Leaf nodes contain key VALUE + PRIMARY KEY (pointer back to clustered index)
// Two-step lookup: secondary index → primary key → clustered index lookup

// Example: secondary index on email column
Secondary Index Leaf:
┌──────────────────────────────────────────────────────────┐
│ key="alice@ex.com" │ pk=1001 │   ← pointer to PK, not row │
│ key="bob@ex.com"   │ pk=1002 │                             │
│ key="carol@ex.com" │ pk=1003 │                             │
└──────────────────────────────────────────────────────────┘

// Secondary index lookup steps (InnoDB "double dip"):
SELECT * FROM users WHERE email = 'alice@ex.com';
// Step 1: Traverse secondary index B+Tree → find pk=1001
// Step 2: Traverse clustered index B+Tree → find full row (extra I/Os!)
// Fix: covering index (include all needed columns in secondary index)
//   → Index-Only Scan: data in secondary index leaf, no step 2 needed

// PostgreSQL secondary index leaf stores:
// (indexed_value, ctid) where ctid = (page_number, tuple_offset)
// Direct heap access — no clustered index lookup needed
// Trade-off: heap is unordered → random I/O for range scans on secondary index

Point Lookup — Full Algorithm

class BPlusTree {
  /**
   * Search for a key. Returns associated value or null.
   * Time: O(log_t n) disk I/Os, O(log t × log_t n) comparisons
   */
  search(key) {
    let node = this.readPage(this.rootPageId); // 1 disk I/O

    while (!node.isLeaf) {
      // Binary search within this node's keys (all in memory — 1 page)
      // Find first key >= search key
      const childIndex = this.binarySearchInternal(node.keys, key);
      // childIndex 0: key < all keys → follow leftmost child
      // childIndex i: keys[i-1] <= key < keys[i] → follow child[i]
      // childIndex n: key >= all keys → follow rightmost child

      node = this.readPage(node.children[childIndex]); // 1 disk I/O per level
    }

    // Now at leaf level — binary search for exact key
    const keyIndex = this.binarySearchLeaf(node.keys, key);

    if (keyIndex !== -1 && node.keys[keyIndex] === key) {
      return node.values[keyIndex]; // Found!
    }
    return null; // Not found
  }

  // Binary search within internal node — returns child index to follow
  binarySearchInternal(keys, searchKey) {
    let lo = 0, hi = keys.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (keys[mid] <= searchKey) lo = mid + 1;
      else hi = mid;
    }
    return lo; // lo = number of keys less than searchKey = child index
  }
}

// Complexity analysis:
// Tree height h = ⌈log_t n⌉ where t = min degree, n = number of entries
// Disk I/Os: exactly h (one per level, including leaf)
// Comparisons per node: O(log t) using binary search
// Total comparisons: O(log t × log_t n) = O(log n)
// For t=500, n=10^9: 3 disk I/Os, ~27 comparisons → extremely fast

Range Scan — The Leaf Chain Advantage

async function* rangeScan(lowerKey, upperKey) {
  // Step 1: Find the leaf page containing lowerKey
  let leaf = await findLeaf(lowerKey); // O(log_t n) I/Os

  // Step 2: Find starting position within leaf
  let pos = lowerBound(leaf.keys, lowerKey); // Binary search within page

  // Step 3: Scan forward through leaf chain (sequential I/O!)
  while (leaf !== null) {
    for (let i = pos; i < leaf.keys.length; i++) {
      if (leaf.keys[i] > upperKey) return; // Past upper bound → done
      yield { key: leaf.keys[i], value: leaf.values[i] };
    }
    // Move to right sibling — ONE disk I/O, sequential read
    leaf = leaf.rightSibling ? await readPage(leaf.rightSiblingPtr) : null;
    pos = 0; // Start from beginning of next leaf
  }
}
// Total I/Os: O(log_t n) to find start + O(k/f) for k results (f = fill factor)
// Sequential reads after initial seek → excellent SSD/HDD performance
// OS read-ahead prefetcher can predict next leaf page → near-zero I/O latency

Prefix Search and LIKE Queries

-- B+Tree can satisfy leading wildcard LIKE queries:
WHERE name LIKE 'Alice%'    ← CAN use B+Tree (prefix match)
WHERE name LIKE '%Alice%'   ← CANNOT use B+Tree (leading wildcard)
WHERE name LIKE '%Alice'    ← CANNOT use B+Tree (suffix only)

-- Why prefix works: 'Alice%' is equivalent to range scan:
-- lowerKey = 'Alice', upperKey = 'Alicf' (increment last char)
-- This maps directly to B+Tree range scan!

-- PostgreSQL EXPLAIN for prefix LIKE (uses index):
EXPLAIN SELECT * FROM users WHERE name LIKE 'Alice%';
-- Index Scan using idx_users_name
--   Index Cond: ((name >= 'Alice') AND (name < 'Alicf'))
--   Filter: (name LIKE 'Alice%')

Insertion — The Full Algorithm with Splits

class BPlusTree {
  insert(key, value) {
    // CLRS approach: proactive splitting on the way DOWN
    // Splits full nodes before descending — avoids second upward pass

    const root = this.readPage(this.rootPageId);

    // If root is full → split root FIRST (only time tree height increases)
    if (root.keys.length === 2 * this.t - 1) {
      const newRoot = this.newPage({ isLeaf: false, keys: [], children: [this.rootPageId] });
      this.rootPageId = newRoot.pageId;
      this.splitChild(newRoot, 0, root);  // Split old root as child of new root
      this.insertNonFull(newRoot, key, value);
    } else {
      this.insertNonFull(root, key, value);
    }
  }

  insertNonFull(node, key, value) {
    if (node.isLeaf) {
      // Insert key into sorted position in leaf
      const pos = this.upperBound(node.keys, key);
      node.keys.splice(pos, 0, key);
      node.values.splice(pos, 0, value);
      this.writePage(node); // Write modified leaf to disk
    } else {
      // Find appropriate child
      let childIndex = this.upperBound(node.keys, key);
      let child = this.readPage(node.children[childIndex]);

      // PROACTIVE SPLIT: if child is full, split before descending
      if (child.keys.length === 2 * this.t - 1) {
        this.splitChild(node, childIndex, child);
        // After split: node gained a new key. Recheck which child to follow.
        if (key > node.keys[childIndex]) childIndex++;
        child = this.readPage(node.children[childIndex]);
      }

      this.insertNonFull(child, key, value); // Recurse into non-full child
    }
  }

  splitChild(parent, childIndex, fullChild) {
    // Split fullChild (2t-1 keys) into two nodes of t-1 keys each
    // Median key promoted to parent
    const t = this.t;
    const medianIndex = t - 1; // Middle key (0-indexed)

    const rightChild = this.newPage({
      isLeaf:   fullChild.isLeaf,
      keys:     fullChild.keys.slice(medianIndex + 1),    // Upper half
      values:   fullChild.isLeaf ? fullChild.values.slice(medianIndex + 1) : [],
      children: fullChild.isLeaf ? [] : fullChild.children.slice(t)
    });

    // For B+Tree leaf split: median key STAYS in right leaf + copied to parent
    // For B-Tree internal split: median key MOVES to parent (not in children)
    const medianKey = fullChild.isLeaf
      ? fullChild.keys[medianIndex]     // B+Tree: copy (stays in right leaf)
      : fullChild.keys[medianIndex];    // B-Tree: move (removed from child)

    // Truncate left child to t-1 keys
    fullChild.keys   = fullChild.keys.slice(0, fullChild.isLeaf ? medianIndex + 1 : medianIndex);
    fullChild.values = fullChild.isLeaf ? fullChild.values.slice(0, medianIndex + 1) : [];
    fullChild.children = fullChild.isLeaf ? [] : fullChild.children.slice(0, t);

    // Wire B+Tree leaf siblings (linked list maintenance)
    if (fullChild.isLeaf) {
      rightChild.rightSibling = fullChild.rightSibling;
      fullChild.rightSibling  = rightChild.pageId;
      if (rightChild.rightSibling) {
        const nextLeaf = this.readPage(rightChild.rightSibling);
        nextLeaf.leftSibling = rightChild.pageId;
        this.writePage(nextLeaf);
      }
    }

    // Insert median key into parent
    parent.keys.splice(childIndex, 0, medianKey);
    parent.children.splice(childIndex + 1, 0, rightChild.pageId);

    // Write all modified pages (3 writes: left child, right child, parent)
    this.writePage(fullChild);
    this.writePage(rightChild);
    this.writePage(parent);
  }
}

I/O Cost of Insertion

// Best case (leaf not full): read h pages + write 1 leaf = h+1 I/Os
// Worst case (all nodes full, cascading splits):
//   Read h pages (traversal) + write h+1 pages (each split level) = 2h+1 I/Os
// Average case: O(h) I/Os (splits rare when nodes average ~69% full)

// PostgreSQL WAL amplification per INSERT:
// 1. WAL record for heap tuple insert
// 2. WAL record for index leaf page modification
// 3. (If split) WAL records for: new right page, parent page update, possibly root
// Full-page images (FPI) on first modification after checkpoint: 8KB per page!
// min_wal_size, wal_compression can reduce WAL bloat

// PostgreSQL page fill factor (reduce splits by leaving space):
CREATE INDEX idx_orders_date ON orders(created_at)
WITH (fillfactor = 70);  // Leave 30% free in each page
// New insertions fit in existing pages → fewer splits → lower write amplification
// Cost: more pages needed → slightly taller tree → more I/Os per read
// Use for: append-heavy workloads (time-series), not point updates

Deletion Cases — The Three Scenarios

function delete(node, key) {
  if (node.isLeaf) {
    // ════ CASE 1: Key is in a leaf ════
    const idx = findKey(node.keys, key);
    if (idx === -1) return; // Key not found

    node.keys.splice(idx, 1);
    node.values.splice(idx, 1);
    // May create underflow (< t-1 keys) — handled by caller
    writePage(node);

  } else {
    const idx = findKey(node.keys, key);

    if (idx !== -1) {
      // ════ CASE 2: Key is in this internal node ════
      // Cannot simply remove (would break tree structure)
      // Replace with predecessor (rightmost key of left subtree)
      // OR successor (leftmost key of right subtree)

      const leftChild  = readPage(node.children[idx]);
      const rightChild = readPage(node.children[idx + 1]);

      if (leftChild.keys.length >= t) {
        // Left child has spare key — steal predecessor
        const pred = findPredecessor(leftChild); // Rightmost leaf of left subtree
        node.keys[idx] = pred.key;
        delete(leftChild, pred.key); // Recursively delete predecessor

      } else if (rightChild.keys.length >= t) {
        // Right child has spare key — steal successor
        const succ = findSuccessor(rightChild); // Leftmost leaf of right subtree
        node.keys[idx] = succ.key;
        delete(rightChild, succ.key); // Recursively delete successor

      } else {
        // Both children have exactly t-1 keys → MERGE them
        mergeChildren(node, idx, leftChild, rightChild);
        delete(leftChild, key); // Key now in merged child
      }

    } else {
      // ════ CASE 3: Key not in this node → descend ════
      let childIdx = upperBound(node.keys, key);
      let child = readPage(node.children[childIdx]);

      // Ensure child won't underflow after deletion (proactive fix)
      if (child.keys.length === t - 1) {
        childIdx = fixUnderflow(node, childIdx, child);
        child = readPage(node.children[childIdx]);
      }
      delete(child, key);
    }
  }
}

function fixUnderflow(parent, childIdx, child) {
  const leftSibling  = childIdx > 0
    ? readPage(parent.children[childIdx - 1]) : null;
  const rightSibling = childIdx < parent.children.length - 1
    ? readPage(parent.children[childIdx + 1]) : null;

  if (leftSibling && leftSibling.keys.length >= t) {
    // BORROW from left sibling (rotate right)
    borrowFromLeft(parent, childIdx, child, leftSibling);
    return childIdx;

  } else if (rightSibling && rightSibling.keys.length >= t) {
    // BORROW from right sibling (rotate left)
    borrowFromRight(parent, childIdx, child, rightSibling);
    return childIdx;

  } else if (leftSibling) {
    // MERGE with left sibling
    mergeChildren(parent, childIdx - 1, leftSibling, child);
    return childIdx - 1; // Merged node is at childIdx-1

  } else {
    // MERGE with right sibling
    mergeChildren(parent, childIdx, child, rightSibling);
    return childIdx;
  }
}

Lazy Deletion — The Production Shortcut

// Full deletion with merges is expensive and rarely done immediately
// PostgreSQL, MySQL: LAZY DELETION using tombstones + VACUUM

// PostgreSQL approach:
// DELETE statement marks heap tuple as deleted (xmax set)
// Index entry remains! Points to dead heap tuple.
// Query: index scan → heap lookup → tuple is dead → skip
// VACUUM: walks index, removes dead index entries, reclaims space
// VACUUM can do "page-at-a-time" deletion without merges

// HOT (Heap Only Tuple) updates — avoid index modification:
// UPDATE that only changes non-indexed columns:
// Old tuple marked dead, new tuple added to SAME heap page
// t_ctid chain: old tuple → new tuple
// Index still points to old tuple → follows chain → finds new tuple
// Result: UPDATE doesn't touch the index at all!
// Monitor HOT updates: SELECT n_tup_hot_upd FROM pg_stat_user_tables;
// High HOT ratio = good (index not thrashed by updates)

WAL Integration — Crash Safety for B-Tree Modifications

// Every B-Tree page modification generates WAL records
// WAL must be flushed to disk BEFORE modified page can leave buffer pool
// This is the Write-Ahead Log rule (no data without WAL first)

// WAL record for B-Tree leaf insert (simplified):
WAL_Record {
  lsn:     0x00000001/83B210A0,   // Log Sequence Number (unique, monotonic)
  xid:     7823,                   // Transaction ID
  rmid:    RM_BTREE_ID,            // Resource manager (BTree WAL handler)
  op_type: XLOG_BTREE_INSERT_LEAF,
  target_page: 42,                 // Which page was modified
  offset: 115,                     // Offset within page
  new_item: [key_bytes, itemptr]   // The actual inserted index entry
}

// Full-Page Image (FPI): first modification of a page after checkpoint
// Includes entire 8KB page content in WAL record (instead of just delta)
// Why: partial page writes are possible if crash during write of 8KB page
// FPI ensures crash recovery can reconstruct complete page
// FPI WAL records are 8KB+ → significant WAL volume during checkpoints!
// wal_compression = on: compresses FPIs → typically 50-80% size reduction

// Checkpoint: writes all dirty buffer pages to disk
// After checkpoint: WAL replay only needed from checkpoint forward
// checkpoint_completion_target: spread checkpoint I/O over time
// max_wal_size: trigger checkpoint when WAL reaches this size

Latches vs Locks — Critical Distinction

🔐 Latch (Mutex)
  • Protects physical B-Tree page structure
  • Held for microseconds (duration of page access)
  • No deadlock detection (must avoid by ordering)
  • Modes: read (shared), write (exclusive)
  • NOT visible to transactions — internal to storage engine
  • Example: shared latch on page during traversal
🔑 Lock (Transaction Lock)
  • Protects logical data (rows, tables, ranges)
  • Held for transaction duration (ms to seconds)
  • Deadlock detection required (wait-for graph)
  • Modes: S, X, IS, IX, SIX
  • Visible to transaction manager / MVCC
  • Example: row lock during UPDATE

Lock Coupling (Latch Crabbing) — Safe Concurrent Traversal

// Naive approach: lock root, traverse, release all → bottleneck on root!
// Lock coupling: release parent latch as soon as child is safe

// READ traversal (latch crabbing for search):
function search(key) {
  let parent = null;
  let node = acquireReadLatch(rootPage);  // Acquire read latch on root

  while (!node.isLeaf) {
    const child = acquireReadLatch(node.children[findChild(node, key)]);
    if (parent) releaseReadLatch(parent);  // Release parent immediately!
    parent = node;
    node = child;
  }
  // Only hold latch on current node — parent released
  // Root latch held for nanoseconds, not entire traversal

  const result = searchLeaf(node, key);
  releaseReadLatch(node);
  return result;
}

// WRITE traversal (insertion/deletion with potential splits/merges):
function insert(key, value) {
  const path = [];  // Stack of write-latched ancestors

  let node = acquireWriteLatch(rootPage); // Write latch root
  path.push(node);

  while (!node.isLeaf) {
    const child = acquireWriteLatch(node.children[findChild(node, key)]);

    // "Safe" node: will NOT need to split (has room) → release ancestors
    if (child.keys.length < 2 * t - 1) {
      // Child is safe → no split → ancestors unaffected → release them all
      for (const ancestor of path) releaseWriteLatch(ancestor);
      path.length = 0;
    }

    path.push(child);
    node = child;
  }
  // path contains only necessary ancestors (those that might split)
  // Root is released early if lower nodes are safe → massive concurrency gain
}
// In practice: 99%+ of inserts release root latch within 1-2 levels

Blink-Tree — Non-Blocking Concurrent B+Trees

Blink-Tree (Lehman & Yao 1981) is the foundation for most production database B-Tree implementations (PostgreSQL, InnoDB). It adds a right-link pointer to each node, enabling concurrent readers to recover from concurrent splits without holding parent latches:

// Problem with lock coupling: writer holds write latch on root for splits
// → blocks all other readers/writers during root splits

// Blink-Tree insight: add "right sibling" pointer to INTERNAL nodes too
// (B+Tree already has right sibling for LEAF nodes)

// When a split occurs (concurrent with a reader traversal):
// BEFORE split: internal node N has keys [10, 20, 30]
// Reader latches N, sees child for key=25 → chooses child C
// Reader releases latch on N, latches C
// SPLIT occurs: N splits into N=[10,20] and N'=[30]
// But child C is now under N' not N!
// Reader would lose key=25 without Blink-Tree

// Blink-Tree fix: N has a "high key" (max key in this node) + right-link
// When reader reaches C and finds key > N's high key:
// → Follow right-link to N' (the new node created by split)
// → Continue search in N' without going back up to parent
// → No parent latch needed → lockless descent!

function blinkSearch(key, startPage) {
  let node = readPage(startPage);

  while (key > node.highKey && node.rightLink) {
    // Key belongs in a right sibling (concurrent split happened)
    node = readPage(node.rightLink); // Follow right-link
  }

  if (!node.isLeaf) {
    const childPageId = node.children[findChild(node, key)];
    return blinkSearch(key, childPageId); // Recurse to child
  }

  return findInLeaf(node, key);
}
// PostgreSQL uses Blink-Tree variant with concurrent index scans
// Result: reads never block writes, writes rarely block reads

B-Tree Variants

B*Tree, Fractal Tree, Copy-on-Write B-Tree, and comparison with LSM-Trees

B*TreeFractal Tree Index Copy-on-WriteAppend-Only LSM-Tree ComparisonWrite Amplification

B*Tree — Deferring Splits with 3-Way Distribution

// B*Tree: when a node overflows, try to redistribute with sibling first
// Only split when BOTH the node AND its sibling are full
// Then: split two nodes into THREE nodes (instead of B-Tree's 1→2)

// B-Tree split: 1 full node → 2 nodes at ~50% full
// B*Tree split: 2 full nodes → 3 nodes at ~67% full
// B*Tree minimum fill: 2/3 (vs 1/2 for B-Tree)

// Benefits:
// ✓ Higher average fill factor → fewer pages → shorter tree → fewer I/Os
// ✓ Fewer splits (distributes to sibling before splitting)
// ✗ More complex implementation (must coordinate 2 siblings)

// Used by: older IBM systems, some file systems
// PostgreSQL/MySQL: use standard B+Tree with configurable fillfactor instead

Fractal Tree Index (TokuDB / Percona FT)

// Fractal Tree: B-Tree + message buffers at each internal node
// Writes go to root buffer → cascade down lazily (batched I/O)
// Write amplification: O(log²n / B) vs B-Tree's O(log n)
// where B = buffer size ratio

// Each internal node has:
// - Standard B-Tree keys and child pointers
// - A buffer of pending messages (inserts/updates/deletes)

// Write path:
// 1. Insert message deposited at root buffer (1 I/O: root usually cached)
// 2. When buffer full → "flush" messages to child buffers (batch I/O)
// 3. Messages propagate down lazily
// 4. At leaf: apply all messages for that key range

// Read path:
// Must check ALL buffers on path from root to leaf (may contain relevant msgs)
// Reads slower than B-Tree → optimized with bloom filters per buffer

// Write amplification comparison:
// B-Tree:       O(log n)     → ~30 I/Os for 1B records
// Fractal Tree: O(log²n/B)   → ~3 I/Os  for 1B records (with B=100)
// LSM-Tree:     O(L×log n)   → similar to Fractal for writes, worse for reads

// Used by: TokuDB (acquired by Percona), BetrFS, Tokutek

Copy-on-Write B-Tree (Append-Only / Persistent)

// COW B-Tree: NEVER modify existing pages in-place
// Instead: copy modified page to new location, update parent pointer
// Cascade up to root: root is always a NEW page
// Old pages become immutable snapshots (garbage collected eventually)

// Used by: ZFS (ZFS DMU), Btrfs, LMDB (Lightning Memory-Mapped DB)

// COW write path for updating leaf page L:
// 1. Copy L → L' (new page with modification)
// 2. Update parent P: pointer to L → pointer to L'
// 3. Copy P → P' (parent also changes)
// 4. Update grandparent: pointer to P → pointer to P'
// 5. ... cascade to root
// 6. New root R' points to entire new consistent tree
// 7. Atomically update "root pointer" to R'
// All in one atomic operation (one pointer change)

// Benefits:
// ✓ NO WAL needed! Old tree version always valid → crash safe
// ✓ Free snapshots: old root pointer = old consistent snapshot
// ✓ Readers never blocked (reading old version while writes create new)
// ✓ MVCC naturally: transactions see snapshot at start time

// Drawbacks:
// ✗ Write amplification = O(h) pages written per leaf update (path to root)
// ✗ Space: old pages accumulate until garbage collected
// ✗ More I/Os than in-place update for write-heavy workloads

// LMDB (used by OpenLDAP, many embedded systems):
// Pure COW B-Tree, memory-mapped files, zero-copy reads
// Readers: NEVER blocked, NEVER lock, ZERO overhead
// Writers: serialized (one writer at a time)
// Perfect for: read-heavy, embedded, single-writer workloads

PostgreSQL — nbtree Implementation Details

-- PostgreSQL uses "nbtree" — a Blink-Tree variant
-- Key features beyond standard B+Tree:

-- 1. UNIQUE INDEX DEDUPLICATION (PostgreSQL 13+)
-- For non-unique indexes: multiple entries with same key are deduplicated
-- Instead of: [key=42, ctid=(1,1)] [key=42, ctid=(1,2)] [key=42, ctid=(1,3)]
-- Stored as: [key=42, posting_list=[(1,1),(1,2),(1,3)]]
-- Saves ~70% space for low-cardinality indexes (e.g., status, type columns)
CREATE INDEX idx_orders_status ON orders(status);
-- 'pending' status on 1M rows: without dedup = 1M entries, with dedup = 5 entries

-- 2. COVERING INDEXES WITH INCLUDE
CREATE INDEX idx_users_email_covering ON users(email)
INCLUDE (name, avatar_url);
-- email = B+Tree key (determines sort order, used for lookups)
-- name, avatar_url = stored in leaf only (not key, not in internal nodes)
-- SELECT name, avatar_url FROM users WHERE email = ? → Index Only Scan
-- No heap access needed! All data in index leaf.

-- 3. SUFFIX TRUNCATION (internal nodes)
-- Internal node separator keys can be truncated to minimum distinguishing prefix
-- Instead of full key "2024-01-15 10:30:45.123456" as separator
-- Use just "2024-01-15" if that's enough to route correctly
-- Saves space in internal nodes → higher fan-out → shorter tree

-- 4. CONCURRENT INDEX BUILD (CREATE INDEX CONCURRENTLY)
-- Phase 1: Build index snapshot (one heap scan, no locks)
-- Phase 2: Apply changes that occurred during Phase 1 (second scan)
-- Phase 3: Wait for all transactions that might have outdated info
-- Phase 4: Validate index (mark as valid)
-- Total: 2 heap scans, no table lock, ~2× longer than regular CREATE INDEX

-- 5. METAPAGE (page 0 of every index)
SELECT * FROM bt_metap('idx_orders_customer');
--  magic | version | root | level | fastroot | fastlevel | last_cleanup_num_delpages
-- -------+---------+------+-------+----------+-----------+--------------------------
--  340322|       4  |  412 |     3 |      412 |         3 |                       28
-- root=412: page number of current root
-- level=3: tree height (0-indexed, so 4 levels: meta, root, internal, leaf)

-- INSPECT B-TREE INTERNALS (pg_am, pageinspect extension):
CREATE EXTENSION pageinspect;
SELECT * FROM bt_page_stats('idx_orders_customer', 3); -- Stats for page 3
SELECT * FROM bt_page_items('idx_orders_customer', 3); -- Items on page 3

MySQL InnoDB — Clustered Index Specifics

-- InnoDB: PRIMARY KEY = Clustered Index (table IS the B+Tree)
-- Row data stored in B+Tree leaf pages (not separate heap)

-- InnoDB page structure (16KB default):
-- File Header (38 bytes): page type, checksums, prev/next page pointers
-- Page Header (56 bytes): slot count, free space offset, etc.
-- Infimum/Supremum Records: virtual boundary records (always present)
-- User Records: sorted singly-linked list (physical order ≠ logical order!)
-- Page Directory: array of slot pointers (enables binary search)
-- File Trailer (8 bytes): checksum

-- ADAPTIVE HASH INDEX (AnnoDB unique feature):
-- InnoDB monitors which B+Tree pages are accessed most
-- Automatically builds in-memory hash index for "hot" pages
-- Equality lookup on hot index: O(1) hash → skip B+Tree traversal
-- Controlled by: innodb_adaptive_hash_index = ON (default)
-- Disable for: high-concurrency workloads (AHI has internal contention)

SHOW ENGINE INNODB STATUS\G
-- Hash table size 553229, node heap has 2 buffer(s)
-- 0.00 hash searches/s, 0.00 non-hash searches/s
-- ↑ 0 means AHI not being used (table too small or access pattern not hot)

-- CHANGE BUFFER: defers secondary index updates
-- Problem: secondary index pages randomly distributed → random I/O on insert
-- Solution: buffer secondary index changes when page NOT in buffer pool
-- Merge changes when page IS read into buffer pool later
-- Reduces random I/O for secondary index maintenance by up to 75%
-- innodb_change_buffer_max_size = 25 (% of buffer pool, default)

Bulk Loading — Building Index from Scratch

-- Bulk loading: much faster than N individual inserts
-- Individual inserts: O(N log N) I/Os (each insert = tree traversal)
-- Bulk load: O(N/B) I/Os (sequential scan of sorted data)

-- PostgreSQL: CREATE INDEX uses bulk loading automatically
-- 1. Scan table → sort all index entries (using external merge sort)
-- 2. Build B+Tree bottom-up: fill leaf pages to 90% (fillfactor=90 default for build)
-- 3. Build internal pages from leaf page boundary keys
-- 4. Build root from internal page boundary keys
-- Result: perfectly packed tree with consistent fill factor

-- maintenance_work_mem controls sort memory:
SET maintenance_work_mem = '2GB';  -- More RAM → faster sort → less temp disk I/O
CREATE INDEX idx_orders_customer ON orders(customer_id);

-- For very large tables: parallel index build (PostgreSQL 11+)
SET max_parallel_maintenance_workers = 4;
CREATE INDEX idx_huge_table ON huge_table(col);
-- 4 workers sort partitions in parallel → up to 4× faster

Index Bloat — Detection and Remediation

-- Why indexes bloat:
-- Deletions: dead tuples in leaf pages (lazy deletion)
-- Updates: HOT fails (indexed column changed) → new entry + old entry
-- Splits: half-full pages after splits never fill back up
-- Random inserts: splits at random positions → all pages ~50% full

-- Measure index bloat (PostgreSQL):
SELECT
  schemaname,
  tablename,
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan AS scans,
  round(100.0 * idx_scan / NULLIF(seq_scan + idx_scan, 0), 1) AS idx_scan_pct
FROM pg_stat_user_indexes
JOIN pg_stat_user_tables USING (relname)
ORDER BY pg_relation_size(indexrelid) DESC;

-- pgstattuple extension (exact bloat measurement):
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstatindex('idx_orders_customer');
-- avg_leaf_density: 42.3  ← only 42% full! Heavy bloat
-- leaf_fragmentation: 23.5 ← 23% of leaf pages are out of order on disk

-- Fix index bloat:
-- Option 1: REINDEX (locks table, not suitable for production)
REINDEX INDEX idx_orders_customer;

-- Option 2: REINDEX CONCURRENTLY (PostgreSQL 12+, no locks)
REINDEX INDEX CONCURRENTLY idx_orders_customer;
-- Creates new index, atomically swaps → zero downtime
-- Takes ~2× longer than regular REINDEX

-- Option 3: pg_repack extension (online, no locks)
pg_repack --index idx_orders_customer mydb

Query Planner Interaction — When the Planner Ignores Your Index

-- Planner uses statistics to decide: index scan vs seq scan
-- Statistics: pg_statistic table, updated by ANALYZE

-- Planner chooses INDEX SCAN when:
-- Estimated rows to return < ~5-10% of table (high selectivity)
-- Sequential scan too expensive relative to random I/O cost

-- Planner chooses SEQ SCAN when:
-- Low selectivity (most rows match WHERE clause)
-- Small table (fits in cache → seq scan faster)
-- LIKE '%suffix%' → index useless

-- Force/test index usage (debugging only):
SET enable_seqscan = off;   -- Disable seq scan for testing
SET enable_bitmapscan = off; -- Disable bitmap heap scan
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;

-- Update statistics (when planner makes wrong choices):
ANALYZE orders;              -- Update all columns
ANALYZE orders(customer_id); -- Update specific column

-- Increase statistics target for skewed columns:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
-- Default: 100 histogram buckets. 500 = more accurate estimates for skewed data
ANALYZE orders;

-- random_page_cost vs seq_page_cost (crucial for index decisions):
-- Default: random=4.0, seq=1.0 (HDD assumption: random 4× more expensive)
-- For NVMe SSD: random≈1.1, seq=1.0 (nearly equal!)
SET random_page_cost = 1.1;  -- Makes planner favor index scans more
-- Low random_page_cost → planner uses indexes more aggressively → correct for SSD

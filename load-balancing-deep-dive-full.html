1. What Load Balancing Means

Load balancing is the process of distributing traffic or work across multiple resources so that no single resource becomes overloaded while others remain underused.

These resources may be:

  • Web servers
  • Application servers
  • Database replicas
  • Cache nodes
  • Worker nodes
  • Network links

Simple definition

Load balancing answers the question: “How do we spread incoming work across many machines in a safe and efficient way?”

2. Why Load Balancing Matters

Without load balancing, traffic distribution is uneven and fragile.

This creates problems such as:

  • One server getting overloaded while others sit idle
  • Poor resource utilization
  • Increased latency
  • Higher failure rates
  • Harder failover during server crashes
  • Difficulty scaling horizontally

Load balancing is one of the core mechanisms that turns a set of independent machines into a single scalable service.

3. Core Idea Behind Load Balancing

The purpose of load balancing is to spread work intelligently so that the system can use capacity efficiently, remain responsive, and continue operating even when some backends fail.

Good load balancing is not just about equal distribution. It is about useful distribution under real conditions.

4. What Problems Load Balancing Solves

  • Uneven traffic distribution
  • Backend overload
  • Single server dependence
  • Difficulty adding more servers
  • Lack of failover when nodes die
  • Need for routing by path, host, or protocol
  • Need to hide backend topology from clients

5. Key Components of a Load Balancing System

  • Client
  • Load balancer
  • Backend servers
  • Health check system
  • Routing policy / balancing algorithm
  • Connection management
  • Optional TLS termination
  • Optional observability and traffic shaping rules

6. How Load Balancing Works Behind the Scenes

At a high level, the flow looks like this:

  1. Client sends request to a load balancer address
  2. Load balancer receives the connection or request
  3. Load balancer checks which backends are healthy
  4. Load balancer selects one backend using a policy
  5. Request is forwarded
  6. Response is returned to client
  7. Backend health and traffic metrics continue to be monitored

Important internal idea

The load balancer becomes the system’s traffic control plane for that layer. It makes routing decisions continuously based on backend health, traffic state, and policy.

7. Types of Load Balancing

7.1 Layer 4 Load Balancing

Layer 4 load balancers operate at the transport layer, usually using information like:

  • Source IP
  • Destination IP
  • Port
  • TCP or UDP protocol

How it works internally

The balancer does not need to understand HTTP paths or headers. It routes traffic based on connection-level information.

Advantages

  • Fast
  • Lower overhead
  • Works for non-HTTP protocols too

Disadvantages

  • Less routing intelligence
  • Cannot route by URL path or HTTP headers

7.2 Layer 7 Load Balancing

Layer 7 load balancers operate at the application layer.

They can route based on:

  • HTTP path
  • Host header
  • Cookies
  • Headers
  • Methods
  • Request content patterns

How it works internally

The load balancer must parse the application-layer protocol, understand request metadata, and then choose the backend.

Advantages

  • Fine-grained routing
  • Supports API gateway style behavior
  • Can apply WAF, auth, or header-based rules

Disadvantages

  • More complex
  • Higher overhead
  • More CPU intensive

7.3 DNS Load Balancing

DNS can also distribute traffic by returning different IP addresses for the same domain.

Why it helps

It can direct users to different regions, edges, or datacenters before a connection even starts.

Limitation

DNS is coarse-grained and affected by caching. Once a client caches a result, traffic may continue going to the same destination until TTL expires.

7.4 Global vs Local Load Balancing

Global load balancing

Distributes traffic across regions or datacenters.

Local load balancing

Distributes traffic among servers within one region, AZ, or cluster.

8. Core Load Balancing Algorithms

8.1 Round Robin

Requests are distributed in a rotating sequence.

Example:

  • Request 1 → Server A
  • Request 2 → Server B
  • Request 3 → Server C
  • Request 4 → Server A

Pros

  • Simple
  • Works reasonably well when requests are similar in cost

Cons

  • Bad if request cost varies a lot
  • Does not consider active load

8.2 Weighted Round Robin

Some backends receive more traffic because they have greater capacity.

Example:

  • Server A weight 2
  • Server B weight 1

Server A gets roughly twice as much traffic.

8.3 Least Connections

Traffic goes to the backend with the fewest active connections.

Why it helps

If some requests are long-lived, least-connections can distribute load better than round robin.

Limitation

Number of connections does not always match true work cost.

8.4 Least Response Time / Latency-Based Routing

Requests go to the backend responding fastest.

This can improve user latency, but may become unstable if the balancer reacts too aggressively to short-term fluctuations.

8.5 Hash-Based Routing

A hash of some key determines the backend.

The key may be:

  • Client IP
  • User ID
  • Session ID
  • Request key

Why it helps

Useful for session affinity, partition-aware routing, or cache locality.

8.6 Random with Power of Two Choices

Choose two random backends and send the request to the less loaded one.

Why it matters

This simple method often performs surprisingly well and is widely respected in distributed systems.

9. Session Persistence and Sticky Sessions

What are sticky sessions?

Sticky sessions mean requests from the same client are repeatedly sent to the same backend.

Why they are used

They are often used when session state is stored locally in app server memory.

Why they are risky

  • Uneven load distribution
  • Harder failover
  • Poor autoscaling behavior
  • Coupling users to instances

Preferred approach

In scalable systems, it is usually better to externalize session state and keep services stateless instead of depending heavily on sticky sessions.

10. Health Checks

Why health checks matter

A load balancer is only useful if it can avoid sending traffic to unhealthy instances.

Types of health checks

  • TCP health check — can a connection be opened?
  • HTTP health check — does an endpoint respond correctly?
  • Deep health check — can the instance reach critical dependencies and serve requests correctly?

Important insight

A server may respond to a shallow health check but still be unusable for real traffic. For example, it may be alive while all database calls fail.

11. Traffic Distribution Challenges

Traffic is rarely uniform in production. Some important challenges include:

  • Uneven request cost
  • Long-lived connections
  • Slow backends
  • Hot clients or sessions
  • Connection reuse imbalance
  • Retry storms
  • Regional skew

Important lesson

Equal request counts do not guarantee equal system load.

12. Interview-Level Important Load Balancing Concepts Explained Deeply

12.1 Why Load Balancing Is Essential for Horizontal Scaling

Core idea

Horizontal scaling only works if traffic can be distributed across multiple instances. If you add ten app servers but all traffic still goes to one of them, you have not truly scaled.

Why it matters

Load balancing is the mechanism that makes multiple servers act like one larger service. It is what converts raw infrastructure into usable capacity.

Behind the scenes

The load balancer continuously maps incoming traffic to healthy backends. This mapping is what allows capacity to grow when more instances are added.

12.2 L4 vs L7 Load Balancing

What interviewers want to see

They want to know whether you understand that there are different layers of routing intelligence.

L4 meaning

L4 works with transport-level details only. It is generally simpler and faster.

L7 meaning

L7 understands application-level information and can route based on URLs, headers, methods, and other request metadata.

Tradeoff

L7 is more powerful and more expensive. L4 is faster and simpler but less expressive.

12.3 Load Balancing Is Not Just Equal Distribution

Important idea

Good load balancing is not about sending the exact same number of requests everywhere. It is about preventing overload and making best use of capacity.

Example

Suppose one request takes 2 ms and another takes 2 seconds. Sending the same count of requests to two servers may still create severe imbalance.

Implication

The load balancing policy must match workload characteristics.

12.4 Request-Level vs Connection-Level Balancing

Request-level balancing

Each individual request can be routed independently.

Connection-level balancing

Once a TCP connection is assigned, multiple requests may continue flowing over that same connection.

Why it matters

In protocols with connection reuse, traffic may not distribute evenly just because the balancer accepted connections evenly. Some connections carry far more requests than others.

12.5 Health Checks and Why “Alive” Is Not Enough

Shallow vs deep health

A server process being alive is not enough. It may still be unable to:

  • Reach the database
  • Access the cache
  • Serve traffic within acceptable latency

Why interviewers care

Many real outages happen because unhealthy instances still pass shallow health checks and continue receiving traffic.

12.6 Session Affinity and Sticky Sessions

What it is

Session affinity keeps the same client bound to the same backend.

Why it is sometimes used

It supports stateful applications that keep user session state in memory.

Why it hurts scalability

  • Traffic becomes uneven
  • Failover becomes harder
  • Autoscaling becomes less effective
  • Specific servers may become hot

Better design

Move state to shared systems and keep application servers stateless.

12.7 Failover and Availability

Why load balancers help availability

If one backend fails, the load balancer can stop sending it traffic and route requests elsewhere.

Important nuance

Failover speed depends on how quickly failure is detected, how health checks are configured, and whether healthy alternatives actually exist.

12.8 TLS Termination at the Load Balancer

What it means

The load balancer handles the TLS handshake and decrypts traffic before forwarding it to backends.

Why it is used

  • Centralized certificate management
  • Reduced crypto overhead on app servers
  • Ability to inspect HTTP metadata for routing

Tradeoff

If internal traffic is not re-encrypted and the internal network is not trusted, security risk increases.

12.9 Queueing, Backpressure, and Overload

Why load balancers matter under overload

A load balancer is not only a router. It can also become part of overload control by rejecting traffic, shedding load, or limiting concurrency.

Why this matters

Without overload protection, sending all traffic blindly to already struggling backends can make the whole system collapse.

12.10 Hotspots and Uneven Traffic

Problem

Some users, paths, or requests are far heavier than others. This creates hotspots even in systems with many backends.

Examples

  • One user with very high traffic
  • One API path that triggers heavy DB queries
  • One backend holding many sticky sessions

Implication

Observability and smarter balancing policies are needed. Pure round robin may not be enough.

12.11 Global Load Balancing

What it is

Global load balancing directs clients to different regions or datacenters.

Goals

  • Reduce latency
  • Improve disaster resilience
  • Distribute regional load

How it is often done

  • DNS routing
  • Anycast
  • Geo-based traffic steering

Important limitation

Global routing decisions are coarser than local load balancing and are affected by DNS caching and network routing behavior.

12.12 Client-Side vs Server-Side Load Balancing

Server-side load balancing

A dedicated load balancer chooses the backend.

Client-side load balancing

The client or calling service chooses the backend from a discovered set of instances.

Why this matters in microservices

In service mesh and microservice environments, client-side load balancing can reduce central bottlenecks and allow smarter routing decisions closer to the caller.

Tradeoff

Client-side balancing shifts complexity to clients and requires accurate service discovery.

12.13 Observability in Load Balancing

What must be measured

  • Request distribution
  • Error rate by backend
  • Latency by backend
  • Connection counts
  • Health check failures
  • Retry behavior

Why it matters

Without observability, imbalance may exist without being obvious. A system may appear healthy overall while one backend is overloaded.

12.14 Load Balancer as a Potential SPOF

Important point

A load balancer improves backend reliability only if the load balancer itself is not a single point of failure.

Solution

  • Redundant load balancer nodes
  • Managed HA load balancer services
  • Anycast or multi-endpoint failover

12.15 Algorithm Selection Depends on Workload

What this means

No one algorithm is always best.

  • Round robin works for fairly uniform short requests
  • Least-connections may help with long-lived sessions
  • Hashing helps session locality
  • Weighted routing helps mixed-capacity fleets

Interview expectation

Strong candidates justify the algorithm based on workload rather than naming algorithms randomly.

13. Example: Load Balancing in an E-Commerce System

Suppose an e-commerce platform has:

  • Multiple web servers
  • Multiple API servers
  • Search service
  • Checkout service
  • Recommendation service

How load balancing is used

  1. Users reach a public load balancer
  2. Static content may go to CDN
  3. /api/products routes to catalog servers
  4. /api/cart routes to cart service
  5. /api/checkout routes to checkout service

Failure scenario

If one checkout server becomes unhealthy:

  • Health checks fail
  • Load balancer removes it from rotation
  • Remaining healthy servers continue serving traffic

Scaling scenario

If holiday traffic doubles:

  • More API servers are added
  • Load balancer begins sending traffic to new nodes
  • Capacity increases without changing client behavior

14. Common Load Balancing Failure Modes

  • Load balancer is a single point of failure
  • Health checks are too shallow
  • Sticky sessions create hotspots
  • Round robin used for highly uneven request costs
  • Retries amplify backend overload
  • Connection reuse causes imbalance
  • One region gets too much traffic
  • Backend removal is too slow after failure
  • Improper TLS termination design
  • Global routing caches stale targets

15. Strong Interview Answer

Load balancing is the mechanism that distributes incoming traffic across multiple resources so the system can scale horizontally, remain available, and use capacity efficiently. It works by routing requests or connections to healthy backends using algorithms such as round robin, least connections, weighted routing, or hashing. The right load balancing design depends on workload characteristics, protocol layer, health-check quality, and whether the system needs features such as TLS termination, sticky sessions, or global traffic steering.

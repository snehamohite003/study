Why Sharding — When Vertical Scaling and Replication Aren't Enough

Replication scales reads, but all writes still hit one primary. Vertical scaling has hardware ceilings. Sharding (horizontal partitioning) distributes both reads AND writes across multiple independent database nodes — each owning a subset of the data:

// When to shard — triggering signals:
// 1. Single DB write throughput ceiling (~50K writes/sec for PostgreSQL)
// 2. Dataset exceeds single server storage (e.g., 20TB table)
// 3. B+Tree height increase slows all queries (index > RAM → disk I/O)
// 4. Lock contention on hot rows serializes writes
// 5. VACUUM/maintenance takes too long for data volume

// Sharding vocabulary:
// Shard Key:    Column(s) used to determine which shard owns a row
// Shard:        Independent database node owning a subset of rows
// Shard Map:    Routing table: shard_key_range → shard endpoint
// Logical Shard: Unit of data that can be moved between physical shards
// Physical Shard: Actual database server/cluster hosting logical shards

Sharding Strategy 1 — Hash-Based Sharding

Apply a hash function to the shard key; the result modulo N determines the shard. Guarantees uniform data distribution even if shard keys are skewed:

Hash Sharding — Naive modulo approach shard = hash(user_id) % 4 user_id=1001 → hash=7823481 → 7823481 % 4 = 1 → Shard 1 user_id=1002 → hash=9134752 → 9134752 % 4 = 0 → Shard 0 user_id=1003 → hash=4421109 → 4421109 % 4 = 1 → Shard 1 user_id=1004 → hash=6782340 → 6782340 % 4 = 0 → Shard 0 Shard 0: [DB0] users 1002, 1004, 1008, ... ← ~25% of data Shard 1: [DB1] users 1001, 1003, 1007, ... ← ~25% of data Shard 2: [DB2] users 1006, 1010, 1014, ... ← ~25% of data Shard 3: [DB3] users 1005, 1009, 1013, ... ← ~25% of data PROBLEM: Adding Shard 4 shard = hash(user_id) % 5 ← N changes from 4 to 5 user_id=1001 → 7823481 % 5 = 1 → still Shard 1 ✓ user_id=1002 → 9134752 % 5 = 2 → now Shard 2! ← was Shard 0 ~80% of all rows must MOVE to new shards — catastrophic resharding!

Consistent Hashing — Solving the Resharding Problem

Consistent hashing maps both data keys and shard nodes onto a virtual ring. When nodes are added/removed, only the data between adjacent nodes on the ring needs to move — minimizing resharding impact:

Consistent Hash Ring (0 – 2³²) 0 / 2³² │ 3,900,000,000 ──── 100,000,000 / \ 3,400,000,000 Ring (360° = 2³² values) 400,000,000 | | 2,900,000,000 900,000,000 \ / 2,400,000,000 ─── 1,900,000,000 │ 1,400,000,000 Nodes placed at hash(node_id) positions: Node A at position 500,000,000 Node B at position 1,500,000,000 Node C at position 2,500,000,000 Node D at position 3,500,000,000 Routing rule: walk CLOCKWISE from hash(key) → first node you hit key "user:1001" → hash= 700,000,000 → clockwise → Node B (1,500,000,000) key "user:1002" → hash=2,100,000,000 → clockwise → Node C (2,500,000,000) key "user:1003" → hash=3,800,000,000 → clockwise → Node A ( 500,000,000, wraps) Adding Node E at position 1,000,000,000: Only keys between Node A (500M) and Node E (1B) migrate: → Move from Node B to Node E → ~25% of Node B's data moves (1 shard worth, not everything!) → All other nodes UNAFFECTED ✓

Virtual Nodes (vnodes) — Solving Uneven Distribution

// Problem with basic consistent hashing:
// Hash ring positions are random → nodes may get unequal data shares
// Removing a node dumps ALL its data onto ONE neighbor → hotspot

// Solution: each physical node owns MULTIPLE virtual nodes on the ring
// Cassandra default: 256 vnodes per physical node

Physical Node A (128GB RAM) → vnodes at positions: [23M, 180M, 445M, 712M, ...]
Physical Node B (256GB RAM) → vnodes at positions: [91M, 234M, 511M, 890M, ...]
// Node B has more vnodes proportional to its capacity

// Benefits:
// 1. Even data distribution: more vnodes → closer to uniform
// 2. Node failure: data spreads across MANY neighbors (all vnode successors)
// 3. Heterogeneous hardware: powerful nodes get more vnodes
// 4. Adding node: takes vnodes from MANY existing nodes → parallel data migration

// Cassandra vnode routing (simplified):
const ring = new SortedMap(); // position → node mapping

function getNode(key) {
  const pos = murmur3Hash(key); // Cassandra uses Murmur3
  // Find first vnode position >= pos (ceiling)
  const entry = ring.ceilingEntry(pos) ?? ring.firstEntry(); // wrap
  return entry.node;
}

// Replication: walk ring clockwise, pick next RF unique physical nodes
function getReplicaNodes(key, replicationFactor) {
  const nodes = new Set();
  let pos = murmur3Hash(key);
  while (nodes.size < replicationFactor) {
    const entry = ring.ceilingEntry(pos) ?? ring.firstEntry();
    nodes.add(entry.physicalNode); // deduplicate by physical node
    pos = entry.position + 1;
  }
  return [...nodes];
}

Sharding Strategy 2 — Range-Based Sharding

-- Range sharding: assign contiguous key ranges to shards
-- Good for: range queries, time-series data, sorted access

-- Shard map for orders table (sharded by created_at year):
Shard 0: created_at ∈ [2020-01-01, 2021-01-01)  → DB_2020
Shard 1: created_at ∈ [2021-01-01, 2022-01-01)  → DB_2021
Shard 2: created_at ∈ [2022-01-01, 2023-01-01)  → DB_2022
Shard 3: created_at ∈ [2023-01-01, 2024-01-01)  → DB_2023
Shard 4: created_at ∈ [2024-01-01, ∞)           → DB_2024 (current)

-- Query routing: date range → determine shard(s)
SELECT * FROM orders WHERE created_at BETWEEN '2023-06-01' AND '2023-12-31';
-- Routes to: DB_2023 only ← single shard query ✓

SELECT * FROM orders WHERE created_at BETWEEN '2022-11-01' AND '2023-03-31';
-- Routes to: DB_2022 AND DB_2023 ← two-shard scatter-gather

-- PROBLEM: Hotspot on current shard
-- ALL new orders go to DB_2024 → that shard gets 100% of write traffic!
-- Historical shards: reads only. Current shard: reads + all writes.
-- Fix: sub-shard current period by customer_id range OR hash within range

Sharding Strategy 3 — Directory-Based (Lookup Service)

// A dedicated lookup service maps shard key → shard endpoint
// Most flexible — resharding is just updating the directory, not moving data

class ShardDirectory {
  async getShard(tenantId) {
    // Check local cache first (avoid per-request lookups)
    if (this.cache.has(tenantId)) return this.cache.get(tenantId);

    // Query directory service (backed by Redis or ZooKeeper)
    const shard = await this.redis.hget('shard_map', tenantId);
    this.cache.set(tenantId, shard, { ttl: 300 }); // cache 5 min
    return shard;
  }

  async moveTenant(tenantId, fromShard, toShard) {
    // Step 1: Dual-write to both shards
    await this.enableDualWrite(tenantId, fromShard, toShard);

    // Step 2: Copy historical data from → to shard
    await this.copyData(tenantId, fromShard, toShard);

    // Step 3: Verify data integrity
    await this.verifyChecksum(tenantId, fromShard, toShard);

    // Step 4: Atomically update directory
    await this.redis.hset('shard_map', tenantId, toShard);

    // Step 5: Stop dual-write, disable old shard data
    await this.disableDualWrite(tenantId, fromShard);
  }
}

// Trade-offs:
// ✓ Resharding = update directory (no key formula change)
// ✓ Heterogeneous placement (tenant-aware, VIP customers on better hardware)
// ✗ Directory is a single point of failure → must be highly available
// ✗ Extra network hop for every request (mitigated by local cache)
// Used by: Notion, Shopify (tenant-based sharding), Discord

Hotspot Elimination — The Celebrity Problem

// Hot key problem: one shard key receives disproportionate traffic
// Example: Twitter celebrity with 100M followers posts a tweet
// → All 100M follow requests hit the same shard (tweet_id shard key)

// Solution 1: Key Salting — append random suffix to distribute reads
function getHotKey(userId, numSalts = 10) {
  const salt = Math.floor(Math.random() * numSalts);
  return `user:${userId}:${salt}`; // Spread across 10 shards
}
// Write: update ALL 10 salted keys (fan-out write)
// Read:  pick random salt → reads distributed across 10 shards
// Cost: 10× write amplification. Worth it for extreme hot keys.

// Solution 2: Dedicated shard for known hot tenants
const hotTenants = new Set(['twitter', 'google', 'meta']);
function getShard(tenantId) {
  if (hotTenants.has(tenantId)) return 'dedicated-shard-vip'; // Own shard
  return `shard-${hash(tenantId) % NUM_SHARDS}`;
}

// Solution 3: Caching layer absorbs hot key reads
// CDN/Redis caches celebrity's profile with high TTL
// Shard only sees cache-miss traffic (~1%)

// Solution 4: Read-local writes with CRDTs
// For counters (likes, views): each shard maintains local counter
// Periodically merge (G-Counter CRDT) for global count
// No single shard is the write destination for counter updates

Cross-Shard Operations — The Hard Problems

Scatter-Gather Queries

// Query spans multiple shards → must query all and merge
async function searchOrders(filters) {
  // Determine which shards to query (if shard key not in filter → ALL shards)
  const targetShards = filters.customerId
    ? [getShardForCustomer(filters.customerId)]  // Single shard ✓
    : ALL_SHARDS;                                   // Scatter-gather ✗

  // Query all target shards in PARALLEL
  const results = await Promise.all(
    targetShards.map(shard => shard.query(filters))
  );

  // Gather: merge, deduplicate, sort, paginate in application memory
  const merged = results.flat().sort((a, b) => b.createdAt - a.createdAt);

  // PROBLEM with deep pagination across shards:
  // SELECT * ORDER BY created_at LIMIT 10 OFFSET 9990
  // Must fetch 10,000 rows from EACH shard → merge → take last 10
  // N shards × 10,000 rows fetched = 10,000N rows for 10 results!
  // Fix: cursor-based pagination using shard key monotonic values
  return merged.slice(0, filters.limit);
}

Distributed Transactions Across Shards

// Moving money between users on different shards requires distributed transaction

// Option 1: Two-Phase Commit (2PC)
// Phase 1 (Prepare): Coordinator asks all shards to lock and prepare
// Phase 2 (Commit):  If all ACK → commit all; else → abort all
// Problem: blocking protocol — coordinator crash leaves shards locked forever
// Problem: latency = 2 × max(shard_latency) × 2 network round trips

// Option 2: Saga Pattern (preferred for microservices/sharded DBs)
// Step 1: Debit shard A (local ACID transaction) → if fails, done
// Step 2: Credit shard B (local ACID transaction) → if fails, compensate
// Step 3: Compensating tx: re-credit shard A if step 2 failed

async function transferFunds(fromUserId, toUserId, amount) {
  const fromShard = getShard(fromUserId);
  const toShard   = getShard(toUserId);

  // Step 1: Reserve funds on source shard (idempotent with idempotency key)
  const txId = uuid();
  await fromShard.debit({ userId: fromUserId, amount, txId });

  try {
    // Step 2: Credit destination shard
    await toShard.credit({ userId: toUserId, amount, txId });
  } catch (err) {
    // Step 3: Compensate — reverse debit (idempotent)
    await fromShard.reverseDebit({ txId });
    throw err;
  }
}
// Design shard key to co-locate related data and minimize cross-shard ops
// Instagram: shard by user_id so all a user's data is on one shard

Time Series Databases — InfluxDB & TimescaleDB

Optimized for timestamped measurements: metrics, IoT sensors, financial ticks, monitoring

Why General Databases Fail for Time-Series

Time-series data has unique characteristics that general-purpose databases handle poorly: extremely high ingest rate (millions of data points/second), almost exclusively append-only writes, queries always include a time range, and most data becomes cold (rarely queried) after a retention window:

// Time-series data shape (Prometheus metrics):
// (timestamp, metric_name, labels{}, value)
cpu_usage{host="web-01", region="us-east"} 73.4  @1705000001
cpu_usage{host="web-01", region="us-east"} 74.1  @1705000061
cpu_usage{host="web-02", region="us-east"} 41.2  @1705000001

// Problems with PostgreSQL for this data:
// 1. Random inserts into B+Tree: millions/sec → constant page splits
// 2. No automatic downsampling: 1yr × 1M metrics × 1/min = 525B rows
// 3. No built-in compression for repetitive sequential data
// 4. Aggregation (avg over 1hr window) requires full scan of raw data
// 5. TTL/expiry: manual DELETE jobs → locks, bloat
InfluxDB TSM Storage Engine (Time-Structured Merge Tree)
// TSM = LSM-Tree variant optimized for time-series
// Key insight: timestamp is always monotonically increasing
// → No random inserts → sequential writes always → no page splits

// Data model: Measurement + Tags (indexed) + Fields (values) + Timestamp
INSERT cpu_usage,host=web-01,region=us-east usage_idle=26.6,usage_user=73.4 1705000001000000000

// Storage layout per series key (host=web-01 cpu_usage):
// Timestamps: [t1, t2, t3, ...] → delta-encoded → zigzag → Snappy compressed
// Values:     [73.4, 74.1, 73.8, ...] → XOR compression (float deltas near 0)

// XOR float compression (Gorilla compression, Facebook 2015):
v1 = 73.4  → IEEE754: 0100000101010011001100110011010
v2 = 74.1  → IEEE754: 0100000101010100001100110011010
XOR v1^v2  → 0000000000000111000000000000000  (only 3 bits differ!)
// Store only the XOR difference → 95%+ compression for slowly-changing metrics

// Continuous Queries / Materialized Rollups:
// Raw data: 1-second resolution, 30-day retention
// 1-minute rollup: AVG/MAX/MIN per minute, 1-year retention
// 1-hour rollup:   AVG/MAX/MIN per hour, 5-year retention
// Query automatically routes to appropriate rollup resolution
TimescaleDB — Time-Series on PostgreSQL
-- TimescaleDB: PostgreSQL extension with automatic time partitioning
-- Best of both worlds: familiar SQL + time-series optimizations

-- Convert regular table to hypertable (automatic time-based chunks):
CREATE TABLE metrics (
  time        TIMESTAMPTZ NOT NULL,
  host        TEXT NOT NULL,
  metric_name TEXT NOT NULL,
  value       DOUBLE PRECISION
);

SELECT create_hypertable('metrics', 'time',
  chunk_time_interval => INTERVAL '1 day'  -- 1 chunk per day
);

-- Each chunk is a separate PostgreSQL table internally
-- Recent chunks: hot, in memory (shared_buffers)
-- Old chunks: cold, compressed on disk (90%+ size reduction)

-- Enable compression for chunks older than 7 days:
ALTER TABLE metrics SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'host, metric_name',
  timescaledb.compress_orderby = 'time DESC'
);
SELECT add_compression_policy('metrics', INTERVAL '7 days');

-- Time-series specific functions:
SELECT
  time_bucket('1 hour', time) AS hour,
  host,
  AVG(value)   AS avg_cpu,
  MAX(value)   AS max_cpu,
  MIN(value)   AS min_cpu,
  last(value, time) AS latest_cpu  ← last value in window
FROM metrics
WHERE metric_name = 'cpu_usage'
  AND time > NOW() - INTERVAL '24 hours'
GROUP BY hour, host
ORDER BY hour DESC, host;

-- Query planner automatically prunes irrelevant chunks (chunk exclusion)
-- WHERE time > NOW()-24h → only touches last 24 daily chunks, not all history

Apache Cassandra — Wide-Column Distributed Database

Masterless AP system: linear write scalability, tunable consistency, multi-datacenter replication

Cassandra Data Model — Partition Key + Clustering Columns
-- Cassandra data model is query-driven (design tables around query patterns)
-- Unlike relational: NO joins, NO foreign keys, NO subqueries

-- Table: user timeline (ordered messages per user)
CREATE TABLE user_timeline (
  user_id    UUID,
  created_at TIMEUUID,          -- Time-based UUID (monotonic ordering)
  message_id UUID,
  content    TEXT,
  author_id  UUID,
  PRIMARY KEY (user_id, created_at)  -- (partition_key, clustering_column)
) WITH CLUSTERING ORDER BY (created_at DESC)
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_size': 1,
                    'compaction_window_unit': 'DAYS'};

-- user_id = PARTITION KEY: determines which shard/node owns this partition
-- created_at = CLUSTERING COLUMN: sort order WITHIN the partition
-- All rows with same user_id stored TOGETHER on the same node (co-located)
-- → Range queries on created_at within a user are sequential reads (fast!)

-- Efficient query (uses partition key):
SELECT * FROM user_timeline
WHERE user_id = ? AND created_at > ? LIMIT 20;
-- Single node lookup → sorted sequential read → O(1) routing + O(log n) range

-- Inefficient query (no partition key → full cluster scan):
SELECT * FROM user_timeline WHERE author_id = ?; ← ALLOW FILTERING required
-- Fix: create a separate table user_timeline_by_author with author_id as partition key
-- Cassandra pattern: one table per query pattern!

Cassandra Read Path — Why Reads Are More Complex
// Cassandra read is more expensive than write (must reconcile multiple SSTables)
// Read path (per replica):
// 1. Check Row Cache (optional, entire partition cached)
// 2. Check MemTable (most recent data)
// 3. Check Key Cache (maps partition key → SSTable offset)
// 4. Check Bloom Filter of each SSTable ("might this key be in this file?")
// 5. Check SSTable index (partition → offset within file)
// 6. Read SSTable data pages
// Merge results from all SSTables (newer timestamp wins)

// Read Repair: coordinator compares responses from R replicas
// If replicas disagree → send most recent to stale replicas (background)
// Ensures eventual consistency converges faster

// Hinted Handoff: what happens when a replica is DOWN during write
// Coordinator stores the write as a "hint" locally
// When downed replica comes back → coordinator replays hints
// Hint TTL: max_hint_window (default 3h) — beyond this, full repair needed
// nodetool repair: manual full synchronization (run weekly)

Elasticsearch — Distributed Inverted Index

Full-text search, log analytics, and document store built on Lucene's inverted index

Inverted Index — The Core Data Structure
// Inverted index: maps terms → list of documents containing that term
// (opposite of a database's forward index: document → its fields)

// Example documents:
Doc 1: "The quick brown fox jumps over the lazy dog"
Doc 2: "The fox is quick and the dog is lazy"
Doc 3: "Quick brown foxes are not lazy"

// Inverted index (after tokenization, lowercasing, stop word removal):
Term       → Posting List (doc_id, freq, positions)
"quick"    → [(1, 1, [2]),  (2, 1, [4]),   (3, 1, [1])]
"brown"    → [(1, 1, [3]),  (3, 1, [2])]
"fox"      → [(1, 1, [4]),  (2, 1, [2])]
"lazy"     → [(1, 1, [9]),  (2, 1, [8]),   (3, 1, [4])]
"dog"      → [(1, 1, [10]), (2, 1, [7])]
"jump"     → [(1, 1, [5])]  ← "jumps" stemmed to "jump"

// Query "quick fox":
// 1. Look up "quick" → posting list: [1, 2, 3]
// 2. Look up "fox"   → posting list: [1, 2]
// 3. Intersect (AND) → [1, 2]
// 4. Score each doc using BM25
// 5. Return sorted by score
BM25 Scoring — How Elasticsearch Ranks Results
// BM25 (Best Match 25) — the industry-standard ranking formula
// Replaces classic TF-IDF (still used by older engines)

// BM25 formula for term t in document d:
//                 IDF(t) × TF(t,d) × (k1 + 1)
// score(t,d) = ─────────────────────────────────────────────
//              TF(t,d) + k1 × (1 - b + b × |d|/avgdl)

// Components:
// IDF(t) = log(1 + (N - df + 0.5) / (df + 0.5))
//   N = total documents, df = docs containing term t
//   Rare terms score higher (discriminative terms matter more)

// TF(t,d) = frequency of term t in document d
//   BM25 applies saturation: 5 occurrences not 5× better than 1
//   k1 controls saturation (default 1.2)

// |d| = document length, avgdl = average doc length across corpus
// b = length normalization (default 0.75)
//   Longer docs don't unfairly score higher just by repeating terms more

// Practical tuning:
PUT /my-index/_settings {
  "similarity": {
    "my_bm25": {
      "type": "BM25",
      "k1": 1.5,    // Higher k1: term frequency matters more
      "b": 0.5      // Lower b: less length normalization penalty
    }
  }
}
Elasticsearch Cluster Architecture — Shards, Replicas, Routing
// Elasticsearch index = collection of Lucene shards
// Each shard is a full Lucene instance with its own inverted index

PUT /orders
{
  "settings": {
    "number_of_shards":   5,   // Primary shards (set at creation, cannot change)
    "number_of_replicas": 1    // Replica per primary (can change)
  }
}
// Total shards in cluster: 5 primary + 5 replica = 10 Lucene instances
// Primary and its replica never on same node (HA)

// Document routing: which shard owns this doc?
shard = hash(doc_id) % num_primary_shards
// WHY you cannot change shard count after creation:
// Changing num_shards changes routing formula → existing docs unreachable!

// Lucene Segment internals (within each shard):
// Each index operation creates a new in-memory buffer (256MB default)
// Refresh (default every 1s): flush buffer to new immutable Lucene segment
// Segment = immutable inverted index file on disk
// Merge: background process merges small segments into larger ones
//   (like LSM compaction) — reduces per-query segment count

// Query execution across cluster:
// 1. Client → any node (coordinating node)
// 2. Coordinating node broadcasts query to all 5 primary (or replica) shards
// 3. Each shard: search local Lucene index, return top-K doc IDs + scores
// 4. Coordinating node: merge 5×K results, sort by score, take top K
// 5. Fetch phase: retrieve full _source for top K doc IDs
// → Deep pagination expensive: page 1000 × size 10 = fetch 10,010 from each shard!
// Fix: use search_after (cursor) or scroll API for deep pagination

Neo4j — Native Graph Database

Nodes, relationships, properties — index-free adjacency for O(1) relationship traversal

Graph Data Model — When to Choose It

Graph databases excel when the relationships between entities are as important as the entities themselves, and when queries traverse multiple levels of relationships. The data model: Nodes (entities) → Relationships (directed, typed edges) → Properties (on both nodes and relationships):

// Use cases where graphs outperform relational DBs:
// Social networks: friends-of-friends, influence propagation
// Fraud detection: circular transaction patterns, shared identity
// Recommendation: "users who bought X also bought Y"
// Knowledge graphs: entity relationships, ontologies
// Network topology: infrastructure dependencies, impact analysis
// Access control: hierarchical permissions, role inheritance

// Cypher Query Language — SQL for graphs

// Create nodes and relationships:
CREATE (alice:Person {name: 'Alice', age: 30})
CREATE (bob:Person   {name: 'Bob',   age: 25})
CREATE (carol:Person {name: 'Carol', age: 35})
CREATE (alice)-[:KNOWS {since: 2020}]->(bob)
CREATE (bob)-[:KNOWS   {since: 2022}]->(carol)
CREATE (alice)-[:WORKS_AT]->(acme:Company {name: 'Acme Corp'})

// Find Alice's friends:
MATCH (alice:Person {name:'Alice'})-[:KNOWS]->(friend:Person)
RETURN friend.name, friend.age

// Friends of friends (2 hops):
MATCH (alice:Person {name:'Alice'})-[:KNOWS*2]->(fof:Person)
WHERE NOT (alice)-[:KNOWS]->(fof)  -- exclude direct friends
RETURN DISTINCT fof.name

// Variable-length path (up to 6 hops — "six degrees of separation"):
MATCH path = shortestPath(
  (alice:Person {name:'Alice'})-[:KNOWS*1..6]-(target:Person {name:'Dave'})
)
RETURN path, length(path) AS degrees

// Fraud detection: find circular money flows
MATCH cycle = (account)-[:TRANSFERRED_TO*3..5]->(account)
WHERE ALL(tx IN relationships(cycle) WHERE tx.amount > 10000)
RETURN cycle LIMIT 10
Index-Free Adjacency — The Core Performance Advantage
// Relational DB: finding neighbors requires index lookup + join
// SELECT * FROM friendships WHERE user_id = 42
// → B+Tree lookup: O(log n) where n = ALL friendships in DB
// For 5-hop traversal: O(log n) × 5 hops × fan-out at each hop
// Gets SLOWER as database grows (global index scale)

// Neo4j: each node stores DIRECT POINTER to its relationship list
// Node record (on disk):
NodeRecord {
  id:              42,
  labels:          [Person],
  properties:      ptr → {name: "Alice", age: 30},
  first_rel_ptr:   ptr → RelationshipRecord #1001  ← direct pointer!
}

// RelationshipRecord #1001 (doubly linked list of relationships):
RelRecord {
  start_node:      42 (Alice),
  end_node:        99 (Bob),
  type:            KNOWS,
  properties:      ptr → {since: 2020},
  next_rel_start:  ptr → RelRecord #1005,  ← Alice's next relationship
  next_rel_end:    ptr → RelRecord #2008,  ← Bob's next relationship
}

// Traversal: follow pointer chain — NO index lookup needed!
// Alice's friends: node[42].first_rel → rel[1001] → rel[1005] → rel[1009]...
// Cost: O(degree) — proportional to node's connections, NOT database size!
// 5-hop traversal stays fast regardless of total graph size → true O(1) per hop

// When graph DB wins: query touches small local neighborhood
// When graph DB loses: global aggregations (COUNT all nodes, average degree)
// → Use graph for traversal queries, relational for analytics

The Consistency Spectrum — From Strongest to Weakest

Consistency is not binary. There is a rich spectrum of consistency models between "every read sees the latest write" and "reads may return anything." Stronger consistency = higher latency + lower availability. Weaker consistency = lower latency + higher availability:

← Stronger (More Correct) Weaker (More Available) →
Linearizability Sequential Causal Session (RYW) Eventual

Linearizability (Strong Consistency) — The Gold Standard

Linearizability is the strongest consistency model for distributed systems. It guarantees that operations appear to execute atomically at some single point in real time, and all observers see them in that same real-time order. A linearizable system behaves as if there is only one copy of the data:

// Linearizability test: can we find a valid serialization?
// Each operation has an INVOKE time and a RETURN time
// A linearization point must exist BETWEEN invoke and return for each op

Timeline:
           t0    t1    t2    t3    t4    t5
Client A: [write x=1  ]
Client B:       [read x] → returns 1              ← VALID (after A's write)
Client C:              [read x] → returns 0       ← INVALID! write completed at t1
                                                    C's read started at t3 → must see 1

// Linearizability requires:
// 1. If operation A completes before operation B starts:
//    B must see A's effects
// 2. Concurrent operations can be ordered either way
//    but ALL clients must see them in the SAME order

// HOW linearizability is achieved:
// Raft/Paxos: only leader serves reads (stale leader detected via term/lease)
// etcd: LinearizableRead = read goes through Raft log (confirm leadership first)
// DynamoDB strong reads: quorum read (R + W > N)
// Spanner: TrueTime API — physical clock bounds ensure real-time ordering

// Linearizability vs Serializability (ACID):
// Serializability: transactions execute as if SOME serial order (not necessarily real-time)
// Linearizability: single-object, respects real-time ordering
// Strict Serializability = both (Spanner, CockroachDB)
//   = transactions execute in REAL-TIME order → the holy grail

Cost of Linearizability — Why It's Not Free

// Scenario: 3 Raft nodes, leader in US-EAST, followers in US-WEST and EU
// Client in EU reads from EU follower → stale data!
// To be linearizable: EU client must read from leader (US-EAST) → +100ms RTT
// OR: EU client must wait for leader to confirm it's still leader before local read

// Linearizable read from etcd (goes through Raft):
resp, _ := client.Get(ctx, "key",
  clientv3.WithSerializable())   // FAST: read from local follower (stale allowed)
resp, _ := client.Get(ctx, "key") // DEFAULT: linearizable (goes through leader)

// Network partition impact on linearizable systems:
// Minority partition: REFUSES all reads and writes (no quorum)
// Majority partition: continues normally
// Users on minority partition see service UNAVAILABLE during partition
// → CAP: CP system sacrifices A for C

Sequential Consistency — Weaker but More Available

// Sequential consistency: all operations appear in SOME sequential order
// consistent with each process's own order, but NOT necessarily real-time order

// Valid under sequential consistency (NOT valid under linearizability):
Client A: write(x, 1) at t=0
Client B: write(x, 2) at t=1
Client C: read(x) → returns 2  at t=2
Client D: read(x) → returns 1  at t=2  ← Still valid! Sees different order than C
// C and D see different values for the same key at the same time
// Would be INVALID under linearizability (both should see 2 after t=1)
// But sequential: each client sees ops in some consistent sequential order

// Used by: CPU memory models (x86 TSO approximates sequential consistency)
// Most single-leader databases (MySQL binlog replication) have sequential
// consistency within a single replica's view

Causal Consistency — Causally Related Ops Are Ordered

Causal consistency preserves the order of causally related operations (if A caused B, all nodes see A before B), but allows concurrent operations to be seen in different orders by different nodes. This is the strongest model that can be achieved while maintaining availability during partitions:

// Causal dependency tracking with Vector Clocks:
// Each process maintains a vector clock V[0..n-1]
// On local event: V[self]++
// On send: attach current V to message
// On receive: V[i] = max(V[i], msg.V[i]) for all i; V[self]++

// Example: blog comment thread
Alice posts: "Nice article!"              VC_Alice=[1,0,0]
Bob replies to Alice: "I agree!"          VC_Bob=[1,1,0] (saw Alice's post)
Carol replies to Alice: "Disagree!"       VC_Carol=[1,0,1] (saw Alice's post)
Dave replies to Bob: "Why agree?"        VC_Dave=[1,1,0,1] (saw Bob's reply)

// Causal consistency guarantees:
// Any node that serves Bob's reply MUST have already applied Alice's post
// Any node that serves Dave's reply MUST have applied Bob's + Alice's
// Carol's and Bob's replies are CONCURRENT — can appear in any order

// COPS (Clusters of Order-Preserving Servers) — causal consistency protocol:
// Used by Facebook TAO (social graph), MongoDB sessions
// Write annotated with causal dependencies
// Remote DC checks: "have I applied all this write's dependencies?"
// If not: wait for dependencies before making write visible
// Avoids showing Bob's "I agree" before Alice's post that he's agreeing with!

Session Consistency Guarantees — Practical Strong Enough

For most applications, full linearizability is overkill. Session-level guarantees provide the right balance — strong guarantees within a user's session, weaker globally:

GuaranteeDefinitionImplementationViolated By
Read-Your-WritesAfter writing, you always read back your own writeRoute post-write reads to same replica for N seconds, or use LSN tokenWriting to primary, reading from lagging replica
Monotonic ReadsOnce you read a value, you never read an older valueSticky session to same replica; track read LSN per clientLoad balancer switching user between replicas with different lag
Monotonic WritesWrites from one client are applied in orderPer-client sequence numbers; leader serializes writes from same clientMulti-master where writes reach different masters out-of-order
Writes-Follow-ReadsWrites are ordered after reads that preceded them causallyAttach read timestamp to subsequent writes; ensure write applied afterAsync multi-master with no causal tracking
// Read-Your-Writes — LSN Token approach (AWS Aurora, CockroachDB):

async function createPost(userId, content) {
  // Write to primary
  const result = await primary.insert({ userId, content });

  // Primary returns its current log sequence number
  const lsn = result.lsn; // e.g., "0/18B3210"

  // Store LSN in user's session/cookie
  session.set('last_write_lsn', lsn);

  return result;
}

async function getMyPosts(userId, session) {
  const requiredLsn = session.get('last_write_lsn');

  // Ask read replica: "are you at least at this LSN?"
  const replicaLsn = await replica.query('SELECT pg_last_wal_replay_lsn()');

  if (replicaLsn >= requiredLsn) {
    return replica.query('SELECT * FROM posts WHERE user_id=$1', [userId]);
  } else {
    // Replica not caught up → read from primary OR wait
    return primary.query('SELECT * FROM posts WHERE user_id=$1', [userId]);
  }
}

Eventual Consistency — How Convergence Actually Works

Eventual consistency guarantees that if no new updates are made, all replicas will eventually converge to the same value. The key word is "eventually" — there is no bound on how long convergence takes. Two important properties distinguish well-designed eventually consistent systems:

// Convergence requires a conflict resolution strategy:

// 1. Last-Write-Wins (LWW) — simplest, most dangerous
// Each write has a timestamp. On conflict: highest timestamp wins.
// PROBLEM: Clock skew (NTP typically ±100ms) means "last" isn't accurate
// PROBLEM: Silent data loss — winning write obliterates losing write
// Cassandra default: LWW with client-provided timestamps
// Safe use: immutable events (sensor readings — latest IS correct)

// 2. Multi-Version Concurrency + Application Resolution
// DynamoDB: on conflict, store ALL concurrent versions
// Application reads ALL versions and decides which is correct
DynamoDB.get({
  TableName: 'cart',
  Key: { userId: '42' },
  ConsistentRead: false  // may return multiple versions
})
// Response may include: { Items: [{value: [bookA, bookB]}, {value: [bookA, bookC]}] }
// Shopping cart merge: UNION of all versions = [bookA, bookB, bookC]
// Amazon Dynamo paper: cart merge = union (never lose items)

// 3. CRDTs (Conflict-free Replicated Data Types) — mathematical convergence
// No conflict resolution needed — merge function is provably correct

// G-Counter (Grow-only): distributed unique ID counter
class GCounter {
  constructor(nodeId, n) {
    this.id = nodeId;
    this.counts = new Array(n).fill(0);
  }
  increment() { this.counts[this.id]++; }
  value() { return this.counts.reduce((a,b) => a+b, 0); }
  merge(other) {
    this.counts = this.counts.map((v,i) => Math.max(v, other.counts[i]));
  }
  // merge is: commutative, associative, idempotent
  // → Order doesn't matter, duplicate merges are safe → always converges!
}

// LWW-Register CRDT (safe version with HLC):
class LWWRegister {
  set(value, hlcTimestamp) {
    if (hlcTimestamp > this.timestamp) {
      this.value = value;
      this.timestamp = hlcTimestamp;
    }
  }
  merge(other) { this.set(other.value, other.timestamp); }
}

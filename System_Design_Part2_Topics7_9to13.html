7. HTTP vs HTTPS

7.1 HTTP Protocol Internals

7.1.1 HTTP/1.1 – Text-Based Request/Response

Client Server (port 80) │ │ │── TCP 3-way handshake (1 RTT) ─────────→│ SYN → SYN-ACK → ACK │ │ │── REQUEST (plaintext on wire) ─────────→│ │ GET /api/users HTTP/1.1 │ │ Host: api.example.com │ │ Authorization: Bearer eyJhbG... │ ← READABLE by any packet sniffer! │ Cookie: session_id=abc123 │ ← READABLE! │ │ │←── RESPONSE (plaintext) ───────────────│ │ HTTP/1.1 200 OK │ │ Content-Type: application/json │ │ Content-Length: 245 │ │ {"users":[{"ssn":"123-45-6789"...}]} │ ← Sensitive data exposed! │ │

How the kernel handles HTTP internally:

  • Application calls write(socket_fd, request_bytes)
  • Kernel copies data into TCP send buffer
  • TCP segments the data (MSS ~1460 bytes), adds TCP header (src port, dst port, seq#, checksum)
  • IP layer adds IP header (src IP, dst IP)
  • Data link adds Ethernet frame (MAC addresses)
  • At every hop (router, switch, WiFi AP), the HTTP payload is in plaintext — anyone with access to any intermediate network device can read the entire request/response

7.1.2 HTTP/1.1 Fundamental Problems

  • Head-of-Line Blocking: One TCP connection = one request at a time. If response 1 takes 5s, requests 2-10 wait. Browsers open 6 parallel connections as workaround (wasting memory, repeating TCP slow start).
  • Redundant Headers: Every request sends full headers (~800 bytes minimum). Cookies alone can be 4-8KB. Over 100 AJAX calls per page = 400-800KB wasted.
  • No Server Push: Server can only respond to explicit requests, never proactively send data the client will need.
  • Text Parsing Overhead: Finding end of headers requires scanning byte-by-byte for \r\n\r\n.

7.1.3 HTTP/2 – Binary Multiplexing

HTTP/2 Frame (binary): +-----------------------------------------------+ | Length (24 bits) | +---------------+---------------+---------------+ | Type (8) | Flags (8) | | +-+-------------+---------------+ | |R| Stream Identifier (31 bits) | +-----------------------------------------------+ | Frame Payload ... | +-----------------------------------------------+ Single TCP Connection with multiplexed streams: ┌──────────────────────────────────────────────────────────┐ │ [HEADERS stream=1 GET /page] [HEADERS stream=3 GET /js] │ │ [DATA stream=1 chunk1] [DATA stream=3 chunk1] │ │ [DATA stream=1 chunk2] [HEADERS stream=5 GET /css] │ │ [DATA stream=5 all] [DATA stream=3 chunk2] │ └──────────────────────────────────────────────────────────┘ No HTTP-level HOL blocking! Streams interleaved freely.

HPACK Header Compression:

  • Static table: 61 pre-defined header entries (:method: GET = index 2, just 1 byte)
  • Dynamic table: Headers indexed during connection. Second request referencing same header sends 1 byte instead of 50+.
  • Huffman encoding on literal values (optimized for HTTP character frequencies)
  • Result: 85-95% header size reduction after first request

7.1.4 HTTP/3 – QUIC (UDP-Based Transport)

Why HTTP/2 still has a problem: TCP treats all bytes as one ordered stream. If TCP packet #3 is lost, packets #4-10 are buffered by the kernel until #3 is retransmitted. ALL HTTP/2 streams are blocked — worse than HTTP/1.1's 6 connections.

// HTTP/3 over QUIC solves this:
// - Each QUIC stream has independent ordering and flow control
// - Lost packet on stream 1 does NOT block streams 3, 5, 7
// - Built-in TLS 1.3 (encrypted from first byte)
// - Connection identified by Connection ID, not IP:port tuple
//   → Phone switching WiFi→4G doesn't break the connection

// Connection establishment latency:
// TCP + TLS 1.2:  3 RTT (SYN/ACK + ClientHello/ServerHello + Finished)
// TCP + TLS 1.3:  2 RTT (SYN/ACK + 1-RTT TLS handshake)
// QUIC (first):   1 RTT (handshake includes TLS in same flight)
// QUIC (resume):  0 RTT (send application data in first packet!)
//
// On 100ms RTT transatlantic link:
// TCP+TLS1.2 = 300ms before first byte. QUIC resume = 0ms.

7.2.2 ECDHE Key Exchange – How Two Strangers Create a Shared Secret

// Elliptic Curve Diffie-Hellman Ephemeral (x25519):
//
// Both agree on curve: Curve25519, base point G
//
// Client:
//   private_a = 32 random bytes
//   public_A = private_a × G (elliptic curve point multiplication)
//   → Sends public_A to server (32 bytes in ClientHello key_share)
//
// Server:
//   private_b = 32 random bytes
//   public_B = private_b × G
//   → Sends public_B to client (32 bytes in ServerHello key_share)
//
// Shared secret (both independently compute):
//   Client: S = private_a × public_B = private_a × private_b × G
//   Server: S = private_b × public_A = private_b × private_a × G
//   S is identical! Used as input to HKDF to derive encryption keys.
//
// Why "Ephemeral" (the E in ECDHE):
//   private_a and private_b are DISCARDED after handshake.
//   → Perfect Forward Secrecy: Even if server's long-term key leaks tomorrow,
//     today's recorded traffic CANNOT be decrypted (attacker doesn't have
//     the ephemeral private keys).
//
// Performance: x25519 = ~50 microseconds per operation (negligible)

7.4 HTTPS Performance (Modern Reality)

Myth: "HTTPS is slow." Reality in 2024+:
  • AES-NI hardware: ~1 CPU cycle per byte = 30+ Gbps encryption throughput on a single core
  • TLS 1.3: Only +1 RTT latency (0 RTT on resumption)
  • Session tickets: Client caches session state, resumes without full handshake
  • OCSP stapling: Server pre-fetches revocation proof, saves client a round trip
  • Net effect: HTTP/2 (requires HTTPS) multiplexing SAVES more latency than TLS adds. HTTPS is often FASTER.

9. Circuit Breaker

9.1 The Problem: Cascading Failures

Without Circuit Breaker: ┌─────────┐ ┌─────────┐ ┌─────────────┐ │ Service │────→│ Service │────→│ Database │ ← DOWN (overloaded) │ A │ │ B │ │ │ └─────────┘ └─────────┘ └─────────────┘ 1. Database becomes slow (10s response instead of 50ms) 2. Service B threads all blocked waiting for DB (thread pool exhausted) 3. Service B can't handle ANY requests (not just DB ones) 4. Service A requests to B time out (30s × 100 connections = all threads stuck) 5. Service A also becomes unresponsive 6. Entire system is DOWN due to one slow dependency CASCADE: One failure → consumes all threads → propagates upstream → total outage

9.2 Circuit Breaker – State Machine

┌─────────────────────────────────────────┐ │ │ ▼ failure_count >= threshold │ ┌──────────┐ ──────────────────────────→ ┌──────────┐ │ CLOSED │ │ OPEN │ │ (normal) │ ←─────────────────────────── │ (reject) │ └──────────┘ probe succeeds └──────────┘ ▲ │ │ │ │ timeout expires │ │ ▼ │ ┌───────────┐ └────── probe succeeds ────────────│ HALF-OPEN │ │ (probe) │ probe fails ───────────────→└───────────┘ (back to OPEN) │ │ Allow limited requests through to test recovery

State Details:

StateBehaviorTransition Trigger
CLOSED All requests pass through normally. Failures are counted in a sliding window. → OPEN: when failure rate exceeds threshold (e.g., 50% in last 10 seconds, minimum 20 calls)
OPEN ALL requests immediately fail with fallback response. No network calls to downstream. Extremely fast (microseconds). → HALF-OPEN: after configured timeout (e.g., 30 seconds)
HALF-OPEN Allow a limited number of probe requests (e.g., 3-5) through to test if downstream recovered. → CLOSED: if probes succeed
→ OPEN: if any probe fails

9.3 Implementation – Production-Grade

class CircuitBreaker {
    constructor(options) {
        this.name = options.name;
        this.failureThreshold = options.failureThreshold || 0.5;  // 50% failure rate
        this.minimumCalls = options.minimumCalls || 20;           // need at least 20 calls to evaluate
        this.openDuration = options.openDuration || 30000;        // 30s in OPEN state
        this.halfOpenPermits = options.halfOpenPermits || 5;      // 5 probe requests

        this.state = 'CLOSED';
        this.slidingWindow = new SlidingWindowMetrics(options.windowSize || 10000); // 10s window
        this.openedAt = null;
        this.halfOpenSuccesses = 0;
        this.halfOpenFailures = 0;
    }

    async execute(fn, fallback) {
        // OPEN state: fail fast
        if (this.state === 'OPEN') {
            if (Date.now() - this.openedAt >= this.openDuration) {
                this.transitionTo('HALF_OPEN');
            } else {
                this.metrics.recordRejection();
                return fallback ? fallback() : Promise.reject(new CircuitOpenError(this.name));
            }
        }

        // HALF-OPEN state: allow limited probes
        if (this.state === 'HALF_OPEN') {
            if (this.halfOpenSuccesses + this.halfOpenFailures >= this.halfOpenPermits) {
                // All probe slots used, reject remaining
                return fallback ? fallback() : Promise.reject(new CircuitOpenError(this.name));
            }
        }

        // Execute the actual call
        const startTime = Date.now();
        try {
            const result = await fn();
            this.onSuccess(Date.now() - startTime);
            return result;
        } catch (error) {
            this.onFailure(error, Date.now() - startTime);
            if (fallback) return fallback();
            throw error;
        }
    }

    onSuccess(duration) {
        if (this.state === 'HALF_OPEN') {
            this.halfOpenSuccesses++;
            if (this.halfOpenSuccesses >= this.halfOpenPermits) {
                this.transitionTo('CLOSED');  // Recovered!
            }
        } else {
            this.slidingWindow.recordSuccess(duration);
        }
    }

    onFailure(error, duration) {
        if (this.state === 'HALF_OPEN') {
            this.halfOpenFailures++;
            this.transitionTo('OPEN');  // Still broken
        } else {
            this.slidingWindow.recordFailure(duration);
            this.evaluateState();
        }
    }

    evaluateState() {
        const metrics = this.slidingWindow.getMetrics();
        if (metrics.totalCalls >= this.minimumCalls) {
            const failureRate = metrics.failures / metrics.totalCalls;
            if (failureRate >= this.failureThreshold) {
                this.transitionTo('OPEN');
            }
        }
    }

    transitionTo(newState) {
        console.log(`CircuitBreaker[${this.name}]: ${this.state} → ${newState}`);
        this.state = newState;
        if (newState === 'OPEN') {
            this.openedAt = Date.now();
            this.emitEvent('circuit_opened');
        } else if (newState === 'HALF_OPEN') {
            this.halfOpenSuccesses = 0;
            this.halfOpenFailures = 0;
        } else if (newState === 'CLOSED') {
            this.slidingWindow.reset();
            this.emitEvent('circuit_closed');
        }
    }
}

9.4 Sliding Window Implementations

Count-Based Sliding Window:

// Fixed-size ring buffer of last N calls
// Pro: Simple, predictable memory
// Con: Time-insensitive (old calls have same weight as recent)

class CountBasedWindow {
    constructor(size = 100) {
        this.buffer = new Array(size);
        this.index = 0;
        this.size = size;
    }

    record(outcome) {  // outcome: 'success' | 'failure' | 'slow'
        this.buffer[this.index % this.size] = outcome;
        this.index++;
    }

    getFailureRate() {
        const filled = Math.min(this.index, this.size);
        const failures = this.buffer.slice(0, filled).filter(o => o === 'failure').length;
        return failures / filled;
    }
}

Time-Based Sliding Window:

// Divide time into buckets (e.g., 10 buckets of 1 second each = 10s window)
// Pro: Recent failures weighted appropriately
// Con: Slightly more memory

class TimeBasedWindow {
    constructor(windowMs = 10000, buckets = 10) {
        this.windowMs = windowMs;
        this.bucketMs = windowMs / buckets;
        this.buckets = new Array(buckets).fill(null).map(() => ({
            successes: 0, failures: 0, slowCalls: 0, timestamp: 0
        }));
    }

    record(outcome) {
        const now = Date.now();
        const bucketIndex = Math.floor((now / this.bucketMs) % this.buckets.length);
        const bucket = this.buckets[bucketIndex];

        // Reset bucket if it's from a previous rotation
        if (now - bucket.timestamp > this.windowMs) {
            bucket.successes = 0;
            bucket.failures = 0;
            bucket.slowCalls = 0;
        }
        bucket.timestamp = now;

        if (outcome === 'failure') bucket.failures++;
        else if (outcome === 'slow') bucket.slowCalls++;
        else bucket.successes++;
    }

    getMetrics() {
        const now = Date.now();
        let total = 0, failures = 0;
        for (const bucket of this.buckets) {
            if (now - bucket.timestamp <= this.windowMs) {
                total += bucket.successes + bucket.failures + bucket.slowCalls;
                failures += bucket.failures + bucket.slowCalls;
            }
        }
        return { totalCalls: total, failures, failureRate: total > 0 ? failures / total : 0 };
    }
}

9.5 Fallback Strategies

// When circuit is OPEN, return degraded but useful responses:

const breaker = new CircuitBreaker({ name: 'recommendation-service' });

async function getRecommendations(userId) {
    return breaker.execute(
        // Primary: call recommendation service
        () => recommendationService.getPersonalized(userId),

        // Fallback hierarchy:

            // Fallback 1: Try cache (stale is better than nothing)

            // Fallback 2: Return popular items (pre-computed, always available)

            // Fallback 3: Return empty (graceful degradation)

}

9.6 Circuit Breaker vs Retry vs Timeout

PatternPurposeWhen to Use
TimeoutLimit how long to wait for a single requestAlways. Every network call needs a timeout.
RetryRetry transient failures (network blip, temporary 503)Idempotent operations + exponential backoff + jitter
Circuit BreakerStop calling a service that's clearly brokenWhen dependency is DOWN (not just occasional failures). Prevents wasting resources on doomed calls.
Combined Pattern (production standard):
Request → Timeout (5s) → Retry (2 attempts, exponential backoff) → Circuit Breaker (tracks failure rate across all requests).

If circuit is OPEN, skip both timeout and retry — fail immediately (microseconds instead of 10+ seconds).

10. Bandwidth

10.1 Definitions: Bandwidth vs Throughput vs Latency

TermDefinitionAnalogy
BandwidthMaximum theoretical data transfer rate of a link (bits/second)Width of a highway (how many lanes)
ThroughputActual data transfer rate achieved (always ≤ bandwidth)Actual cars passing per hour (affected by traffic, accidents)
LatencyTime for a single unit of data to travel from source to destinationTime for one car to drive the full highway length
Key Insight: Bandwidth × Latency = "Bandwidth-Delay Product" (BDP) = how much data can be "in flight" in the network at any moment.

Example: 1 Gbps link, 50ms RTT:
BDP = 1,000,000,000 bits/s × 0.050 s = 50,000,000 bits = 6.25 MB
TCP must have a window of at least 6.25 MB to fully utilize this link!
Default TCP buffer (64KB) would only achieve 64KB/50ms = 10 Mbps on a 1Gbps link (1% utilization!).

10.3.2 TCP Congestion Control – How Bandwidth is Shared

TCP dynamically adjusts sending rate to avoid overwhelming the network. Understanding this is crucial for system performance.

TCP Congestion Window (cwnd) over time: cwnd │ │ ┌──── Congestion event (packet loss) │ │ cwnd cut in half │ ▼ │ ╱─────────╲ │ ╱ ╲────────╱────── │ ╱ (linear increase) (linear again) │ ╱ │ ╱ ← Exponential growth (Slow Start) │╱ └──────────────────────────────────────── time │← Slow →│←── Congestion Avoidance ──→│ Start Algorithms: - Slow Start: cwnd doubles every RTT (exponential) until threshold or loss - Congestion Avoidance: cwnd += 1 MSS per RTT (linear, AIMD) - On loss: cwnd halved (multiplicative decrease) - Modern: BBR (Google) measures actual bottleneck bandwidth + min RTT instead of relying on packet loss signals

10.3.3 Bandwidth Optimization Techniques

// 1. COMPRESSION: Reduce data size on wire
//    gzip: 60-80% reduction for text (HTML, JSON, CSS, JS)
//    Brotli: 15-25% better than gzip (used by modern CDNs)
//    Protocol Buffers: 3-10x smaller than JSON for structured data

// 2. BATCHING: Amortize per-request overhead
//    Instead of 100 individual API calls:
//    POST /api/batch
//    { "requests": [{"method":"GET","path":"/users/1"}, ...] }
//    Saves: 100 × TCP headers + 100 × TLS records = significant overhead

// 3. DELTA ENCODING: Send only changes
//    Full sync: 10MB user data every time
//    Delta sync: {"updated": [...], "deleted": [...]} = 50KB
//    Used by: Dropbox, git, database replication

// 4. CONNECTION POOLING: Reuse TCP connections
//    TCP handshake: 1 RTT + TLS: 1-2 RTT = wasted bandwidth for short requests
//    HTTP/2: Single connection, unlimited requests
//    Database: Pool of 20 connections reused across thousands of queries

// 5. EDGE COMPUTING: Reduce distance = reduce latency × bandwidth waste
//    Process data at the edge (CDN, IoT gateway)
//    Only send aggregated results to origin

10.5 Bandwidth Cost in Cloud

Cloud bandwidth pricing (a major cost driver):
  • Inbound (ingress): Usually FREE
  • Outbound (egress): $0.01-0.09 per GB (AWS/GCP/Azure)
  • Cross-region: $0.01-0.02 per GB
  • Cross-AZ (same region): $0.01 per GB (often overlooked!)
  • Same-AZ: FREE (keep communicating services in same AZ when possible)
At scale: 100TB/month egress = $5,000-$9,000/month just for bandwidth!
Design implication: CDNs, compression, and caching directly reduce cloud bills.

11.2 Anycast Routing – How Users Reach the Nearest PoP

CDN edge servers share the same IP address globally. BGP (Border Gateway Protocol) routing automatically sends packets to the geographically closest one.

// How Anycast works:
// 1. CDN announces the same IP prefix (e.g., 104.16.0.0/12) from ALL PoPs globally
// 2. Each PoP advertises this to their upstream ISPs via BGP
// 3. Internet routers choose the "shortest AS-path" to reach that IP
// 4. Result: Tokyo user's packets route to Tokyo PoP, London user's to London PoP
//    All using the SAME destination IP address!

// DNS resolution for CDN-fronted site:
// www.example.com → CNAME → www.example.com.cdn.cloudflare.net → A 104.16.123.45
// That IP (104.16.123.45) exists in 300+ PoPs simultaneously
// User connects to whichever is topologically closest

// Failover: If a PoP goes down, BGP withdraws the route
//   → traffic automatically flows to next-nearest PoP (seconds)
//   → No DNS TTL propagation delay!

11.3 CDN Caching – Deep Internals

11.3.1 Cache Key Construction

// What uniquely identifies a cached object?
// Default cache key: scheme + host + path + query string
// Example: https://example.com/images/logo.png?v=2

// Cache key variations (configurable):
cache_key = hash(
    method,                    // GET vs POST (POST usually not cached)
    scheme,                    // http vs https
    host,                      // example.com
    path,                      // /images/logo.png
    sorted_query_params,       // ?v=2 (sorted to normalize order)
    // Optional:
    accept_encoding_header,    // gzip vs br (different cached variants)
    cookie['country'],         // geo-specific content
    device_type,               // mobile vs desktop (if Vary header used)
);

// Vary Header: Tells CDN to cache multiple variants
// Response: Vary: Accept-Encoding, Accept-Language
// CDN stores separate cached copies for:
//   Accept-Encoding: gzip  → compressed version
//   Accept-Encoding: br    → brotli version
//   Accept-Language: en    → English version
//   Accept-Language: fr    → French version

11.3.2 Cache-Control Headers (Origin → CDN → Browser)

// Origin server tells CDN AND browser how to cache:

// Cache publicly (CDN + browser) for 1 year (immutable assets):
Cache-Control: public, max-age=31536000, immutable
// Used for: versioned assets (app.a3f2b1.js, style.8c4d2e.css)
// 'immutable' = don't even revalidate on browser refresh

// Cache at CDN for 1 hour, browser for 5 minutes:
Cache-Control: public, max-age=300, s-maxage=3600
// s-maxage = shared cache (CDN) TTL, overrides max-age for CDN
// max-age = browser TTL
// Use case: API responses that change occasionally

// Don't cache (sensitive data):
Cache-Control: private, no-store, no-cache
// private = only browser can cache (CDN must not)
// no-store = don't cache anywhere
// no-cache = cache it but revalidate with origin every time (confusing name!)

// Stale-while-revalidate (modern, brilliant for performance):
Cache-Control: public, max-age=60, stale-while-revalidate=300
// First 60s: serve from cache (fresh)
// 60-360s: serve STALE cache immediately, revalidate in background
// After 360s: must revalidate before serving
// Result: Users almost NEVER wait for origin response!

11.3.3 Cache Revalidation (Conditional Requests)

ETag-based revalidation: First request: Client → CDN: GET /api/products CDN → Origin: GET /api/products Origin → CDN: 200 OK, ETag: "a1b2c3d4", body: [large JSON] CDN → Client: 200 OK, ETag: "a1b2c3d4", body: [large JSON] CDN stores: {key: /api/products, etag: "a1b2c3d4", body: [...]} After TTL expires, next request: Client → CDN: GET /api/products CDN → Origin: GET /api/products, If-None-Match: "a1b2c3d4" If content unchanged: Origin → CDN: 304 Not Modified (NO body! saves bandwidth) CDN refreshes TTL, serves cached body to client If content changed: Origin → CDN: 200 OK, ETag: "e5f6g7h8", body: [new JSON] CDN updates cache, serves new body

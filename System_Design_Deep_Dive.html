1. Scalability

1.1 What Scalability Really Means Internally

Scalability is the capability of a system to handle a growing amount of work by adding resources. It's not just "adding more servers"—it involves fundamental architectural decisions about how data flows, how state is managed, and how components communicate under increasing load.

A system is scalable if its performance characteristics (latency, throughput) degrade gracefully—or not at all—as the workload increases proportionally with added resources.

1.2 Vertical Scaling (Scale Up)

Vertical scaling means increasing the capacity of a single machine—adding more CPU cores, RAM, faster SSDs, or upgrading to a more powerful NIC.

How It Works Internally:

  • CPU Scaling: Adding cores allows the OS scheduler (e.g., Linux CFS - Completely Fair Scheduler) to distribute threads across cores. However, Amdahl's Law limits the speedup: Speedup = 1 / (S + (1-S)/N) where S is the serial fraction and N is the number of processors.
  • Memory Scaling: More RAM means larger page caches, reducing disk I/O. The kernel's virtual memory manager uses page tables (4-level on x86_64) to map virtual addresses to physical frames. More RAM = fewer page faults = fewer expensive disk reads.
  • Disk I/O Scaling: NVMe SSDs communicate via PCIe lanes directly, bypassing the SATA/AHCI bottleneck. They support multiple I/O queues (up to 65,535) compared to SATA's single queue of depth 32.
Limitations: There's a hardware ceiling (you can't buy a single machine with 10TB RAM easily). Single point of failure remains. Context switching overhead increases with too many threads on limited cores. NUMA (Non-Uniform Memory Access) effects mean not all RAM access is equal on multi-socket systems.

1.3 Horizontal Scaling (Scale Out)

Horizontal scaling means adding more machines to distribute the workload. This is what modern distributed systems rely on.

How It Works Internally:

1.3.1 Stateless Service Scaling

Stateless services (e.g., API servers) are the easiest to scale horizontally. Each request contains all information needed to process it. No shared mutable state between instances.

// Stateless API server - any instance can handle any request
app.get('/user/:id', async (req, res) => {
    // All state comes from the request + external data store
    const user = await database.query('SELECT * FROM users WHERE id = ?', [req.params.id]);
    res.json(user);
});

Behind the scenes, a load balancer distributes incoming TCP connections across instances. Each instance maintains its own connection pool to the database.

1.3.2 Stateful Service Scaling - The Hard Problem

When services hold state (sessions, caches, in-memory data), scaling requires:

  • Sticky Sessions: The load balancer routes requests from the same client to the same backend (using cookies or IP hash). Problem: uneven load distribution, failover loses state.
  • Externalized State: Move state to a shared store (Redis, Memcached). Now services are stateless again, but you've moved the scaling problem to the data layer.
  • Partitioned State (Sharding): Distribute state across nodes using consistent hashing or range-based partitioning.

1.3.3 Database Horizontal Scaling

Sharding partitions data across multiple database instances. Each shard holds a subset of the data.

Sharding Strategies: 1. Hash-Based Sharding: shard_id = hash(partition_key) % num_shards User ID 12345 → hash(12345) = 0xA3F2... → mod 4 → Shard 2 2. Range-Based Sharding: Users A-F → Shard 1 Users G-M → Shard 2 Users N-S → Shard 3 Users T-Z → Shard 4 3. Directory-Based Sharding: Lookup service maps keys → shards Flexible but adds latency + single point of failure

Consistent Hashing (Deep Dive):

Traditional modular hashing (hash(key) % N) breaks when N changes—almost all keys remap. Consistent hashing solves this:

  • Imagine a ring of values [0, 2^32 - 1]
  • Each node is hashed to a position on the ring
  • Each key is hashed and walks clockwise to find its assigned node
  • When a node is added/removed, only K/N keys need to move (where K = total keys, N = total nodes)
  • Virtual nodes: Each physical node maps to multiple positions on the ring (e.g., 150-200 vnodes) to ensure even distribution. Without vnodes, node removal can cause cascading hotspots.
// Consistent Hashing Implementation Concept
class ConsistentHash {
    constructor(nodes, virtualNodeCount = 150) {
        this.ring = new TreeMap(); // sorted map
        for (const node of nodes) {
            for (let i = 0; i < virtualNodeCount; i++) {
                const hash = md5(`${node}-vnode-${i}`);
                this.ring.set(hash, node);
            }
        }
    }

    getNode(key) {
        const hash = md5(key);
        // Find the first node position >= hash (clockwise walk)
        const entry = this.ring.ceilingEntry(hash);
        return entry ? entry.value : this.ring.firstEntry().value;
    }
}

1.4 Data Replication Strategies

1.4.1 Single-Leader Replication

One node (leader/primary) accepts writes. Replicas receive a replication log (WAL - Write-Ahead Log in PostgreSQL, binlog in MySQL).

  • Synchronous replication: Leader waits for at least one replica to acknowledge before confirming write to client. Guarantees durability but adds latency.
  • Asynchronous replication: Leader confirms immediately. Replicas may lag (replication lag). Risk: if leader dies, confirmed writes may be lost.
  • Semi-synchronous: One replica is synchronous, rest are async. Best trade-off for most systems.

1.4.2 Multi-Leader Replication

Multiple nodes accept writes. Used in multi-datacenter setups. Challenge: write conflicts when two leaders modify the same data.

Conflict Resolution Strategies:

  • Last Writer Wins (LWW): Timestamp-based. Simple but loses data. Used by Cassandra.
  • Merge: Concatenate/union conflicting values (CRDTs - Conflict-free Replicated Data Types).
  • Custom resolution: Application-level logic (e.g., Git-style manual merge).

1.4.3 Leaderless Replication (Dynamo-style)

Any node accepts reads/writes. Uses quorum: W + R > N for consistency (W = write acknowledgments needed, R = read nodes queried, N = total replicas).

Example - Cassandra with N=3, W=2, R=2:
Write goes to all 3 replicas. Client waits for 2 ACKs. Read queries 2 replicas and takes the value with the highest timestamp. Since W+R (4) > N (3), at least one node in the read set has the latest write → strong consistency.

1.5 Caching for Scalability

Cache Patterns (Internal Mechanics):

PatternHow It WorksTrade-offs
Cache-Aside (Lazy Loading) App checks cache first. On miss, reads from DB, populates cache, returns data. On write, app updates DB and invalidates/updates cache. Cache misses cause extra latency (cache check + DB read + cache write). Stale data possible if DB is updated without cache invalidation.
Write-Through Every write goes to cache AND database synchronously. Reads always hit cache. Write latency increases (two writes per operation). Cache always consistent. Cold start problem (cache is empty initially).
Write-Behind (Write-Back) Writes go to cache only. Cache asynchronously flushes to DB in batches. Extremely fast writes. Risk of data loss if cache node dies before flush. Complex to implement correctly.
Read-Through Cache itself is responsible for loading data from DB on miss. App only talks to cache. Simpler application code. Cache library must support DB integration.

Redis implements an approximated LRU. Instead of maintaining a linked list of all keys (expensive), it samples N random keys and evicts the one with the oldest access time. This is O(1) per eviction vs O(N) for true LRU.

1.6 Scalability Anti-Patterns

  • Distributed Monolith: Microservices that are tightly coupled—deploying one requires deploying others. You get the complexity of distribution without the scaling benefits.
  • Shared Mutable State: Multiple services writing to the same database table. Creates hidden coupling and contention.
  • N+1 Query Problem at Scale: Fetching a list of 1000 items, then making 1000 individual queries for related data. At scale, this explodes latency.
  • Synchronous Chains: Service A → B → C → D synchronously. Latency is additive. Failure in any link breaks the chain.

2. Availability

2.1 Defining Availability Mathematically

Availability = Uptime / (Uptime + Downtime) over a given period.

2.2 Serial vs Parallel Availability

Components in Series (all must work):

A_total = A1 × A2 × A3 × ... × An

Example: Load Balancer (99.99%) → App Server (99.99%) → Database (99.99%)
Total = 0.9999 × 0.9999 × 0.9999 = 99.97% — worse than any individual component!

Components in Parallel (any one must work):

A_total = 1 - (1 - A1) × (1 - A2) × ... × (1 - An)

Example: Two database replicas, each 99.9% available:
Total = 1 - (0.001 × 0.001) = 1 - 0.000001 = 99.9999% — dramatically better!

2.3 Failure Detection Mechanisms

2.3.1 Heartbeats

Nodes periodically send "I'm alive" messages. If no heartbeat is received within a timeout, the node is considered dead.

  • Timeout tuning: Too short → false positives (healthy node marked dead due to network jitter). Too long → slow detection of actual failures.
  • Phi Accrual Failure Detector (Cassandra): Instead of binary alive/dead, calculates a suspicion level (phi) based on the statistical distribution of heartbeat inter-arrival times. Adapts to network conditions automatically.
// Phi Accrual Failure Detector concept
// Maintains a sliding window of heartbeat arrival intervals
// Calculates phi = -log10(1 - CDF(timeSinceLastHeartbeat))
// If phi > threshold (e.g., 8), node is considered dead
// Phi of 1 = 10% chance of false positive
// Phi of 8 = 0.00000001% chance of false positive

2.3.2 Gossip Protocols

Each node periodically picks a random peer and exchanges state information. Information propagates exponentially—reaches all N nodes in O(log N) rounds.

How it works internally:

  1. Each node maintains a list of all members with their heartbeat counters and timestamps
  2. Every T seconds, a node increments its own heartbeat counter
  3. It picks a random peer and sends its full member list
  4. The receiving peer merges the list (keeping higher heartbeat counters)
  5. If a member's heartbeat hasn't increased in T_fail seconds, it's marked suspicious
  6. After T_cleanup more seconds, it's removed from the list

2.4 Redundancy Patterns

2.4.1 Active-Passive (Failover)

┌─────────────┐ Heartbeat ┌─────────────┐ │ Primary │ ←───────────────→ │ Standby │ │ (Active) │ │ (Passive) │ └──────┬──────┘ └──────┬──────┘ │ │ │ Replication (sync/async) │ │ WAL shipping / streaming │ └──────────────────────────────────┘ On primary failure: 1. Standby detects missing heartbeats 2. Standby promotes itself to primary 3. VIP (Virtual IP) floats to new primary 4. Clients reconnect transparently

Split-Brain Problem: Both nodes think they're primary (network partition between them, but both can reach clients). Solutions:

  • STONITH (Shoot The Other Node In The Head): Fencing mechanism that power-cycles the other node via IPMI/iLO.
  • Quorum-based: Need majority of cluster to agree on who is primary. With 2 nodes, add a witness/arbiter.
  • Lease-based: Primary holds a time-limited lease from a distributed lock service (ZooKeeper, etcd). Must renew before expiry or lose primary status.

2.4.2 Active-Active

All nodes handle traffic simultaneously. More complex but better resource utilization and no failover delay.

  • Stateless services: straightforward—all instances serve requests
  • Stateful services: requires distributed consensus or conflict resolution
  • Databases: multi-primary with conflict resolution (CRDTs, vector clocks, application-level merge)

2.5 Consensus Algorithms for High Availability

2.5.1 Raft (used in etcd, CockroachDB, TiKV)

Raft ensures a cluster of nodes agrees on a sequence of operations despite failures.

  1. Leader Election: Nodes start as followers. If a follower doesn't hear from a leader within election timeout (randomized 150-300ms), it becomes a candidate and requests votes. Majority grants leadership.
  2. Log Replication: Leader receives client writes, appends to its log, sends AppendEntries RPCs to followers. Once majority acknowledges, entry is committed.
  3. Safety: A candidate can only win if its log is at least as up-to-date as the majority. This prevents stale nodes from becoming leader and losing committed entries.

2.6 Circuit Breaker Pattern (Internal Mechanics)

Prevents cascading failures by failing fast when a downstream service is unhealthy.

States: ┌────────┐ failure threshold ┌────────┐ timeout ┌───────────┐ │ CLOSED │ ─────────────────────→ │ OPEN │ ────────────→ │ HALF-OPEN │ │(normal)│ │(reject)│ │ (probe) │ └────────┘ └────────┘ └───────────┘ ↑ ↑ │ │ success │ failure │ └──────────────────────────────────┼────────────────────────┘ │ (probe failed)
  • CLOSED: Requests pass through. Track failure rate in sliding window (e.g., 50% failures in last 10 seconds).
  • OPEN: All requests immediately fail with fallback response. No network calls to downstream. Timer starts.
  • HALF-OPEN: After timeout, allow one probe request. If succeeds → CLOSED. If fails → OPEN again.
// Circuit Breaker implementation concept
class CircuitBreaker {
    constructor(options) {
        this.failureThreshold = options.failureThreshold || 5;
        this.resetTimeout = options.resetTimeout || 30000; // 30s
        this.state = 'CLOSED';
        this.failureCount = 0;
        this.lastFailureTime = null;
        this.slidingWindow = new SlidingWindowCounter(10000); // 10s window
    }

    async call(fn) {
        if (this.state === 'OPEN') {
            if (Date.now() - this.lastFailureTime > this.resetTimeout) {
                this.state = 'HALF_OPEN';
            } else {
                throw new CircuitOpenError('Service unavailable');
            }
        }

        try {
            const result = await fn();
            this.onSuccess();
            return result;
        } catch (error) {
            this.onFailure();
            throw error;
        }
    }

    onSuccess() {
        this.failureCount = 0;
        this.state = 'CLOSED';
    }

    onFailure() {
        this.failureCount++;
        this.lastFailureTime = Date.now();
        this.slidingWindow.record();
        if (this.slidingWindow.count() >= this.failureThreshold) {
            this.state = 'OPEN';
        }
    }
}

2.7 Graceful Degradation

When parts of the system fail, serve reduced functionality rather than complete failure:

  • Netflix: If recommendation service is down, show generic popular content instead of personalized recommendations
  • Twitter: If timeline generation is slow, serve cached (slightly stale) timeline
  • E-commerce: If inventory service is slow, allow checkout but verify stock asynchronously (with possible backorder notification)

2.8 Health Checks - Deep Dive

  • Shallow health check: /health returns 200 if process is running. Doesn't verify dependencies.
  • Deep health check: /health/ready verifies database connectivity, cache connectivity, disk space, memory. Used by orchestrators (Kubernetes readiness probe) to remove unhealthy pods from service.
  • Liveness vs Readiness (Kubernetes): Liveness failure → restart container. Readiness failure → stop sending traffic but don't restart.

3. Load Balancing

3.1 Why Load Balancing Exists

A single server has finite capacity. Load balancers distribute traffic across multiple servers, providing: horizontal scalability, high availability (routes around failed servers), and SSL termination offloading.

3.2 OSI Layer Classification

3.2.1 Layer 4 (Transport Layer) Load Balancing

Operates at TCP/UDP level. Makes routing decisions based on IP address and port number without inspecting packet content.

Internal mechanics:

  • NAT-based: LB rewrites destination IP/port in packet headers. Backend sees LB's IP as source (unless DSR is used).
  • Direct Server Return (DSR): LB only handles inbound traffic. Responses go directly from backend to client, bypassing LB. Dramatically reduces LB bandwidth requirements (responses are typically 10-100x larger than requests).
  • IP tunneling (IPIP): LB encapsulates original packet in a new IP packet destined for the backend. Backend decapsulates and responds directly to client.
NAT Mode: Client → [SYN dst=LB:80] → LB rewrites → [SYN dst=Backend1:80] → Backend1 Client ← [ACK src=LB:80] ← LB rewrites ← [ACK src=Backend1:80] ← Backend1 DSR Mode: Client → [SYN dst=VIP:80] → LB (only touches inbound) → Backend1 Client ← [ACK src=VIP:80] ← Backend1 (responds directly, spoofs VIP as source)

Performance: L4 LBs can handle millions of connections/sec because they don't parse HTTP. Linux IPVS (IP Virtual Server) operates in kernel space, handling 1M+ connections with minimal overhead.

3.2.2 Layer 7 (Application Layer) Load Balancing

Terminates the TCP connection, parses HTTP, and makes routing decisions based on URL path, headers, cookies, request body.

Internal mechanics:

  • Client establishes TCP + TLS connection with LB
  • LB terminates TLS (decrypts request)
  • LB parses HTTP request (headers, URL, method)
  • Routing decision made based on rules (e.g., /api/* → API cluster, /static/* → CDN origin)
  • LB establishes separate TCP connection to chosen backend (connection pooling/reuse)
  • LB forwards request, receives response, forwards to client
# NGINX L7 Load Balancing - content-based routing
upstream api_servers {
    server 10.0.1.1:8080 weight=3;
    server 10.0.1.2:8080 weight=2;
    server 10.0.1.3:8080 weight=1;
    keepalive 64; # connection pool to backends
}

upstream static_servers {
    server 10.0.2.1:80;
    server 10.0.2.2:80;
}

server {
    listen 443 ssl;

    location /api/ {
        proxy_pass http://api_servers;
        proxy_http_version 1.1;
        proxy_set_header Connection ""; # enable keepalive to backend
    }

    location /static/ {
        proxy_pass http://static_servers;
        proxy_cache_valid 200 1h;
    }

    # Route based on cookie (sticky sessions)
    location /app/ {
        set $backend "";
        if ($cookie_server_id = "server1") {
            set $backend "10.0.1.1:8080";
        }
        proxy_pass http://$backend;
    }
}

3.3 Load Balancing Algorithms - Deep Internals

3.3.1 Round Robin

Simplest algorithm. Rotates through servers sequentially. Maintains a counter; each new connection goes to servers[counter % N].

Problem: Assumes all servers have equal capacity and all requests have equal cost. A slow request on Server A ties up that connection while Server B sits idle.

3.3.2 Weighted Round Robin

Assigns weights based on server capacity. Server with weight 3 gets 3x the traffic of weight 1.

// Smooth Weighted Round Robin (NGINX's implementation)
// Prevents burst allocation to high-weight servers
// Each round: current_weight += effective_weight
// Select server with highest current_weight
// Selected server: current_weight -= total_weight

// Example: A(weight=5), B(weight=1), C(weight=1), total=7
// Round 1: A=5, B=1, C=1 → select A → A=-2, B=1, C=1
// Round 2: A=3, B=2, C=2 → select A → A=-4, B=2, C=2
// Round 3: A=1, B=3, C=3 → select B → A=1, B=-4, C=3
// Result: A,A,B,A,C,A,A (spread evenly, not AAAAA,B,C)

3.3.3 Least Connections

Routes to the server with fewest active connections. Better than round robin for long-lived connections or variable request processing times.

Implementation: LB maintains a counter per backend. Increment on new connection, decrement on connection close. O(N) to find minimum, or use a min-heap for O(log N).

3.3.4 Least Response Time

Routes to the server with the lowest average response time AND fewest active connections. Requires the LB to track response times using exponential moving average (EMA).

// Exponential Moving Average for response time tracking
// new_avg = alpha * latest_response_time + (1 - alpha) * old_avg
// alpha = 0.1 means recent measurements have 10% influence
// Prevents a single outlier from drastically changing routing

3.3.5 Consistent Hashing (for Load Balancing)

Hash the request (by client IP, URL, or session ID) to determine the backend. Same request always goes to the same backend → useful for cache affinity.

3.3.6 Power of Two Random Choices (P2C)

Pick two random backends, route to the one with fewer connections. Surprisingly, this simple algorithm provides near-optimal load distribution and is used by Envoy proxy.

Why it works: With pure random choice, the most loaded server has O(log N / log log N) connections above average. With two choices, this drops to O(log log N) — exponential improvement.

3.4 Health Checking Internals

  • Active health checks: LB periodically sends probe requests (TCP connect, HTTP GET /health). Configurable interval (e.g., every 5s), threshold (e.g., 3 consecutive failures = unhealthy).
  • Passive health checks: LB monitors actual traffic responses. If backend returns 5xx errors or timeouts exceed threshold, mark unhealthy. No extra probe traffic.
  • Hybrid: Use passive checks for quick detection, active checks for recovery detection (when to add server back).

3.5 Global Server Load Balancing (GSLB)

Distributes traffic across geographically distributed data centers using DNS-based routing:

  • GeoDNS: Returns different IP addresses based on client's geographic location (determined by source IP of DNS resolver)
  • Latency-based: Routes to the datacenter with lowest measured latency (AWS Route 53)
  • Failover: Health-checks each datacenter. If primary fails, DNS returns secondary datacenter IPs

3.6 Modern Load Balancing: Service Mesh

In Kubernetes environments, sidecar proxies (Envoy in Istio) handle load balancing at the pod level:

  • Every pod gets a sidecar proxy that intercepts all network traffic
  • Proxy performs client-side load balancing with circuit breaking, retries, timeouts
  • Control plane (Istiod) pushes routing configuration to all sidecars
  • No dedicated LB hardware needed—load balancing is distributed

3.7 Connection Draining

When removing a backend from rotation (for deployment or health failure):

  1. Stop sending NEW connections to the backend
  2. Allow EXISTING connections to complete (with a timeout, e.g., 30s)
  3. After timeout or all connections close, fully remove backend
  4. This prevents in-flight requests from being dropped

4. Reliability

4.1 Reliability vs Availability

Availability: Is the system up? (Can I reach it?)

Reliability: Does the system produce correct results consistently? (Can I trust it?)

A system can be available but unreliable (returns wrong data). A reliable system is necessarily available (if it works correctly, it must be running).

4.3 Fault Tolerance Techniques

4.3.1 Replication (covered in Scalability)

4.3.2 Checksums and Data Integrity

Data corruption can occur silently (bit rot on disk, network corruption not caught by TCP checksum).

  • ZFS: Checksums every block (256-bit). On read, verifies checksum. If corrupted, automatically repairs from redundant copy.
  • HDFS: Stores CRC32 for every 512 bytes. DataNodes verify on read and periodic background scanning.
  • Application level: Store hash of important data alongside it. Verify on retrieval.

4.3.3 Idempotency

An operation is idempotent if performing it multiple times produces the same result as performing it once. Critical for reliability because retries are inevitable in distributed systems.

// Non-idempotent: Retrying doubles the charge!
POST /payment {amount: 100}

// Idempotent: Client generates unique key. Server deduplicates.
POST /payment {amount: 100, idempotency_key: "uuid-abc-123"}

// Server implementation:
async function processPayment(request) {
    const existing = await db.query(
        'SELECT * FROM payments WHERE idempotency_key = ?',
        [request.idempotency_key]
    );
    if (existing) return existing.result; // Already processed

    const result = await chargeCard(request.amount);
    await db.insert('payments', {
        idempotency_key: request.idempotency_key,
        result: result,
        created_at: now()
    });
    return result;
}

4.3.4 Saga Pattern (Distributed Transactions)

In microservices, traditional ACID transactions across services are impractical. Sagas break a transaction into a sequence of local transactions with compensating actions.

Order Saga: T1: Create Order (pending) T2: Reserve Inventory T3: Process Payment T4: Confirm Order If T3 fails: C2: Release Inventory (compensate T2) C1: Cancel Order (compensate T1) Choreography: Each service emits events, next service reacts Orchestration: Central coordinator directs the saga steps

4.3.5 Write-Ahead Logging (WAL)

Before modifying data, write the intended change to a sequential log. If crash occurs mid-operation, replay the log on recovery.

How PostgreSQL WAL works internally:

  1. Transaction modifies pages in shared buffer cache (memory)
  2. Before any dirty page is written to disk, WAL record is written first
  3. WAL is flushed to disk on commit (fsync)
  4. Background writer lazily writes dirty pages to data files (checkpointing)
  5. On crash recovery: replay WAL from last checkpoint forward

4.4 Chaos Engineering

Proactively inject failures to find weaknesses before they cause outages in production.

  • Netflix Chaos Monkey: Randomly kills production instances. Forces engineers to build services that tolerate instance failure.
  • Chaos Kong: Simulates entire AWS region failure. Tests cross-region failover.
  • Latency Monkey: Injects artificial latency into network calls. Tests timeout and retry logic.
  • Gremlin: Platform for controlled fault injection (CPU stress, disk fill, network partition, DNS failure).

4.5 Retry Strategies

// Exponential Backoff with Jitter
function retryWithBackoff(fn, maxRetries = 5) {
    for (let attempt = 0; attempt < maxRetries; attempt++) {
        try {
            return await fn();
        } catch (error) {
            if (!isRetryable(error) || attempt === maxRetries - 1) throw error;

            // Exponential backoff: 1s, 2s, 4s, 8s, 16s
            const baseDelay = Math.pow(2, attempt) * 1000;

            // Full jitter: randomize between 0 and baseDelay
            // Prevents thundering herd (all clients retrying simultaneously)
            const jitter = Math.random() * baseDelay;

            await sleep(jitter);
        }
    }
}

// Decorrelated jitter (AWS recommendation - better spread)
function decorrelatedJitter(baseMs, maxMs, attempt, prevDelay) {
    return Math.min(maxMs, random(baseMs, prevDelay * 3));
}

4.6 Bulkhead Pattern

Isolate components so that failure in one doesn't cascade to others. Named after ship bulkheads that prevent a single hull breach from sinking the ship.

  • Thread pool bulkhead: Each downstream service gets its own thread pool. If Service A is slow, only its thread pool saturates; Service B's threads remain available.
  • Semaphore bulkhead: Limit concurrent calls to each dependency. Lighter than thread pools but doesn't protect against slow calls blocking threads.
  • Process/container isolation: Run different services in separate containers with resource limits (cgroups). CPU/memory exhaustion in one container doesn't affect others.

RPO (Recovery Point Objective): Maximum acceptable data loss measured in time. RPO of 1 hour means you can lose up to 1 hour of data.

RTO (Recovery Time Objective): Maximum acceptable downtime. RTO of 15 minutes means system must recover within 15 minutes.

5. Proxy Servers

5.1 Forward Proxy

Sits between clients and the internet. Client is aware of the proxy and configures its browser/OS to use it.

How Forward Proxy Works Internally:

HTTP Proxy (non-HTTPS): 1. Client sends full URL in request: GET http://example.com/page HTTP/1.1 2. Proxy resolves example.com, connects to origin 3. Proxy forwards request (may modify headers) 4. Origin responds to proxy 5. Proxy forwards response to client (may cache it) HTTPS Proxy (CONNECT tunnel): 1. Client sends: CONNECT example.com:443 HTTP/1.1 2. Proxy establishes TCP connection to example.com:443 3. Proxy responds: HTTP/1.1 200 Connection Established 4. Client performs TLS handshake through the tunnel 5. Proxy blindly relays encrypted bytes (cannot inspect) 6. Proxy only sees the destination hostname, not URL paths or content

Use Cases:

  • Corporate filtering: Block access to certain websites
  • Caching: Cache frequently accessed content (Squid proxy)
  • Anonymity: Hide client IP from origin server
  • Access control: Authenticate users before allowing internet access

5.2 Reverse Proxy

Sits between the internet and backend servers. Client is unaware of the proxy—thinks it's communicating directly with the origin server.

How Reverse Proxy Works Internally:

  1. Client resolves www.example.com → gets reverse proxy's IP
  2. Client sends request to proxy (thinks it's the actual server)
  3. Proxy terminates TLS connection (has the SSL certificate)
  4. Proxy inspects request, applies rules (rate limiting, WAF, routing)
  5. Proxy selects backend and forwards request (possibly over plain HTTP internally)
  6. Backend responds. Proxy may modify response (add headers, compress, cache)
  7. Proxy sends response to client

Key Capabilities:

  • SSL/TLS Termination: Proxy handles expensive TLS handshakes (RSA/ECDHE key exchange). Backend communication is plain HTTP (within trusted network). Offloads CPU from application servers.
  • Compression: gzip/brotli compression of responses. Single configuration point rather than per-backend.
  • Caching: Cache static assets and API responses. Serves cached content without hitting backends.
  • Request buffering: Proxy reads the full request from slow clients before forwarding to backend. Backend connection is brief, freeing worker threads quickly (slow-loris protection).

5.3 NGINX Internals as a Reverse Proxy

NGINX uses an event-driven, non-blocking architecture:

  • Master process: Reads config, manages worker processes
  • Worker processes: Handle connections. Each worker runs a single-threaded event loop (epoll on Linux, kqueue on BSD)
  • One worker can handle thousands of connections because it never blocks on I/O. Uses kernel's event notification to know when sockets are readable/writable.
// NGINX event loop (conceptual)
while (true) {
    events = epoll_wait(epfd, timeout);  // Block until events or timeout
    for (event in events) {
        if (event.type == READ_READY) {
            read_from_client(event.fd);      // Non-blocking read
            if (request_complete) {
                connect_to_backend();         // Non-blocking connect
            }
        }
        if (event.type == WRITE_READY) {
            write_to_client(event.fd);       // Non-blocking write
        }
        if (event.type == BACKEND_RESPONSE) {
            buffer_response(event.fd);
            schedule_write_to_client();
        }
    }
}

5.4 Transparent Proxy

Intercepts traffic without client configuration. Network router redirects traffic (using iptables REDIRECT or TPROXY) to the proxy.

# Linux iptables - redirect all outbound HTTP to transparent proxy on port 3128
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 -j REDIRECT --to-port 3128

# TPROXY (preserves original destination IP in socket)
iptables -t mangle -A PREROUTING -p tcp --dport 80 -j TPROXY \
    --tproxy-mark 0x1/0x1 --on-port 3128

5.6 CDN as a Distributed Reverse Proxy

CDNs (Cloudflare, CloudFront, Akamai) are globally distributed reverse proxy networks:

  • Anycast routing: Same IP address is announced from hundreds of PoPs (Points of Presence). BGP routing sends clients to nearest PoP.
  • Edge caching: Each PoP caches content. Cache-Control headers determine TTL.
  • Cache hierarchy: Edge → Regional tier → Origin shield → Origin server. Reduces origin load dramatically.
  • Cache invalidation: Purge by URL, tag, or prefix. Propagates to all PoPs (typically <1 second for modern CDNs).

5.7 API Gateway as a Specialized Reverse Proxy

API gateways (Kong, AWS API Gateway, Apigee) add application-aware functionality:

  • Authentication/Authorization (JWT validation, OAuth token introspection)
  • Rate limiting (token bucket, sliding window per API key)
  • Request/response transformation (header injection, body mapping)
  • API versioning and routing
  • Request aggregation (fan-out to multiple services, aggregate responses)

6.3.2 DNS over HTTPS (DoH) and DNS over TLS (DoT)

  • DoT: Wraps DNS in TLS on port 853. Simple but easy to block (distinct port).
  • DoH: DNS queries sent as HTTPS POST/GET to a URL (e.g., https://dns.google/dns-query). Indistinguishable from normal HTTPS traffic. Uses wire format in body or JSON API.

6.4 DNS Caching and TTL Mechanics

TTL (Time To Live):

  • Set by the authoritative server on each record
  • Recursive resolvers decrement TTL as they cache
  • When TTL hits 0, record must be re-fetched from authoritative server
  • Low TTL (60s): Enables fast failover (change IP, propagates in 60s). More DNS queries to authoritative servers.
  • High TTL (86400s): Reduces DNS traffic. Slower failover. Good for stable records.
TTL Gotcha: Many clients don't respect TTL. Java (by default) caches DNS forever. Some ISP resolvers enforce minimum TTL of 300s. Browser minimum TTL varies (Chrome enforces 60s minimum). Plan migrations assuming some clients will have stale records for hours.

6.5 DNS for System Design - Load Distribution

6.5.1 Round-Robin DNS

Return multiple A records. Clients typically use the first one, but rotate the order:

; Multiple A records - DNS server rotates order each query
example.com.  300  IN  A  10.0.0.1
example.com.  300  IN  A  10.0.0.2
example.com.  300  IN  A  10.0.0.3

; Query 1 response: 10.0.0.1, 10.0.0.2, 10.0.0.3
; Query 2 response: 10.0.0.2, 10.0.0.3, 10.0.0.1
; Query 3 response: 10.0.0.3, 10.0.0.1, 10.0.0.2

Problems: No health checking (returns dead servers). No awareness of server load. Caching means uneven distribution. No session affinity.

6.5.2 Weighted DNS

Return records with different probabilities. AWS Route 53 example: weight 70 to US-East, weight 30 to US-West. The resolver returns one IP per query based on weight ratio.

6.5.3 Latency-Based Routing

DNS provider measures latency from resolver's location to each datacenter. Returns the IP of the lowest-latency datacenter. AWS Route 53 uses latency measurements between AWS regions and the resolver's IP.

6.5.4 GeoDNS

Determines client's approximate location from the resolver's IP (or EDNS Client Subnet extension which sends client's /24 prefix). Returns the geographically closest server IP.

6.6 DNSSEC - Security Extension

DNS responses are unsigned by default—vulnerable to spoofing (Kaminsky attack). DNSSEC adds cryptographic signatures:

  1. Zone signing: Zone owner signs each record set with private key (RRSIG record)
  2. Chain of trust: Parent zone signs child's public key (DS record in parent). Root zone is the trust anchor.
  3. Validation: Recursive resolver verifies signature chain from root down to the queried record
; DNSSEC records
example.com.  DNSKEY  256 3 13 (base64-public-key...)  ; Zone Signing Key
example.com.  DNSKEY  257 3 13 (base64-public-key...)  ; Key Signing Key
example.com.  RRSIG   A 13 2 300 (signature-over-A-records...)
example.com.  DS      12345 13 2 (hash-of-child-DNSKEY...)  ; in .com zone

6.8 DNS Failover Timing

Real-world DNS failover scenario:

1. Primary server at 10.0.0.1 goes down at T=0
2. Health checker detects failure at T=30s (check interval)
3. DNS updated to point to 10.0.0.2 at T=35s
4. Clients with cached record (TTL=60s) still hit 10.0.0.1 until their cache expires
5. Full propagation: T=35s + max(TTL remaining) ≈ T=95s worst case

Lesson: Before planned migrations, reduce TTL days in advance. Go from 3600 → 60, wait 3600s for old TTL to expire from all caches, then perform the migration.

6.9 DNS Amplification Attack

DNS is a common DDoS amplification vector because:

  • Small query (60 bytes) can produce large response (3000+ bytes) → 50x amplification
  • UDP allows source IP spoofing (attacker sends query with victim's IP as source)
  • Open resolvers forward amplified response to victim
  • Mitigation: Response Rate Limiting (RRL) on authoritative servers, BCP38 (ingress filtering), closing open resolvers

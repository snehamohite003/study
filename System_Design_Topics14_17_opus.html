14. Throughput and Latency

14.1 Definitions – Precise Technical Meaning

TermDefinitionUnitAnalogy
LatencyTime between initiating a request and receiving the complete responseMilliseconds (ms), microseconds (μs)How long one car takes to travel from A to B
ThroughputNumber of operations/requests completed per unit of timeRequests/sec, transactions/sec, bytes/secHow many cars pass a checkpoint per hour
BandwidthMaximum theoretical throughput of a channelbits/sec, bytes/secNumber of lanes on the highway
Key Insight: Latency and throughput are NOT inversely proportional by default. You can have:
  • Low latency + high throughput (ideal: fast responses, many of them)
  • Low latency + low throughput (single-threaded fast server with one connection)
  • High latency + high throughput (batch processing: slow per item but massive parallelism)
  • High latency + low throughput (overloaded system: slow AND few completions)
They become coupled under load: as throughput approaches system capacity, latency increases exponentially (queueing theory).

14.2 Latency – Where Time Goes

14.2.1 Anatomy of a Web Request Latency

14.2.3 Percentile Latency (P50, P95, P99, P99.9)

// Why averages lie about latency:
//
// 1000 requests: 990 take 10ms, 10 take 5000ms
// Average: (990×10 + 10×5000) / 1000 = 59.9ms
// But 99% of users saw 10ms! Average is misleading.
//
// Percentiles give the REAL picture:
// P50 (median):  10ms   ← Half of requests are faster than this
// P90:           10ms   ← 90% of requests are faster
// P95:           10ms   ← 95% of requests are faster  
// P99:         5000ms   ← 99% faster. 1% experience 5 SECONDS!
// P99.9:       5000ms   ← The "tail" that ruins user experience

// Why tail latency matters at scale:
// If a page makes 50 parallel API calls:
//   P(all 50 complete within P99) = (0.99)^50 = 60.5%
//   40% of page loads will experience at least one slow call!
//
// If page makes 100 calls:
//   P(all within P99) = (0.99)^100 = 36.6%
//   63% of users hit a tail latency event!
//
// This is why Jeff Dean (Google) says: "at scale, the tail wags the dog"

// Measuring percentiles (implementation):
// Method 1: Keep all values in sorted array (memory-expensive)
// Method 2: t-digest or HDR Histogram (approximate, memory-efficient)
//   t-digest: Merges small clusters of values. Accurate at extremes.
//   HDR Histogram: Fixed-size array with logarithmic bucketing.
//   Both support: addValue(x), getPercentile(p) with < 1% error

14.2.4 Latency Optimization Techniques

// 1. CACHING: Avoid slow operations entirely
//    DB query (5ms) → Redis cache (0.1ms) = 50x improvement
//    CDN edge (5ms) vs origin (100ms) = 20x improvement

// 2. PARALLELIZATION: Do independent work concurrently
//    Sequential: A(50ms) + B(30ms) + C(40ms) = 120ms
//    Parallel:   max(A, B, C) = 50ms

async function getPageData(userId) {
    // BAD: Sequential (120ms)
    const profile = await getProfile(userId);    // 50ms
    const orders = await getOrders(userId);      // 30ms
    const recs = await getRecommendations(userId); // 40ms

    // GOOD: Parallel (50ms)
    const [profile, orders, recs] = await Promise.all([
        getProfile(userId),
        getOrders(userId),
        getRecommendations(userId)
    ]);
}

// 3. PREFETCHING: Load data before it's needed
//    User on page 1 → prefetch page 2 data in background
//    DNS prefetch: <link rel="dns-prefetch" href="//api.example.com">
//    TCP preconnect: <link rel="preconnect" href="//cdn.example.com">

// 4. GEOGRAPHIC PROXIMITY: Move computation closer to user
//    Edge computing, CDN, regional deployments

// 5. CONNECTION POOLING: Eliminate per-request connection setup
//    TCP+TLS handshake: 2 RTT saved per request
//    Database connection: Avoid 5-20ms connection setup per query

// 6. BATCHING: Amortize round-trip cost
//    10 Redis GETs: 10 × 0.5ms = 5ms (pipelined: 0.5ms total!)
//    Redis pipeline: send all commands at once, receive all responses at once

// 7. ASYNC/NON-BLOCKING: Don't wait for non-critical work
//    Send email: Queue it (1ms) vs send inline (500ms)
//    Write audit log: Async fire-and-forget

14.3 Throughput – Maximizing Work Done

14.3.1 Little's Law (Fundamental Relationship)

Little's Law: L = λ × W
  • L = Average number of items in system (concurrency)
  • λ (lambda) = Average arrival rate (throughput)
  • W = Average time in system (latency)
Rearranged: Throughput = Concurrency / Latency

Example: Server handles requests with 20ms average latency, using 100 concurrent threads:
Throughput = 100 / 0.020s = 5,000 requests/second

To increase throughput: Increase concurrency (more threads/connections) OR decrease latency.

14.3.2 Throughput Bottlenecks

// A system's throughput is limited by its SLOWEST bottleneck:

// Example pipeline:
// Load Balancer (50,000 rps) → App Server (2,000 rps) → Database (500 rps)
// System throughput = 500 rps (limited by DB!)

// Identifying bottlenecks:
// 1. CPU-bound: All cores at 100%. Throughput limited by compute.
//    Solution: Optimize algorithm, cache computation results, add cores/servers.
//
// 2. Memory-bound: GC pauses, swapping, cache thrashing.
//    Solution: Reduce allocations, use object pools, increase RAM.
//
// 3. I/O-bound (disk): Waiting for disk reads/writes.
//    Solution: SSD (NVMe), caching (keep hot data in RAM), async I/O.
//
// 4. I/O-bound (network): Waiting for network responses.
//    Solution: Connection pooling, batching, async calls, reduce payload size.
//
// 5. Lock contention: Threads waiting for shared locks.
//    Solution: Lock-free data structures, sharding, reduce critical sections.
//
// 6. External dependency: Downstream service is slow.
//    Solution: Caching, circuit breaker, async processing, timeouts.

// Back-of-envelope throughput calculation:
// Single thread, synchronous processing, 20ms per request:
//   Throughput = 1000ms / 20ms = 50 rps per thread
//   With 20 threads: 50 × 20 = 1,000 rps
//   With 10 servers × 20 threads: 10,000 rps
//
// Async event loop (Node.js/Go), 20ms per request (mostly I/O wait):
//   Can handle thousands of concurrent requests on single thread
//   Because while one request waits for DB, others are processing
//   Throughput = limited by event loop CPU for non-I/O work

14.3.3 Amdahl's Law (Limits of Parallelism)

// Speedup = 1 / (S + (1-S)/N)
// S = fraction of work that is SERIAL (cannot be parallelized)
// N = number of parallel processors
//
// If 5% of work is serial (S=0.05):
//   N=2:    Speedup = 1 / (0.05 + 0.95/2) = 1.90x
//   N=4:    Speedup = 1 / (0.05 + 0.95/4) = 3.48x
//   N=10:   Speedup = 1 / (0.05 + 0.95/10) = 6.90x
//   N=100:  Speedup = 1 / (0.05 + 0.95/100) = 16.8x
//   N=1000: Speedup = 1 / (0.05 + 0.95/1000) = 19.6x
//   N=∞:    Speedup = 1 / 0.05 = 20x  (MAXIMUM POSSIBLE!)
//
// Lesson: Even with infinite parallelism, 5% serial work limits you to 20x speedup.
// In practice: shared locks, sequential I/O, coordination overhead = serial fraction.
// System design implication: Eliminate serial bottlenecks before adding more servers.

14.4 The Throughput-Latency Relationship Under Load

Latency vs Throughput (Queueing Theory): Latency │ (ms) │ │ ╱ 500 │ ╱ ← System saturated │ ╱ (requests queue up) 200 │ ╱ │ ╱ 100 │ ╱╱ │ ╱╱╱ 50 │ ╱╱╱╱ │ ╱╱╱╱╱ 20 │╱╱╱╱ ← Linear region (ample capacity) │ 10 │── Baseline latency (no queueing) │ └───────────────────────────────────────── Throughput (rps) 0% 20% 40% 60% 80% 100% ← % of max capacity Key insight: Latency stays flat until ~60-70% utilization, then increases EXPONENTIALLY as you approach 100% capacity. M/M/1 Queue Model: Average latency = service_time / (1 - utilization) At 50% util: latency = 2× baseline At 80% util: latency = 5× baseline At 90% util: latency = 10× baseline At 99% util: latency = 100× baseline! Design implication: NEVER run systems above 70-80% capacity. Always have headroom for bursts. Auto-scale BEFORE saturation.

15. Observability

15.1 What Observability Means

Observability is the ability to understand the internal state of a system by examining its external outputs. It answers: "Why is the system behaving this way?" — not just "Is it up?"

Monitoring vs Observability: Monitoring (known-unknowns): Observability (unknown-unknowns): "Alert me when CPU > 90%" "Why are 2% of users seeing 5s latency?" "Is the database up?" "Which specific queries are slow, for which users, "How many 500 errors?" triggered by which upstream event?" Monitoring tells you WHAT is broken. Observability tells you WHY it's broken (and helps you find things you didn't know to look for).

15.2 The Three Pillars of Observability

15.2.1 Pillar 1: Metrics (Aggregated Numerical Data)

Metrics are numerical values measured over time. They tell you what is happening at an aggregate level.

// How tracing works internally (OpenTelemetry):

// 1. Context Propagation: Trace ID travels with the request
//    HTTP headers carry trace context between services:
//    traceparent: 00-abc123def456-span789-01
//    Format: version-trace_id-parent_span_id-flags

// 2. Each service creates a "span" for its work:
const tracer = opentelemetry.trace.getTracer('user-service');

async function getUser(userId) {
    // Start a new span (child of incoming span from header)
    return tracer.startActiveSpan('getUser', async (span) => {
        span.setAttribute('user.id', userId);

        // Child span for database query
        return tracer.startActiveSpan('postgres.query', async (dbSpan) => {
            dbSpan.setAttribute('db.system', 'postgresql');
            dbSpan.setAttribute('db.statement', 'SELECT * FROM users WHERE id = $1');
            
            const result = await db.query('SELECT * FROM users WHERE id = $1', [userId]);
            
            dbSpan.setAttribute('db.rows_returned', result.rows.length);
            dbSpan.end();  // Record duration
            
            span.end();
            return result.rows[0];
        });
    });
}

// 3. Spans are exported to tracing backend:
//    Service → OpenTelemetry Collector → Jaeger/Tempo/Zipkin/Datadog
//    Each span: {trace_id, span_id, parent_span_id, operation, start, duration, tags}

// 4. Backend assembles spans into complete trace tree for visualization

Sampling Strategies (you can't trace everything at scale):

// At 100K requests/sec, tracing EVERY request generates enormous data volume.
// Solution: Sampling

// 1. Head-based sampling: Decide at entry point whether to trace
//    Pros: Simple. Consistent (whole trace or nothing).
//    Cons: May miss interesting (rare error) traces.
sampler: probabilistic(0.01)  // Trace 1% of requests

// 2. Tail-based sampling: Collect ALL spans, decide AFTER completion
//    Pros: Keeps all interesting traces (errors, slow requests).
//    Cons: Must buffer all spans temporarily. Higher infrastructure cost.
rules:
  - always_sample_if: status_code >= 500           // All errors
  - always_sample_if: duration > 2000ms            // All slow requests  
  - always_sample_if: http.path == "/api/payment"  // All payment flows
  - probabilistic: 0.001                           // 0.1% of everything else

// 3. Adaptive sampling: Dynamically adjust rate based on traffic
//    High traffic → lower sample rate. Low traffic → higher rate.
//    Target: ~100 traces/second per service (manageable volume).

15.4 Alerting – Turning Observability into Action

// Good alerting principles:
// 1. Alert on SYMPTOMS, not causes
//    BAD:  Alert when CPU > 90% (cause — might be fine under heavy load)
//    GOOD: Alert when P99 latency > 500ms (symptom — users are affected)

// 2. Alert on SLO burn rate (modern best practice)
//    SLO: 99.9% of requests complete in < 300ms over 30 days
//    Error budget: 0.1% of requests can be slow = 43 minutes/month
//
//    If errors in last 5 minutes would exhaust monthly budget in 1 hour → PAGE
//    If errors in last 30 minutes would exhaust budget in 6 hours → TICKET

// Multi-window burn rate alert (Google SRE):
// 
// Long window (1h): burn_rate = error_rate_1h / (1 - slo_target)
// Short window (5m): confirms it's ongoing (not a brief blip)
//
// Example PromQL:
//   (1 - (rate(http_requests_success_total[1h]) / rate(http_requests_total[1h])))
//   / (1 - 0.999) > 14.4
//   AND
//   (1 - (rate(http_requests_success_total[5m]) / rate(http_requests_total[5m])))
//   / (1 - 0.999) > 14.4
//
// 14.4 burn rate = budget consumed in 1 hour. High severity → page immediately.

// 3. Minimize alert fatigue
//    Every alert should be: ACTIONABLE (human can do something)
//    Route properly: Critical → PagerDuty. Warning → Slack. Info → Dashboard.

16. Consensus Algorithms

16.1 The Problem: Agreement in Distributed Systems

In a distributed system, multiple nodes must agree on a single value or sequence of operations despite network delays, partitions, and node crashes. This is the consensus problem.

Why consensus is hard: Node A: "The leader is Node A" Node B: "The leader is Node B" ← SPLIT BRAIN! Both accept writes → data divergence! Node C: (crashed, unreachable) Network partition: ┌─────────┐ ┌─────────┐ │ Node A │ ╳ │ Node B │ ← Network broken between them │ Node C │ │ Node D │ └─────────┘ └─────────┘ Both sides think the other is dead. Without consensus protocol → both sides elect a leader → catastrophe. Requirements for correct consensus: 1. Agreement: All non-faulty nodes decide on the same value 2. Validity: The decided value was proposed by some node 3. Termination: All non-faulty nodes eventually decide 4. Integrity: Each node decides at most once

16.2 Raft – The Understandable Consensus Algorithm

Raft is designed to be understandable (unlike Paxos). Used in: etcd, CockroachDB, TiKV, Consul, RethinkDB.

16.2.1 Raft Roles

RoleResponsibilityBehavior
LeaderHandles all client requests. Replicates log to followers.Sends AppendEntries RPCs (heartbeats + log replication). Only one leader per term.
FollowerPassive. Responds to leader and candidates.If no heartbeat received within election timeout → becomes Candidate.
CandidateRequests votes to become leader.Increments term, votes for self, sends RequestVote RPCs to all nodes.

16.2.2 Leader Election – Step by Step

Initial state: All nodes are Followers with no leader. Node A Node B Node C Node D Node E (Follower) (Follower) (Follower) (Follower) (Follower) Election timeout fires on Node C first (randomized: 150-300ms): Node C transitions to CANDIDATE, increments term to 1. Node C → all: RequestVote(term=1, candidateId=C, lastLogIndex=0, lastLogTerm=0) Node A: "My term is 0 < 1. I haven't voted in term 1. C's log is up-to-date." → Grants vote to C. Updates own term to 1. Node B: → Grants vote to C. Node D: → Grants vote to C. Node E: → Grants vote to C. Node C receives 4 votes (majority of 5 = 3 needed) → BECOMES LEADER (term 1)! Node C → all: AppendEntries(term=1, entries=[], leaderCommit=0) // Heartbeat All nodes: Acknowledge C as leader. Reset election timers. Key rules: • Each node votes for AT MOST ONE candidate per term (prevents split votes) • Candidate must have log at least as up-to-date as voter (safety guarantee) • Randomized election timeout prevents simultaneous candidates (usually)

16.2.3 Log Replication – How Writes Are Committed

// Client sends write request to Leader:

// Step 1: Leader appends entry to its local log (uncommitted)
leader.log.append({
    term: 1,
    index: 5,
    command: "SET x = 42"
});

// Step 2: Leader sends AppendEntries to ALL followers
// AppendEntries RPC:
{
    term: 1,                    // Leader's current term
    leaderId: "C",
    prevLogIndex: 4,            // Index of entry immediately before new entry
    prevLogTerm: 1,             // Term of prevLogIndex entry
    entries: [{term: 1, index: 5, command: "SET x = 42"}],
    leaderCommit: 4             // Leader's commit index
}

// Step 3: Followers receive, validate, append to their log
// Follower checks: Does my log entry at index 4 have term 1? (consistency check)
// If yes → append new entry, respond success
// If no → respond failure (leader will decrement prevLogIndex and retry)

// Step 4: Leader counts successful responses
// Once MAJORITY (3 of 5) have the entry → entry is COMMITTED
leader.commitIndex = 5;

// Step 5: Leader applies committed entry to state machine
stateMachine.apply("SET x = 42");

// Step 6: Leader responds to client: "Write successful"

// Step 7: Next AppendEntries to followers includes updated leaderCommit=5
// Followers learn entry 5 is committed → apply to their state machines

// IMPORTANT: Entry is durable once committed (majority have it on disk).
// Even if leader crashes, new leader will have this entry (election safety).

16.2.4 Safety Guarantees

// Raft guarantees these properties:

// 1. Election Safety: At most one leader per term.
//    Proof: Each node votes once per term. Leader needs majority.
//    Two leaders would need 2 × majority = more nodes than exist. Impossible.

// 2. Leader Append-Only: Leader never overwrites or deletes log entries.
//    It only appends new entries.

// 3. Log Matching: If two logs contain an entry with same index and term,

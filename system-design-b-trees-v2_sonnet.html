The Storage Hierarchy Problem

Why the gap between RAM and disk forces a fundamentally different index structure

Disk I/O ModelFan-out Block TransferRandom vs Sequential Access BST Inadequacy

The Latency Asymmetry Driving B-Tree Design

The entire rationale for B-Trees stems from a single engineering reality: the latency gap between DRAM and persistent storage is not linear — it is four to six orders of magnitude. A main-memory access completes in ~80 nanoseconds. A random read from a 7200 RPM HDD incurs ~10 milliseconds of combined seek time and rotational latency. Even modern NVMe SSDs require ~100 microseconds per random access. This disparity fundamentally shapes every design decision in a B-Tree.

Why Binary Search Trees Fail for Disk-Based Storage

A Binary Search Tree (BST) has exactly one key per node and exactly two child pointers. When a BST is stored on disk, each node occupies a negligible fraction of a storage page (~24 bytes out of 4096 bytes). Every pointer traversal from parent to child is a separate random disk I/O, since the parent and child nodes reside on different, unrelated physical pages.

For a balanced BST over n = 1 billion records, the tree height is ⌈log₂(10⁹)⌉ = 30. Each lookup therefore requires 30 random disk I/Os. At 10ms per HDD seek, this is 300ms per query — completely unacceptable for any real-time system. Furthermore, each 4KB page read retrieves only 24 bytes of useful data; the remaining 4072 bytes are wasted.

The BST's fundamental inadequacy is its low fan-out: 2 children per node. Fan-out is the single most important property governing tree height and therefore I/O cost. B-Trees solve this by filling entire storage pages with keys and child pointers, achieving fan-out of hundreds to thousands.

📐 The Fan-out Principle — Core of B-Tree Design Every B-Tree design decision — page size, key compression, pointer encoding — exists to maximize fan-out. Higher fan-out reduces tree height by one level for every order-of-magnitude increase in table size. With fan-out ≈ 1000, a table can grow from 1 thousand to 1 billion rows while adding only two levels of height. This is why B-Trees exhibit near-constant lookup performance regardless of table size in practical workloads.

Structural Anatomy

The Order Parameter — Minimum Degree t

A B-Tree of minimum degree t (equivalently, order 2t) defines the permitted key count bounds for every node. The parameter t is chosen at tree creation time based on the storage page size, key size, and pointer size — it is a static property of a given index structure. All operational invariants derive directly from t:

🔒 B-Tree Invariants — Maintained at All Times by All Operations
  • Key lower bound (non-root nodes): Every node except the root must hold at least t − 1 keys. This prevents nodes from becoming too sparse, ensuring minimum fan-out and bounded tree height.
  • Key upper bound (all nodes): Every node holds at most 2t − 1 keys. When a node reaches this maximum, it is considered full and must be split before any further insertion.
  • Root exception: The root node may hold as few as 1 key (when the tree has at least 2 nodes) or 0 keys (empty tree). It still obeys the 2t−1 upper bound.
  • Child count: An internal node holding k keys has exactly k + 1 children. The relationship between key count and child count is always exact — no slack permitted.
  • Separator key semantics: For an internal node with keys [k₁, k₂, ..., kₙ] and children [c₀, c₁, ..., cₙ], every key in subtree cᵢ is strictly greater than kᵢ and strictly less than kᵢ₊₁. The separator keys partition the key space into disjoint ranges, one per child pointer.
  • Uniform leaf depth: Every leaf node resides at the same depth. This is the property that guarantees O(log n) worst-case performance for all operations — no path from root to leaf is shorter or longer than any other.
  • Intra-node key ordering: Keys within every node are stored in strictly non-decreasing order, enabling binary search within each node during traversal.

Why Uniform Leaf Depth Is Guaranteed

The B-Tree is the only common tree structure where balance is a structural invariant maintained by the insertion and deletion algorithms themselves, not an after-the-fact rebalancing operation. Height increases only when the root is split — a single, infrequent event that adds exactly one level uniformly across the entire tree. Height decreases only when the root is merged away — equally uniform. At no point can any leaf be at a different depth than any other leaf. This is in stark contrast to AVL or Red-Black trees, which rebalance after insertion via rotations that can leave paths with different depths temporarily.

Deriving the Order Parameter from Hardware

The relationship between the order parameter and physical storage is direct and deterministic. Given a page size P bytes, a key of size K bytes, and a child pointer of size PTR bytes, the maximum number of keys per internal node is ⌊(P − header_overhead) / (K + PTR)⌋. The minimum degree t is then set to ⌊(max_keys + 2) / 2⌋. This calculation ensures that two half-full siblings can always be merged into a single full node — a property required for the deletion algorithm's merge case to be valid.

B+Tree — The Database Standard

How B+Tree diverges from the original B-Tree, leaf-level sibling links, and index locality

Leaf Sibling LinksKey Duplication Internal-Only KeysClustered Index Secondary IndexIndex-Only Scan Double-Dip Problem

The Structural Modification that Defines B+Tree

The original B-Tree (Bayer & McCreight, 1970) stores data records at every level — internal nodes carry both separator keys and associated data, while leaves carry only the lowest-level records. This has two drawbacks: internal nodes become larger (reducing fan-out), and range scans require back-and-forth traversal between levels as the scan crosses internal node boundaries.

The B+Tree modification enforces a strict rule: all data records reside exclusively in leaf nodes. Internal nodes carry only separator keys and child pointers — they are navigation-only structures with no associated data payload. Keys at the internal level are copies of leaf-level keys, promoting upward during splits. The result is maximally high fan-out at internal nodes (no data payload consuming space) and a contiguous, ordered dataset at the leaf level.

The Leaf-Level Doubly Linked List

Every leaf node in a B+Tree carries two additional pointer fields: a right-sibling pointer to the next leaf page (by key order) and a left-sibling pointer to the previous leaf page. Together, these form a doubly linked list across the entire leaf level. This structure is the enabling mechanism for efficient range scans: once the lower bound of a range query has been located via tree traversal, the scan continues horizontally through the leaf chain — entirely sequential reads — without any further interaction with internal nodes. The scan terminates when the upper bound key is exceeded or the right-sibling pointer is null.

Clustered vs Non-Clustered Index — Two B+Tree Variants

Clustered Index (InnoDB Primary Key, SQL Server)

In a clustered index, the leaf nodes of the B+Tree are the table — they contain the full row data for every record. The table has no separate heap storage; the B+Tree is the physical storage structure. Rows are physically ordered on disk in primary key sequence. Range scans on the primary key are therefore sequential disk reads, which is the fastest possible I/O pattern. Each table may have exactly one clustered index.

The primary key selection is critical: monotonically increasing keys (BIGSERIAL, UUID v7, ULID) always append new rows to the rightmost leaf, generating minimal page splits. Randomly distributed keys (UUID v4) scatter insertions across the entire tree, causing frequent splits at arbitrary positions and chronic index fragmentation.

Non-Clustered (Secondary) Index

A secondary index leaf stores the indexed column value alongside a pointer back to the actual row. In InnoDB, this pointer is the primary key value (triggering a second clustered index traversal — the "double-dip" problem). In PostgreSQL, this pointer is a physical ctid (block number + tuple offset within the heap file).

The double-dip problem: a secondary index lookup on a range of keys requiring N rows from the heap performs N random heap page accesses after the index traversal. For large result sets, this random I/O pattern can be slower than a sequential full table scan. PostgreSQL's Bitmap Index Scan mitigates this by collecting all matching ctids from the index, sorting them by physical block number, then fetching heap pages in sequential order — trading latency for reduced random I/O amplification.

Covering Index and Index-Only Scan

When the projected columns of a query are entirely contained within the index — either as key columns or as INCLUDE payload columns stored in the leaf — the database engine can satisfy the query entirely from the index without accessing the heap. This index-only scan eliminates the second I/O hop entirely. In PostgreSQL, the visibility map must confirm that all referenced heap pages are "all-visible" before the planner will choose an index-only scan, since the index itself carries no transaction visibility (MVCC) information.

Search Mechanics

Traversal semantics, intra-node binary search, range scan behaviour, and prefix query handling

Point Lookup — Traversal Semantics

A point lookup initiates at the root page, which is always maintained in the buffer pool for hot indexes. At each internal node, the algorithm performs a binary search over the node's sorted key array to identify the correct child pointer. Specifically, it seeks the smallest separator key strictly greater than the search key; the associated child pointer (to the left of that separator) is the subtree guaranteed to contain the search key. This property — called the separator key semantics — is preserved by all split and merge operations.

The traversal descends level by level, issuing exactly one page read per level. Since upper-level pages (root and first one or two internal levels) are accessed by every query, they are effectively always resident in the database buffer pool. For a height-3 tree, only the leaf page typically requires an actual disk I/O. The effective I/O cost in production is therefore often just one disk read, regardless of tree height, for tables where upper levels fit in shared_buffers.

At the leaf level, a second binary search over the leaf's key array locates the exact key position. If found, the associated row pointer (ctid in PostgreSQL, primary key in InnoDB secondary indexes) is returned. If the key falls between two adjacent entries, the lookup reports no match.

Intra-Node Binary Search — Why It Matters

Within each page, the key array is sorted. Binary search over this array costs O(log k) comparisons where k is the number of keys per node. With k ≈ 500 (typical for 8KB pages with 8-byte integer keys), binary search requires at most ⌈log₂(500)⌉ = 9 comparisons per level. Across a height-3 tree, total comparisons ≈ 27. This is dramatically fewer than what a linear scan would require.

For variable-length keys (e.g., VARCHAR), comparisons are more expensive. Some implementations use a prefix comparison optimisation: once a key's leading bytes differ from the search key, the comparison terminates early without reading the full key string. PostgreSQL's abbreviated key mechanism computes a fixed-size sort key (a hash or truncation) that fits in a machine register; full key comparisons are only performed when abbreviated keys collide.

Range Scan — Leaf Chain Traversal

A range scan decomposes into two phases. The first phase is a standard point lookup to locate the leaf page containing the lower bound key — cost O(log_t n) I/Os. The second phase is a sequential horizontal scan along the leaf sibling chain until the upper bound is exceeded. The second phase issues one page read per leaf page traversed — sequential reads that benefit maximally from OS read-ahead prefetching and the storage controller's sequential access optimisation.

The total I/O cost for a range scan returning k records stored across p leaf pages is O(log_t n + p) disk I/Os, where p = ⌈k / fill_factor / keys_per_page⌉. Because adjacent leaf pages in key order tend to be physically adjacent on disk (especially for clustered indexes populated in key order), the sequential read pattern often achieves near-peak storage bandwidth.

Prefix Queries and the Leftmost Prefix Rule

A leading-prefix LIKE query — for example WHERE name LIKE 'Alice%' — is equivalent to a range scan with lower bound Alice and upper bound Alicf (the lower bound with its last character incremented by one Unicode code point). This maps directly to the range scan mechanism above, and can fully exploit any B+Tree index on the name column.

A trailing or interior wildcard — LIKE '%Alice' or LIKE '%Alice%' — cannot be expressed as a contiguous key range. The B+Tree's sorted order provides no benefit; the engine must examine every entry. A GIN index with trigram decomposition (PostgreSQL's pg_trgm extension) is the correct structure for substring searches.

For composite indexes, the leftmost prefix rule governs which query predicates can exploit the index. The index is sorted first by the leading column, then by the second column within equal leading-column values, and so on. A predicate referencing only the second column (without constraining the first) cannot leverage the sorted order at the first level — the search key spans arbitrary positions across all leaf pages. Only predicates that fully constrain all leading columns (with equality) and optionally the last referenced column (with a range condition) can reduce the scan to a contiguous leaf-chain segment.

Insertion Mechanics

The Two-Pass vs One-Pass Strategy

There are two classical approaches to insertion. The two-pass strategy (Knuth's original formulation) descends to the leaf, inserts the key, and then propagates splits upward as needed — requiring two traversals of the tree. The proactive split strategy (CLRS) splits any full node encountered during the downward traversal, before descending further. This ensures that when the leaf is reached, the immediate parent is guaranteed to be non-full and can absorb a promoted median key without further upward propagation. The proactive strategy requires only a single top-down pass and is universally preferred in production implementations.

Split Mechanics — What Happens When a Node Is Full

When a node reaches its maximum capacity of 2t − 1 keys, it is full and must be split before any further key can be accepted. The split procedure divides the node at its median key (index position t − 1 in 0-indexed terms):

  • The left child retains keys at positions 0 through t − 2 (exactly t − 1 keys — the minimum permitted).
  • The right child receives keys at positions t through 2t − 2 (also exactly t − 1 keys).
  • The median key at position t − 1 is promoted upward to the parent node, where it becomes the new separator between the left and right child pointers.

In the B+Tree variant, the behaviour at the leaf level differs slightly from internal node splits: the median key is copied to the parent (not moved), because it must remain in the right leaf to preserve all original data records at the leaf level. At internal node splits, the median key is genuinely moved to the parent, as internal nodes carry no data payload.

After a leaf split, the sibling pointer chain must be updated: the new right leaf's right-sibling pointer is set to the original leaf's former right sibling; the original leaf's right-sibling pointer is updated to point to the new right leaf; and if the new right leaf has a right neighbour, that neighbour's left-sibling pointer must also be updated. This is a chain of three page writes for sibling pointer maintenance alone, independent of the parent pointer update.

Root Split — The Only Mechanism for Height Increase

When the root node is full, it cannot accept a promoted median key from a child split because it has no parent to receive the overflow. The only resolution is a root split: a new empty root page is allocated, the old full root becomes a child of the new root, and then the old root is split using the standard split procedure with the new root as parent. The new root begins with exactly one key (the promoted median) and exactly two children. Tree height increases by exactly one, uniformly across all paths.

This is the only event that increases tree height. Because the height increase is always uniform (root splits affect all paths simultaneously), the leaf-depth invariant is preserved automatically. Root splits are rare events — they occur at most once every O(t^(h-1)) insertions for a tree of height h.

I/O Cost Analysis for Insertion

In the best case (leaf node not full, no splits required): the traversal reads h pages (one per level), then writes 1 modified leaf page. Total I/Os: h reads + 1 write.

In the worst case (every node on the path from root to leaf is full — cascading splits): h reads during traversal, plus h+1 writes (one per split level including a potential root split). Total I/Os: h reads + (h+1) writes = 2h+1 I/Os.

In practice, splits are amortised: each split creates two half-full nodes, and those nodes will not need splitting until approximately t−1 more keys have been inserted into them. The amortised insertion cost across all operations is O(1) splits per insertion, making the average insertion cost O(h) I/Os.

⚠️ Sequential vs Random Insertion Patterns Sequential primary key insertion (auto-increment integers) always targets the rightmost leaf, producing a rightmost-path split pattern where internal nodes fill up from left to right in a predictable, amortised fashion. Random key insertion (e.g., UUID v4 as primary key) scatters insertions across the entire tree uniformly, causing splits at arbitrary positions throughout the structure. The statistical outcome of random insertion is that the average fill factor stabilises at approximately 69% (ln 2 ≈ 0.693) — every node averages about two-thirds full rather than the theoretical maximum. For write-heavy workloads with random keys, this represents 31% wasted storage and proportionally more pages per lookup.

Underflow — The Core Challenge in Deletion

Deletion is structurally more complex than insertion because removing a key from a node may reduce its key count below the minimum threshold of t − 1. This condition is called underflow. An underflowing node violates the B-Tree invariants and must be resolved before the operation completes. The resolution strategy depends on the occupancy of the underflowing node's immediate siblings.

Three Deletion Cases

Case 1 — Key Resides in a Leaf and No Underflow Occurs

If the target leaf holds more than t − 1 keys (i.e., removing one key still leaves it at or above minimum), the key is deleted in-place by shifting subsequent keys left within the page. No structural change to the tree is necessary. The modified leaf page is written back to disk. This is the common case for well-distributed deletions.

Case 2 — Key Resides in an Internal Node

Internal nodes in B+Trees contain only separator (guide) keys — they do not hold data records. When the separator key being deleted is found in an internal node, the algorithm must replace it with either its in-order predecessor (the rightmost key of the left child's rightmost subtree) or its in-order successor (the leftmost key of the right child's leftmost subtree). The replacement key is then deleted from the appropriate leaf. If the chosen child has strictly more than t − 1 keys, this deletion from the child is safe and does not cause underflow. If both children are at minimum occupancy, they are merged (Case 3) before proceeding.

Case 3 — Deletion Causes Underflow (the Structural Cases)

When a leaf deletion reduces the leaf's key count below t − 1, one of three structural resolutions must be applied, evaluated in order of preference:

Resolution A — Borrow from Left Sibling (Right Rotation)

If the left sibling holds strictly more than t − 1 keys (i.e., it has a spare key), the rightmost key of the left sibling is rotated into the underflowing node via the parent. Specifically: the separator key in the parent that divides the left sibling from the underflowing node descends into the underflowing node's first position; the left sibling's rightmost key ascends to replace that separator in the parent. The parent's separator is updated accordingly. Net result: the left sibling loses one key, the underflowing node gains one key (from the parent, which in turn absorbed one from the left sibling), and no pages are created or destroyed.

Resolution B — Borrow from Right Sibling (Left Rotation)

Symmetric to Resolution A. If the right sibling holds more than t − 1 keys, its leftmost key rotates into the underflowing node via the parent. The parent's separator between the underflowing node and the right sibling is updated to the former second key of the right sibling (which is now the rightmost key of the underflowing node's portion of the key space).

Resolution C — Merge with a Sibling

If both adjacent siblings are at exactly minimum occupancy (exactly t − 1 keys), borrowing is not possible without causing the sibling to underflow. Instead, the underflowing node is merged with one sibling (preferably the left). The merge concatenates the two nodes' key sets and brings down the parent's separator key between them. The result is a single node containing at most (t − 1) + 1 + (t − 1) = 2t − 1 keys — exactly at capacity, a valid full node. The merged node is placed in the left sibling's page slot; the right node's page is freed. One entry is removed from the parent (the separator that came down), which may itself cause underflow at the parent level — propagating the resolution upward.

Cascade to Root — Height Reduction

Merge operations at one level remove a key from the parent. If the parent was at minimum occupancy (t − 1 keys), it now underflows, triggering the same resolution procedure one level up. This cascade can propagate from a leaf all the way to the root. If the root loses its last key due to a merge, the root is removed and its sole remaining child becomes the new root, reducing the tree height by one. This is the only event that reduces tree height, and like root splits, it is exceedingly rare in practice.

Lazy Deletion — The Production Reality

Full deletion with immediate merging is structurally correct but operationally expensive — a cascade merge can require O(h) page writes. In practice, all major production databases implement lazy deletion: the index entry is marked as dead (via a tombstone or by marking the heap tuple's xmax field in PostgreSQL), and the index page is not immediately restructured.

PostgreSQL's VACUUM process periodically traverses index pages and physically removes dead index entries without triggering merges. Pages that fall below minimum occupancy are simply left sparse — the invariant is not enforced during lazy cleanup. REINDEX or REINDEX CONCURRENTLY rebuilds the entire index from scratch with optimal packing. PostgreSQL also implements Heap Only Tuple (HOT) updates: when an UPDATE modifies only non-indexed columns, the new tuple version is placed on the same heap page and chained via a t_ctid pointer, avoiding any index modification entirely. The index entry continues to point to the old tuple's ctid, which the engine follows to find the current version.

Buffer Pool — Caching and Eviction Policy

The database buffer pool (shared_buffers in PostgreSQL, innodb_buffer_pool_size in MySQL) is the primary RAM cache for B-Tree pages. Every page access — read or write — goes through the buffer pool. A modified page becomes dirty and remains in the buffer pool until the background writer or checkpointer flushes it to disk.

PostgreSQL uses a clock-sweep eviction algorithm: each buffer frame carries a usage_count field (0–5). On each buffer access, usage_count is incremented (capped at 5). When a free frame is needed, the clock hand sweeps through all frames; frames with non-zero usage_count are decremented and skipped; the first frame reaching usage_count = 0 is evicted. Frequently accessed pages (root, upper internal levels) are touched by every query and accumulate high usage_count, making them nearly eviction-proof under any realistic workload. Leaf pages, accessed infrequently relative to their count, are evicted on a frequency proportional to their access rate.

The practical consequence: for a height-3 B+Tree on a properly sized buffer pool, the root page and all first-level internal pages are always resident in memory. Effective disk I/O cost per lookup collapses to a single leaf page read, making the theoretical O(log n) cost irrelevant in practice — the dominant cost is one random I/O to the correct leaf page.

Write-Ahead Log (WAL) — Guaranteeing Crash Safety

The WAL protocol mandates that every modification to a B-Tree page is first recorded in the WAL (also called the Redo Log in InnoDB) before the modified page may be written to its permanent location in the data file. This ordering guarantee — WAL before data — ensures that upon crash recovery, the database can replay WAL records to reconstruct any modifications that were in the buffer pool but not yet flushed to disk at crash time.

For B-Tree operations, WAL records are compact delta records: they describe the key inserted, its position in the target page, and any structural changes (split page numbers, promoted median keys, sibling pointer updates). The WAL record for a leaf insert is typically 50–200 bytes — far smaller than the 8KB page itself.

The exception is the Full-Page Image (FPI): the first modification to any page after a checkpoint must include the entire page contents in the WAL record, not just the delta. This guards against partial page writes — a scenario where a crash occurs midway through writing an 8KB page to a storage device that has 512-byte atomic write units, leaving the page in a half-written, unrecoverable state. FPI records are significantly larger (8KB each) and constitute the dominant WAL volume during and immediately following checkpoint cycles. WAL compression (wal_compression = on) applies LZ4 or zstd compression to FPI records, typically achieving 50–80% size reduction.

Checkpointing and Its Interaction with B-Tree I/O

A checkpoint is the process of writing all dirty buffer pool pages to their permanent locations in the data files, then recording a checkpoint record in WAL. After a checkpoint, WAL replay during crash recovery need only start from the checkpoint position rather than the beginning of the WAL. PostgreSQL distributes checkpoint I/O over time using checkpoint_completion_target (default 0.9 = spread writes over 90% of the checkpoint interval) to avoid I/O spikes. The first modification to any page after a checkpoint triggers a full-page image in WAL, increasing WAL write amplification temporarily until all frequently-modified B-Tree pages have been "first-modified" in the new checkpoint cycle.

Latches vs Transaction Locks — A Critical Distinction

🔐 Latches (Physical Concurrency Control)
  • Protect the physical structure of individual B-Tree pages against concurrent access during structural modification
  • Duration: microseconds to low milliseconds — held only while the page is actively read or modified
  • No deadlock detection infrastructure — deadlock prevention enforced by strict top-down latch acquisition ordering
  • Modes: shared (read latch, multiple holders) and exclusive (write latch, single holder)
  • Entirely internal to the storage engine — invisible to transaction managers and MVCC subsystems
  • Implemented as OS mutexes or spinlocks on the buffer descriptor
🔑 Transaction Locks (Logical Concurrency Control)
  • Protect logical data — rows, key ranges, table-level access — against conflicting concurrent transactions
  • Duration: entire transaction lifetime (seconds to minutes)
  • Full deadlock detection via wait-for graph cycle detection
  • Modes: S (shared), X (exclusive), IS, IX, SIX — plus predicate locks for serializable isolation
  • Managed by the lock manager — visible to MVCC, isolation level enforcement, deadlock detector
  • Interact with MVCC snapshot visibility to determine row-level conflict

Lock Coupling (Latch Crabbing) — Safe Concurrent Traversal

The naive approach to concurrent B-Tree access — acquiring an exclusive latch on the root and holding it for the entire traversal — serialises all operations through the root, creating an extreme bottleneck. The lock coupling protocol (also called latch crabbing) solves this by releasing the parent's latch as soon as it is determined that the parent cannot be affected by a structural change in its subtree.

For read operations: shared latches are acquired top-down. The moment a child page's shared latch is acquired, the parent's shared latch is released. At any point in the traversal, only one shared latch is held — on the current node. Multiple concurrent readers can traverse the tree simultaneously without contention.

For write operations (proactive splitting): write latches are acquired top-down and held on all ancestor pages until a safe node is encountered. A safe node is one that will not require splitting (not full, for insertion) or merging (above minimum, for deletion) as a result of the operation in its subtree. Once a safe node is identified, all latches on its ancestors are released. The write latch is held only from the safe node downward. In practice, for uniformly distributed insertions, the first or second level below the root is almost always safe, releasing the root latch within two levels of descent — essentially eliminating root contention in steady-state operation.

Blink-Tree — Enabling Non-Blocking Concurrent Access

Lehman and Yao's 1981 Blink-Tree extends the standard B+Tree with two additions that enable a critical safety property: concurrent reads can tolerate concurrent splits without holding parent latches.

Right-link pointer: every node (not just leaf nodes, as in standard B+Tree) carries a pointer to its right sibling. In the standard B+Tree, only leaf nodes have sibling pointers; internal nodes do not.

High key: every non-rightmost node stores its maximum permissible key — the upper bound of its key range. The high key is the separator key in the parent that routes traffic away from this node toward its right sibling.

These additions solve the following race condition: a reader descends to an internal node and selects a child pointer for key K. Before the reader latches that child, a concurrent split moves K's portion of the key space into a newly created right sibling. Without the right-link, the reader would descend into the wrong subtree. With the right-link, upon reaching the child page, the reader checks whether K exceeds the child's high key. If so, the reader follows the right-link to the correct sibling — traversing laterally along the current level without returning to the parent. This lateral movement requires no parent latch and does not block concurrent writers. PostgreSQL's nbtree implementation is a Blink-Tree variant, and this protocol is the reason PostgreSQL index reads never block index writes.

Structural Variants

B*Tree — Maximising Fill Factor via Deferred Splits

The B*Tree (Knuth) modifies the split trigger and split strategy to achieve a higher guaranteed minimum fill factor of 2/3 compared to the standard B-Tree's 1/2.

When a node overflows in a B*Tree, the algorithm first attempts to redistribute keys with an immediate sibling rather than splitting immediately. If the sibling has capacity, keys are redistributed so that both nodes are more uniformly full. A split is deferred until both the overflowing node and its adjacent sibling are simultaneously full. At that point, the two full nodes are split into three nodes rather than two, distributing 4t − 2 keys across three new nodes (approximately 4t/3 keys each ≈ 2/3 capacity). This produces a guaranteed minimum fill of 2/3 versus 1/2 for standard B-Trees — smaller trees, fewer pages, and fewer I/Os per operation on average. The implementation complexity is higher due to the need to coordinate two adjacent siblings during both insertion and split.

Fractal Tree Index — Write-Optimised Buffering

The Fractal Tree Index (Bender et al., implemented in TokuDB/Percona FT) is a B-Tree variant that dramatically reduces write amplification by introducing a message buffer at each internal node. Rather than propagating each write immediately down to the leaf, writes are deposited as messages into the root's buffer. Buffers are flushed downward lazily — in large batches — when they reach capacity. This batching converts what would be O(log n) individual random writes per insertion into infrequent, large sequential batch flushes down the tree levels.

Write amplification for a Fractal Tree of height h with buffer capacity B is O(log² n / B), compared to O(log n) for a standard B-Tree. The tradeoff: reads must inspect all buffers along the traversal path in addition to the leaf, increasing read amplification. Bloom filters maintained per buffer reduce unnecessary buffer scans for negative lookups. The Fractal Tree is optimal for write-dominated workloads (time-series ingestion, audit logs) where read performance can be slightly degraded in exchange for drastically reduced write I/O.

Copy-on-Write B-Tree — Immutable Page Semantics

A Copy-on-Write (COW) B-Tree never modifies existing pages in-place. Any modification to a page — whether a key insertion, deletion, or structural split — produces a new copy of that page at a new physical location. Because the parent node's child pointer now references an outdated page number, the parent must also be copied with the updated pointer. This cascades from the modified leaf all the way to the root: every ancestor on the modification path receives a new copy, culminating in a new root page. The final step is an atomic update of the root pointer (a single pointer-width write) to point to the new root, making the entire new tree version visible instantaneously.

This approach provides crash safety without any WAL: the old tree remains entirely intact until the atomic root pointer update, so a crash at any point during a modification leaves the database in the previous consistent state. Snapshots are trivially free — preserving the old root pointer preserves the entire historical tree. Readers accessing the old snapshot are never blocked by writers working on new copies. The primary drawback is write amplification: O(h) new pages are written per modification, compared to O(1) for in-place B+Tree modification. Used in: LMDB, ZFS DMU, Btrfs extent trees, Apple APFS.

PostgreSQL — nbtree Implementation

PostgreSQL's B-Tree access method is named nbtree and is a Blink-Tree variant. Its implementation includes several optimisations beyond the standard B+Tree specification:

Index Entry Deduplication (PostgreSQL 13+)

For non-unique indexes on columns with repeated values, storing one index entry per heap tuple produces significant space waste. PostgreSQL 13 introduced index entry deduplication: multiple heap tuple pointers (ItemPointers) that share an identical index key are combined into a single posting list — a compact array of ctid values stored alongside one key copy. A non-unique index on a status column with 5 distinct values and 1 million rows previously required 1 million index entries; with deduplication, it requires 5 posting list entries. Posting lists are maintained in ctid-sorted order to allow binary search within the list. The space saving for low-cardinality indexes frequently exceeds 70%.

Suffix Truncation in Internal Nodes

Internal separator keys only need to be large enough to correctly partition the key space between their adjacent children — they do not need to match any actual leaf key exactly. PostgreSQL's nbtree applies suffix truncation: separator keys in internal nodes are truncated to the shortest prefix that still distinguishes the left and right child subtrees. For variable-length character keys, this can dramatically reduce internal node key sizes, increasing the fan-out and reducing tree height. For example, the separator between a subtree ending at 2024-01-15 and one beginning at 2024-01-16 can be stored as 2024-01-1 (truncated) rather than the full timestamp string.

Metapage and Tree Introspection

Page 0 of every PostgreSQL B-Tree index is a metapage — a dedicated metadata page storing the current root page number, the fast root page number (a shortcut pointer that bypasses deletion-pending pages above a certain level), the tree level, and the last cleanup operation's statistics. The metapage is consulted once per index scan to locate the root.

MySQL InnoDB — Clustered Primary Key Architecture

InnoDB's primary architectural distinction is that every table's primary key is the clustered index — the table is physically stored as a B+Tree whose leaf pages contain full row data. There is no separate heap; the clustered index is the table. This layout provides optimal range scan performance for primary key queries (physically sequential leaf reads) and eliminates the second-lookup problem for covered queries.

Adaptive Hash Index (AHI)

InnoDB monitors B-Tree page access patterns and automatically constructs an in-memory hash index over the most frequently accessed internal B-Tree pages. Once the AHI is established for a particular access pattern, equality lookups against indexed columns served by the AHI bypass the B-Tree traversal entirely, achieving O(1) rather than O(log n) access. The AHI is partitioned to reduce contention in high-concurrency environments. It can be disabled (innodb_adaptive_hash_index = OFF) for workloads with high write concurrency where AHI maintenance overhead exceeds its benefit.

Change Buffer — Deferred Secondary Index Maintenance

Secondary index pages in InnoDB are distributed across the buffer pool without the physical locality of the clustered index. Inserting or deleting rows that require secondary index updates on pages not currently in the buffer pool would generate random I/O. InnoDB's change buffer defers these secondary index modifications: changes targeting secondary index pages absent from the buffer pool are buffered in a dedicated B-Tree structure within the tablespace. When those secondary index pages are eventually read into the buffer pool (for any reason), the buffered changes are applied synchronously. This deferred merge converts random write I/O into sequential merge I/O, reducing secondary index write amplification by up to 75% for insert-heavy workloads.

SQLite — Minimal B-Tree for Embedded Use

SQLite uses a B-Tree for indexes and a B+Tree (with rowid as the key) for tables. All data resides in a single file. SQLite table B-Trees store full row data in leaf nodes keyed on the rowid. WITHOUT ROWID tables use a B-Tree directly keyed on the declared PRIMARY KEY, avoiding the implicit rowid indirection layer entirely — appropriate for tables whose natural primary key is already compact and frequently used as a lookup key.

SQLite's WAL mode (PRAGMA journal_mode = WAL) enables concurrent reads during writes by maintaining a separate WAL file. Readers access a consistent snapshot by reading from the main database file plus any WAL entries that existed at their transaction start time. Writers append to the WAL without blocking readers. A checkpoint operation periodically transfers WAL content back to the main database file. SQLite's B-Tree page size is configurable from 512 to 65536 bytes (power of 2) and must be set before any data is written, as it determines the permanent fan-out for the life of the database.

Bulk Loading — Bottom-Up Tree Construction

When building a B+Tree index from scratch over an existing dataset (via CREATE INDEX), inserting each key individually through the standard insertion path costs O(n log n) I/Os. Bulk loading reduces this dramatically by sorting all index entries first and then constructing the B+Tree bottom-up in a single sequential pass.

The process: the entire set of (key, pointer) pairs is sorted using an external merge sort (bounded by maintenance_work_mem in PostgreSQL). Sorted pairs are packed into leaf pages from left to right at the configured fill factor (default 90% for index builds, higher than the 70% operational fill factor to minimise initial tree size). As each leaf page fills, its boundary key is promoted to construct the level-1 internal nodes. This continues until the root is constructed. The resulting tree is uniformly packed at the fill factor, physically sequential on disk, and requires no buffer pool pressure during construction beyond the sort memory.

-- Maximise build speed by allocating more sort memory:
SET maintenance_work_mem = '4GB';
SET max_parallel_maintenance_workers = 4; -- Parallel sort (PostgreSQL 11+)
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
-- 4 parallel workers sort independent data ranges, then merge-sort.
-- Effective build time scales near-linearly with worker count for I/O-bound builds.

-- Build without blocking concurrent reads (PostgreSQL 8.2+):
CREATE INDEX CONCURRENTLY idx_orders_created ON orders(created_at);
-- Phase 1: build index snapshot from one heap scan (no locks)
-- Phase 2: apply changes from concurrent modifications (second scan)
-- Phase 3: wait for active transactions, validate index consistency
-- Total: ~2× longer than standard CREATE INDEX; zero write blocking

Index Bloat — Detection, Causes, and Remediation

B+Tree indexes accumulate structural bloat over time through several mechanisms: lazy deletion leaves dead index entries occupying leaf page space; random-key insertions cause splits that produce half-full pages that are never refilled; frequent updates to indexed columns produce a stream of deletes and inserts that fragment leaf pages. The cumulative effect is an index that is physically larger than necessary, requires more I/Os per scan, and exhibits reduced buffer pool efficiency.

-- Measure index bloat precisely:
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT
  indexrelname,
  pg_size_pretty(pg_relation_size(indexrelid))  AS current_size,
  round(s.avg_leaf_density, 1)                     AS avg_leaf_fill_pct,
  round(s.leaf_fragmentation, 1)                   AS fragmentation_pct,
  s.dead_leaf_pages
FROM pg_stat_user_indexes i,
     pgstatindex(i.indexrelname::text) s
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

-- avg_leaf_density < 60% → significant bloat → schedule REINDEX
-- leaf_fragmentation > 30% → physical ordering degraded → sequential scans less efficient

-- Online remediation (PostgreSQL 12+, no table lock):
REINDEX INDEX CONCURRENTLY idx_orders_customer_id;
-- Builds a new index alongside the old one, atomically swaps, drops old.
-- ~2× longer than offline REINDEX. Zero query downtime.

-- Fillfactor — leave headroom for future updates:
CREATE INDEX idx_accounts_balance ON accounts(balance)
WITH (fillfactor = 70);
-- Leaf pages filled to 70% during build and splits.
-- 30% headroom absorbs future insertions before triggering splits.
-- Optimal for: range-update heavy tables, hot-row update tables.
-- Tradeoff: ~43% more leaf pages than fillfactor=100.

Query Planner Interaction — When Indexes Are Bypassed

The query planner chooses between index access paths and sequential scans based on estimated I/O cost, which depends on the estimated row count, the table's physical characteristics, and the configured cost parameters. Several common causes of index bypass:

  • Low selectivity: If the predicate matches more than approximately 5–15% of the table, a sequential scan becomes cheaper than the random I/O pattern of an index scan (this threshold varies by random_page_cost setting).
  • Stale statistics: After bulk loads or large DELETE operations, statistics from the previous ANALYZE run may be severely inaccurate. The planner's row count estimates diverge from reality, causing incorrect plan choices.
  • Default cost parameters for HDD: The default random_page_cost = 4.0 reflects HDD seek latency. On NVMe SSDs where random and sequential I/O costs are nearly equal, this setting causes the planner to undervalue index scans. Setting random_page_cost = 1.1 on SSD-backed systems substantially increases index scan selection frequency.
  • Function wrapping: A predicate like WHERE UPPER(email) = 'ALICE@EXAMPLE.COM' cannot use an index on email — the B+Tree is ordered by the raw column value, not its uppercased form. A functional index on UPPER(email) is required.
-- Calibrate cost parameters for SSD storage:
SET random_page_cost = 1.1;  -- SSD: random ≈ sequential → planner favours indexes
SET seq_page_cost    = 1.0;  -- Baseline (default)

-- Increase statistics target for skewed columns:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;
-- Default 100 histogram buckets is insufficient for heavily skewed distributions.
-- 500 buckets gives the planner finer-grained frequency estimates per value.

-- Verify index usage and efficiency:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE customer_id = 12345 AND status = 'pending';
-- Buffers: shared hit=N read=M → N pages from buffer pool, M from disk

Random keys (UUID v4) cause right-branch fragmentation, constant splits across the tree, and long-term 69% fill factor. Monotonic keys maintain ~90% fill and near-zero fragmentation.

Fillfactor configuration: Default fillfactor (90%) is optimal for append-only tables. Reduce to 70–80% for tables with frequent in-place updates to indexed columns, enabling HOT update chains and deferring split events.

shared_buffers sizing: Allocate 25% of physical RAM. This ensures the root and all first-level internal B-Tree pages for active indexes remain permanently resident, collapsing effective lookup cost to one physical leaf page read.

random_page_cost: Set to 1.1 on NVMe SSD deployments. The default 4.0 causes systematic underuse of indexes on random-access workloads where SSD random I/O cost is near-equal to sequential.

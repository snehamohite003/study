1. What Load Balancing Means

What it means

Load balancing is the process of distributing incoming traffic or units of work across multiple resources so that no single resource becomes the bottleneck while others remain underused. The resources may be web servers, API servers, worker nodes, cache nodes, or even database replicas depending on the architecture.

Why it is used

It is used because modern systems cannot depend on one server to handle all traffic reliably. As traffic grows, a single machine becomes a limit for CPU, memory, network, and connection capacity. Load balancing allows multiple machines to work together as one logical service.

How it works internally

The client usually connects to a single public endpoint, which belongs to the load balancer rather than to an individual backend. The load balancer then receives the request, checks which backends are healthy, applies a routing algorithm, and forwards the traffic to one selected backend.

Tradeoff

While load balancing improves scalability and availability, it also introduces another critical infrastructure layer that must itself be reliable and observable. If designed poorly, the load balancer can become a bottleneck or even a single point of failure.

Example

If an application has ten API servers, users should not have to know which one to call. The load balancer hides this complexity and exposes one stable entry point while internally spreading traffic across those ten servers.

2. Why Load Balancing Matters

What it means

Load balancing matters because adding more servers only helps when traffic is actually distributed across them. If all requests keep landing on a small subset of instances, then the rest of the infrastructure does not contribute meaningful capacity.

Why it is used

It is used to improve throughput, reduce latency, increase availability, and make horizontal scaling practical. It also helps systems survive backend failures by redirecting traffic away from dead or degraded instances.

How it works internally

Instead of clients choosing backends directly, the balancing layer continuously decides which backend should receive which request. This allows the system to react dynamically to failures, load changes, autoscaling events, and maintenance operations.

Tradeoff

The more intelligent the balancing logic becomes, the more operational complexity it introduces. Features like path-based routing, sticky sessions, TLS termination, and traffic weighting add power, but they also add failure modes and tuning requirements.

Example

Suppose one application server starts slowing down due to GC pauses or high CPU. Without load balancing, users hitting that server would suffer badly. With load balancing and health awareness, that server can receive less traffic or be removed from rotation.

3. Core Idea Behind Load Balancing

What it means

The core idea is not just to split traffic equally, but to spread work intelligently so that healthy backends are used efficiently, overloaded backends are protected, and failed backends are avoided. Equal request count is not always equal resource usage.

Why it is used

Real production traffic is not uniform. Some requests are cheap and finish quickly, while others are expensive and long-lived. Good load balancing must therefore think in terms of useful work distribution rather than simple counting.

How it works internally

The balancer makes routing decisions using data such as backend health, current connections, response time, routing rules, and sometimes request content. These decisions are repeated continuously as the environment changes.

Interview insight

In interviews, a strong answer is one that explains that load balancing is about protecting system behavior under real workloads, not just “sending traffic to many servers.” The distinction between equal distribution and good distribution is important.

4. Main Components of a Load Balancing System

4.1 Client

What it means

The client is the source of traffic. It may be a browser, mobile app, or another backend service making requests to a system entry point.

Why it is used

From the client’s perspective, the load balancer simplifies the system. The client does not need to know which backend node exists, which one is healthy, or how many instances are available at a given time.

How it works internally

The client typically resolves one hostname and sends traffic to one front door. All backend diversity remains hidden behind that endpoint, and the routing logic is handled inside the system.

4.2 Load Balancer

What it means

The load balancer is the decision-making traffic layer placed between clients and backends. It is responsible for receiving incoming traffic and selecting the appropriate destination.

Why it is used

It is used to centralize routing logic, backend health awareness, and traffic management. This prevents clients from needing direct knowledge of backend topology and allows the system to evolve internally without changing clients.

How it works internally

The balancer maintains a view of healthy backends and applies routing algorithms to incoming traffic. Depending on design, it may also terminate TLS, reuse backend connections, inspect HTTP metadata, and emit observability signals.

4.3 Backend Servers

What it means

Backend servers are the machines or service instances that actually process requests. These may be stateless app servers, web servers, search nodes, or other specialized service instances.

Why it is used

Multiple backends are used so that capacity can grow, failures can be tolerated, and work can be distributed. Without multiple eligible backends, load balancing has very limited value.

How it works internally

The backends register with or are known to the balancer, which periodically checks their health. Healthy backends remain in the routing pool, while failed ones are excluded until they recover.

4.4 Health Check Mechanism

What it means

Health checks are mechanisms used to decide whether a backend is currently able to serve traffic correctly. They are one of the most critical parts of a load balancing system because routing quality depends on health accuracy.

Why it is used

It is used so the balancer does not continue sending user traffic to an instance that is crashed, degraded, disconnected from dependencies, or too unhealthy to serve correctly.

How it works internally

The load balancer periodically probes each backend using TCP, HTTP, or custom application checks. Based on repeated successes or failures, it marks the backend healthy or unhealthy and updates routing eligibility.

4.5 Routing Policy / Algorithm

What it means

The routing policy defines how the balancer selects a backend for each request or connection. This can be simple rotation, least-connections logic, hashing, latency-aware selection, or more advanced policies.

Why it is used

It is used because different workloads behave differently. A policy that works well for short, uniform API calls may fail badly for long-lived sessions or mixed-capacity fleets.

How it works internally

When traffic arrives, the algorithm evaluates the set of eligible backends and chooses one based on configured logic and possibly runtime metrics such as current active connections or observed response times.

5. How Load Balancing Works Behind the Scenes

What it means

Behind the scenes, load balancing is a constant control loop rather than a one-time routing rule. Traffic comes in continuously, backend health changes over time, and the system must keep making new routing decisions based on current conditions.

How it works internally

A request first reaches the load balancer’s public endpoint. The balancer then determines which backends are currently healthy, applies routing logic, forwards the request, and monitors the result. This process repeats for every new request or connection.

  1. Client sends traffic to the load balancer endpoint.
  2. Balancer receives the connection or request.
  3. Balancer checks the healthy backend pool.
  4. Routing policy selects a backend.
  5. Traffic is forwarded.
  6. Response is returned to the client.
  7. Metrics and health state continue to update future decisions.
Why it matters

This dynamic behavior is what allows systems to survive node failures, rolling deploys, scaling events, and uneven traffic. If the balancer made only static routing decisions, it would quickly become ineffective in a live production system.

6. Types of Load Balancing

6.1 Layer 4 Load Balancing

What it means

Layer 4 load balancing operates at the transport layer and routes traffic using information such as source IP, destination IP, port number, and transport protocol. It does not need to parse the full application message in order to make routing decisions.

Why it is used

It is used because it is fast, efficient, and works for many kinds of traffic beyond HTTP. Since it deals with lower-level connection information, it usually has less overhead than application-aware balancing.

How it works internally

The balancer receives a connection and chooses a backend based on transport-level metadata and the configured policy. It then forwards the traffic stream without necessarily understanding HTTP paths, cookies, or headers.

Tradeoff

The tradeoff is reduced routing intelligence. Because the balancer does not understand application semantics, it cannot route requests differently based on URL path, API method, or header-based policies.

Example

A TCP proxy balancing raw API gateway connections to multiple backend nodes without inspecting the internal HTTP path is an example of Layer 4 balancing.

6.2 Layer 7 Load Balancing

What it means

Layer 7 load balancing operates at the application layer and understands protocol-specific details such as HTTP method, path, host, headers, cookies, and sometimes request body information. This makes routing decisions much more expressive.

Why it is used

It is used when the system needs application-aware routing. For example, one URL path may need to go to one service, while another path needs to go to a completely different service or cluster.

How it works internally

The balancer terminates or parses the application request, inspects the metadata, and then matches it against routing rules. Based on these rules, it chooses the correct backend pool and then selects a specific backend instance from that pool.

Tradeoff

The tradeoff is higher complexity and more CPU cost. Parsing application requests, applying routing policies, and performing advanced features like auth integration or WAF checks add overhead compared to simple transport-level forwarding.

Example

The balancer may send /api/catalog to catalog servers, /checkout to checkout servers, and /images to a media service, all from the same public hostname.

6.3 DNS-Based Load Balancing

What it means

DNS-based load balancing distributes traffic by returning different IP addresses for the same hostname. This is usually used to steer users toward specific regions, datacenters, or edge locations before the network connection is even established.

Why it is used

It is used for global traffic steering, disaster recovery, and coarse location-aware routing. DNS can direct users to a nearby region or to an alternate region when one is unhealthy.

How it works internally

When the client resolves the hostname, the DNS layer chooses which IP to return based on policy such as geography, latency estimation, or failover status. The client then connects to that returned destination and later local balancing may happen there.

Tradeoff

The tradeoff is lack of precise real-time control. DNS responses are cached by clients and resolvers, so changes in traffic steering may take time to take effect and cannot influence already-cached clients immediately.

6.4 Global vs Local Load Balancing

What it means

Global load balancing decides which region or datacenter should receive traffic, while local load balancing distributes traffic among instances inside one region, cluster, or datacenter. These two layers often work together in large systems.

Why it is used

It is used because traffic distribution happens at multiple scopes. A system first needs to decide which major location should serve the user, and then it needs to decide which specific machine in that location should handle the request.

How it works internally

Global routing may be done by DNS, anycast, or geo-routing policy, while local routing is usually handled by an L4 or L7 balancer within that selected region. The two-tier model helps combine geographic optimization with backend-level efficiency.

7. Core Load Balancing Algorithms

7.1 Round Robin

What it means

Round robin sends traffic to each backend in rotating sequence. If there are three backends, the balancer picks A, then B, then C, then starts again from A.

Why it is used

It is used because it is simple, predictable, and often good enough when servers are similar and requests have roughly similar cost. It is also easy to reason about operationally.

How it works internally

The balancer keeps track of the last backend selected and advances a pointer with each new request or connection. It does not need runtime load metrics to operate.

Tradeoff

The tradeoff is that it ignores actual backend load and request cost. If some requests are much heavier than others, simple round robin can still create severe imbalance.

Example

For many short-lived and uniform API requests, round robin may perform adequately and provide very simple traffic spread across identical app servers.

7.2 Weighted Round Robin

What it means

Weighted round robin is a variation where some servers receive more traffic than others according to assigned weight. This is useful when the backend fleet has unequal capacity.

Why it is used

It is used when some nodes are larger, newer, or intentionally provisioned with more CPU, memory, or network bandwidth. Sending equal traffic to unequal machines would be inefficient.

How it works internally

The balancer repeats backends in the effective rotation according to their weight. A server with weight 2 may appear twice as often in selection as a server with weight 1.

Tradeoff

The tradeoff is that assigned weight is still only an approximation. If workload changes dynamically or request cost varies unpredictably, static weighting may not reflect real backend pressure.

7.3 Least Connections

What it means

Least-connections routing sends traffic to the backend with the fewest currently active connections. This tries to account for the fact that some servers may already be busy with long-lived sessions.

Why it is used

It is used when connection duration varies a lot and simple request rotation does not reflect actual workload. It can perform better than round robin for chatty or long-lived connection patterns.

How it works internally

The balancer tracks active connection counts for each backend and chooses the backend with the lowest current count. As connections open and close, the state changes continuously.

Tradeoff

The tradeoff is that connection count is still not the same as actual backend cost. One active connection may be idle while another may drive expensive database-heavy traffic.

7.4 Least Response Time / Latency-Based Routing

What it means

This strategy favors backends that are currently responding faster than others. The assumption is that lower response time may indicate lower load or healthier behavior.

Why it is used

It is used when response time is an important operational signal and the system wants to prefer backends that appear to be handling traffic more efficiently.

How it works internally

The balancer measures backend response time over a moving window and uses that as one of the routing inputs. It may combine response time with other signals such as connection count or error rate.

Tradeoff

The tradeoff is instability risk. If the balancer reacts too aggressively to short-lived latency spikes, traffic may oscillate between backends and make the problem worse.

7.5 Hash-Based Routing

What it means

Hash-based routing uses a deterministic key such as client IP, session ID, or user ID to consistently map traffic to a backend. This creates routing affinity without necessarily storing central session state.

Why it is used

It is used when session locality, cache locality, or partition alignment matters. For example, sending the same user repeatedly to the same backend may improve in-memory cache effectiveness.

How it works internally

The balancer computes a hash from the chosen key and maps that result to a backend. If the backend pool changes, the mapping may shift depending on the hashing strategy used.

Tradeoff

The tradeoff is hotspot risk. If certain keys are far more active than others, the mapped backends can become overloaded even though the algorithm is deterministic and stable.

7.6 Random with Power of Two Choices

What it means

This algorithm randomly picks two candidate backends and then chooses the less loaded one. It is a clever technique because it gives much better balance than pure random selection while keeping implementation simple.

Why it is used

It is used because it offers a strong balance between quality and overhead. The system gets much of the benefit of smarter balancing without requiring a full global ranking of all backends for every request.

How it works internally

For each request, the balancer samples two backends from the healthy pool, compares their load-related signal, and chooses the better one. This greatly reduces the chance of traffic repeatedly hitting already-busy nodes.

8. Session Persistence and Sticky Sessions

What it means

Sticky sessions mean that repeated requests from the same client are directed to the same backend instance. This behavior is often used when the application keeps session-specific state in local memory instead of externalizing it.

Why it is used

It is used because it can simplify stateful applications and avoid the immediate need for a shared session store. In legacy architectures, this is sometimes the easiest way to keep user context working.

How it works internally

The balancer identifies a client using a cookie, client IP, or session key, and then applies a rule that keeps subsequent traffic tied to the same backend. As long as that backend remains available, the client keeps returning there.

Tradeoff

The tradeoff is reduced balance quality and weaker failover. If one backend accumulates many heavy sticky sessions, it can become a hotspot while other nodes stay underutilized. If it fails, those session-bound users may suffer more disruption.

Interview insight

In interviews, a strong answer usually says sticky sessions may be acceptable temporarily, but long-term scalable systems prefer stateless application layers with shared or externalized state.

9. Health Checks

What it means

Health checks are the mechanisms the balancer uses to determine whether a backend should continue receiving traffic. They are a central part of availability because routing decisions are only as good as the health information behind them.

Why it is used

It is used to prevent the balancer from forwarding requests to broken or degraded instances. Without health checks, the balancer would keep treating every registered backend as usable even if users are already seeing failures.

How it works internally

The balancer periodically probes backends using TCP checks, HTTP checks, or deeper application-specific logic. Based on repeated pass or fail results, it marks a backend healthy or unhealthy and updates routing state.

Tradeoff

The tradeoff is between speed and correctness. Very shallow health checks may miss serious problems, while very deep health checks may add more complexity and can themselves become noisy or expensive if misdesigned.

Example

A backend might respond successfully to a simple TCP health check even though every real API request fails because the database connection pool is exhausted. That is why meaningful health checks matter.

10. TLS Termination

What it means

The load balancer handles the TLS handshake with the client and decrypts traffic before forwarding it to the backend servers. This means the client establishes the secure HTTPS session with the balancer rather than directly with each application instance.

Why it is used

It is used to centralize certificate management, reduce repeated cryptographic overhead on application servers, and enable Layer 7 inspection of HTTP metadata for routing and security policies. Managing TLS in one place is operationally much simpler than managing it separately on every backend.

How it works internally

When the client connects using HTTPS, the TLS handshake is completed at the load balancer. After traffic is decrypted, the balancer can inspect host, path, headers, or cookies and decide where the request should go. It may then forward the request in plain HTTP internally or re-encrypt it before sending it to the backend.

Tradeoff

If internal traffic is not re-encrypted and the internal network is not trusted, security risk increases because the decrypted request now travels inside the infrastructure in plaintext. TLS termination therefore improves flexibility and simplicity, but it also changes the trust boundary of the system.

Example

An e-commerce platform may terminate TLS at the edge load balancer, inspect the path, and route /catalog to one service and /checkout to another. This is only possible because the balancer has already decrypted the request.

11. Traffic Distribution Challenges

What it means

Traffic distribution is difficult because production traffic is not uniform. Requests differ in size, duration, CPU cost, I/O cost, and downstream dependency usage, so simply counting requests often does not capture real backend pressure.

Why it matters

This matters because a balancing strategy that looks fine in a synthetic benchmark may behave badly in production. A few expensive requests, sticky sessions, or long-lived connections can create hotspots even when the request count appears evenly spread.

How it works internally

Imbalance can emerge from many sources, including connection reuse, retry storms, regional skew, hot clients, uneven backend capacity, and expensive request paths. Observability is needed to detect these hidden forms of imbalance.

Interview insight

Strong candidates explain that good load balancing is workload-aware. They do not assume that one generic algorithm automatically solves all traffic-distribution problems.

12. Interview-Level Important Load Balancing Concepts Explained Deeply

12.1 Why Load Balancing Is Essential for Horizontal Scaling

What it means

Horizontal scaling means increasing capacity by adding more machines. But those machines only become useful if incoming traffic is actually spread across them in a controlled way.

Why it matters

Without load balancing, adding servers does not necessarily increase usable capacity. Traffic may remain concentrated on a subset of nodes, creating overload on those nodes while the rest of the fleet does very little work.

How it works internally

The load balancer acts as the mechanism that maps incoming traffic to the expanded fleet. It is what turns “many servers” into “one larger service” from the client’s perspective.

Interview insight

In interviews, this is an important systems-thinking point. Horizontal scaling is not complete until there is a routing layer that can use the extra capacity effectively.

12.2 L4 vs L7 Load Balancing

What it means

L4 balancing routes traffic using transport-level information, while L7 balancing routes traffic using application-level information. The distinction is fundamentally about how much the balancer understands about the traffic it is forwarding.

Why it matters

This matters because the level of visibility determines both routing power and cost. If you only need to spread raw TCP traffic, L4 may be enough. If you need path-based or header-based routing, you need L7 awareness.

How it works internally

L4 forwards connections based on low-level metadata and typically does less parsing. L7 inspects request contents, applies richer policy, and can integrate with application-facing concerns such as auth, WAF, or API-level routing.

Tradeoff

L7 is more flexible but also more expensive in CPU, memory, and configuration complexity. L4 is simpler and faster but gives up application-aware control.

12.3 Load Balancing Is Not Just Equal Distribution

What it means

A common misconception is that good balancing means every server receives exactly the same number of requests. In reality, the right goal is to prevent overload and use total capacity well, not to make counters look symmetrical.

Why it matters

If one request takes 2 milliseconds and another takes 2 seconds, then equal request count can still mean severe resource imbalance. Backend saturation depends on actual work cost, not just traffic count.

How it works internally

Balancers may need to rely on richer signals such as active connections, response time, queue depth, or adaptive policies to approximate true backend load more accurately than simple request counts can.

12.4 Request-Level vs Connection-Level Balancing

What it means

Some systems balance individual requests, while others primarily balance connections. This distinction matters because one connection can carry many requests over time, especially with keep-alive or multiplexed protocols.

Why it matters

If connections are uneven in request volume, then even perfect connection balancing may still create poor request balancing. One backend might receive a few extremely busy connections while another gets many nearly idle ones.

How it works internally

Connection-level balancing usually occurs once when the connection is assigned. Request-level balancing can make a fresh routing decision for each request, which offers more control but may be more complex depending on the protocol.

12.5 Health Checks and Why “Alive” Is Not Enough

What it means

A backend being alive only means the process or host still exists. It does not guarantee that the backend is capable of serving real production traffic correctly and within acceptable latency.

Why it matters

This matters because user-visible failures often happen when instances are technically running but operationally broken. A backend may be alive while its database calls fail, its thread pool is exhausted, or its latency is far beyond acceptable thresholds.

How it works internally

Meaningful health checks often go beyond port-open tests and verify application readiness or dependency reachability. A good load balancer uses these results to avoid routing traffic to instances that are only “alive” in the shallowest sense.

12.6 Session Affinity and Sticky Sessions

What it means

Session affinity means repeated traffic from the same user or session is directed to the same backend. This creates locality, but also creates coupling between a user and a specific instance.

Why it matters

It matters because it can simplify application design temporarily, but it also makes the system less flexible and less balanced. If one sticky-bound backend becomes overloaded, the load balancer has less freedom to redistribute those users cleanly.

How it works internally

The balancer may use a cookie, IP hash, or session key to persist the mapping. As long as the mapping remains stable, the same user keeps going to the same backend unless failure forces reassignment.

Tradeoff

The tradeoff is that short-term convenience often harms long-term scalability and failover quality. Stateless backends with shared session storage are usually a stronger design for growing systems.

12.7 Load Balancing and Availability

What it means

Load balancing is not only a performance mechanism; it is also an availability mechanism. By avoiding failed nodes and redirecting traffic to healthy ones, it helps the system remain usable despite backend failures.

Why it matters

A single backend crash should not automatically become a user-facing outage. With proper health checks and routing logic, the failure of one instance can be absorbed without users even noticing.

How it works internally

The balancer marks unhealthy backends out of service and routes new requests to the remaining healthy pool. This allows rolling deployments, instance crashes, or partial infrastructure failures to be tolerated more gracefully.

12.8 TLS Termination and Architectural Impact

What it means

TLS termination at the balancer changes the architecture because the balancer becomes both the security endpoint and the request inspection point. It is no longer just forwarding opaque traffic; it is actively participating in the HTTP processing flow.

Why it matters

This matters because it affects operational simplicity, performance, and trust boundaries at the same time. It also influences where security policy is enforced and whether internal traffic needs additional protection.

How it works internally

After the TLS handshake completes, the balancer can inspect request contents, apply Layer 7 routing rules, and optionally attach headers or metadata before forwarding traffic. If desired, it can then re-establish TLS toward the backend.

12.9 Overload Protection and Backpressure

What it means

A load balancer can also participate in overload control by refusing, delaying, or shaping traffic when the backend fleet is already saturated. This makes it part of the system’s protective control plane rather than just a passive router.

Why it matters

Without overload protection, the balancer may continue flooding already unhealthy backends, worsening latency and causing broader collapse. Controlled rejection is often healthier than uncontrolled queue growth and cascading timeouts.

How it works internally

The balancer may cap concurrent requests, reject excess traffic, prioritize certain routes, or work with upstream rate limiting and circuit-breaking systems. These mechanisms preserve system stability under stress.

12.10 Hotspots and Uneven Traffic

What it means

Hotspots occur when some users, keys, paths, or sessions generate far more traffic or far more expensive work than others. Even with a good algorithm, these hotspots can create backend imbalance.

Why it matters

If one subset of traffic is much heavier, then the fleet may appear balanced at high level while one backend or one shard becomes overloaded. This is one reason why real systems need observability in addition to basic routing logic.

How it works internally

Hotspots often emerge through sticky sessions, hash-based routing, long-lived heavy clients, or path-specific expensive operations. Identifying them requires backend-level metrics, not just balancer-level request totals.

12.11 Global Load Balancing

What it means

Global load balancing routes traffic between major regions or datacenters rather than just among local servers. It decides where a user should connect at large geographic scale.

Why it matters

This matters because geographic distance affects latency, and regional failures affect availability. Global balancing helps send users closer to healthy infrastructure while giving the platform a way to survive larger failure domains.

How it works internally

Global routing may use DNS, anycast, geo-routing, or latency-based policy to steer the client toward a chosen region. Once the client reaches that region, local load balancing takes over inside the regional environment.

12.12 Client-Side vs Server-Side Load Balancing

What it means

In server-side load balancing, a dedicated balancing layer chooses the backend. In client-side load balancing, the caller itself chooses a backend from a list obtained through service discovery.

Why it matters

This matters because the placement of balancing logic affects architecture, observability, coordination, and failure modes. Centralized balancing simplifies clients, while client-side balancing can reduce central bottlenecks and allow more local decision-making.

How it works internally

In client-side balancing, the client keeps an updated view of service instances and chooses one based on a local algorithm. In server-side balancing, the client remains simpler because the dedicated balancer does the selection.

12.13 Observability in Load Balancing

What it means

Observability in load balancing means measuring how traffic is distributed, how backends are performing, and whether the balancing policy is actually producing healthy outcomes. Without this, teams are effectively routing traffic blindly.

Why it matters

Imbalance, retries, backend slowness, and regional skew are often invisible without metrics. A fleet can appear fine from the outside while one backend pool is overloaded or one route is producing hidden failures.

How it works internally

Important signals include request count by backend, error rate, response time, health-check failures, active connections, retry volume, and backend saturation. These metrics help tune routing policy and detect hidden hotspots.

12.14 Load Balancer as a Potential Single Point of Failure

What it means

Even though the load balancer improves backend resilience, it can itself become a critical dependency. If it is the only front door and it fails, the whole service may become unreachable.

Why it matters

This matters because many architectures accidentally move the SPOF from the backend tier to the ingress tier. High availability at the backend layer is not enough if the entry point remains fragile.

How it works internally

Production systems typically solve this using redundant balancers, managed HA services, multiple balancer nodes, or global failover strategies. The load-balancing layer must itself be designed for resilience.

12.15 Algorithm Selection Depends on Workload

What it means

No single algorithm is always the best choice. The correct algorithm depends on backend uniformity, request duration, session behavior, request cost variability, and the need for locality or affinity.

Why it matters

Choosing an algorithm without understanding workload is a common design mistake. An approach that works for one system may perform badly in another because the traffic pattern is different.

How it works internally

Engineers usually start with a simple policy and evolve it when metrics show imbalance, hotspots, or poor latency behavior. Algorithm choice should follow workload evidence, not habit.

Interview insight

In interviews, the strongest answers explain why a particular algorithm fits the scenario. Naming algorithms is not enough; matching them to workload characteristics is what demonstrates understanding.

13. Example: Load Balancing in an E-Commerce System

What it means

Consider an e-commerce platform with multiple frontend servers, API servers, checkout services, and recommendation services. Users see one entry point, but internally traffic must be distributed across many specialized backend pools.

How it works internally

A public Layer 7 load balancer terminates TLS and inspects the request path. It may route /api/catalog to catalog servers, /checkout to checkout servers, and static content toward CDN-backed origins or media services.

Why it matters

This allows each service group to scale independently and makes backend failures less visible to users. If one checkout instance fails, health checks remove it from rotation and the rest of the checkout fleet continues serving requests.

Example failure scenario

If holiday traffic spikes sharply, additional API or checkout servers can be added behind the same load balancer. The clients continue using the same public endpoint, while the balancer begins distributing traffic across the larger backend fleet.

14. Common Load Balancing Failure Modes

What it means

Load balancing systems can fail in subtle ways even when the idea is correct. Common problems include shallow health checks, balancer-level single points of failure, sticky-session hotspots, bad algorithm choice, and retry amplification.

Why it matters

These failures are dangerous because they often create the illusion that traffic is distributed while users still experience outages or high latency. The presence of a load balancer does not automatically guarantee good balancing.

Examples
  • Load balancer itself is a single point of failure
  • Health checks are too shallow to detect degraded nodes
  • Round robin is used for highly uneven request costs
  • Sticky sessions create overloaded backends
  • Retries increase traffic to already struggling services
  • Connection reuse creates hidden imbalance
  • Global DNS routing keeps stale region mappings cached

15. Strong Interview Answer

Load balancing is the mechanism that distributes incoming traffic across multiple resources so the system can scale horizontally, remain available, and use capacity efficiently. It works by selecting healthy backends using policies such as round robin, least connections, weighted routing, or hashing, and it often includes features like health checks, failover, TLS termination, and path-based routing. The right load balancing design depends on traffic patterns, protocol layer, backend behavior, and the need to balance performance, resilience, and operational complexity.

16. Final Summary

What you should deeply understand

To understand load balancing well, you should know why it exists, how it enables horizontal scaling, how L4 and L7 differ, how routing algorithms behave under real workloads, why health checks are critical, and why sticky sessions can be problematic in scalable systems.

What matters in real systems

You should also understand that load balancing is tied to availability, failover, TLS termination, observability, overload protection, and hotspot detection. It is not just a networking feature; it is a core control mechanism in distributed systems.

Most important takeaway

Load balancing is not simply “sending requests to many servers.” It is controlled traffic management that helps a distributed system use capacity effectively, stay available during failure, and grow without collapsing under uneven load.

Why Indexes Exist — The Full Table Scan Problem

Without an index, every query must scan every row of a table to find matching records. For a table with 100 million rows, even a simple WHERE user_id = 42 requires reading every row. An index transforms this O(n) scan into an O(log n) tree traversal or O(1) hash lookup:

-- No index: full sequential scan (100M rows read)
EXPLAIN SELECT * FROM orders WHERE customer_id = 12345;
-- Seq Scan on orders  (cost=0.00..2100000.00 rows=847 width=128)
--                      ^^^^^^^^^^^^ reads ALL 100M rows

-- With B+Tree index on customer_id:
CREATE INDEX idx_orders_customer ON orders(customer_id);
EXPLAIN SELECT * FROM orders WHERE customer_id = 12345;
-- Index Scan using idx_orders_customer  (cost=0.56..3247.89 rows=847 width=128)
--                                        ^^^^ traverses ~26 B+Tree levels (log₂ 100M)
--                                        then reads only the 847 matching rows

-- Performance: 2,100,000 → 3,247 cost units = ~646x faster
-- In practice: seconds → milliseconds

B-Tree vs B+Tree — The Standard Database Index Structure

Almost every relational database (PostgreSQL, MySQL InnoDB, Oracle, SQL Server) uses a B+Tree as its primary index structure. Understanding the internal layout is critical for query optimization:

B+Tree Structure (order=4, max 3 keys per node) Root Node (Internal) ┌───────────────────────┐ │ 30 │ 70 │ └─────┬─────┴──────┬────┘ ┌─────────────┘ └──────────────┐ Internal Node Internal Node ┌─────────────────┐ ┌────────────────────┐ │ 10 │ 20 │ │ 50 │ 60 │ 70 │ └──┬───┴────┬─────┘ └──┬───┴──┬───┴──┬───┘ │ │ │ │ │ Leaf Nodes (contain ACTUAL DATA, linked as doubly linked list) ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │1│2│3│...│←→│10│15│20 │←→│30│35│40 │←→│50│55│60 │←→│70│80│90 │ └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘ ↑ ↑ Each leaf node contains: key + pointer to actual row (heap tuple) Leaf nodes linked → enables efficient range scans without returning to root! Key properties vs plain B-Tree: B-Tree: internal nodes store BOTH keys AND data → less fan-out B+Tree: internal nodes store ONLY keys → higher fan-out → shallower tree B+Tree: ALL data in leaf level → consistent O(log n) for all lookups B+Tree: leaf linked list → range scans are sequential reads (fast I/O)

B+Tree Height and I/O Cost Analysis

// Why B+Trees are shallow (minimizing disk I/O):
// Page size = 16KB (PostgreSQL default)
// Key size = 8 bytes (bigint), pointer = 6 bytes → ~1000 keys per internal node

// Tree height for different table sizes:
Height = ceil(log₁₀₀₀(num_rows))

rows = 1,000          → height = 1  (root IS the leaf)
rows = 1,000,000      → height = 2  (root → leaf)
rows = 1,000,000,000  → height = 3  (root → internal → leaf)
rows = 10^12          → height = 4  (root → 2 internal levels → leaf)

// Even 1 TRILLION rows: only 4 I/O operations to find any row!
// Compare: hash index = 1 I/O (but no range scan)
// Compare: full scan = 10^12 I/Os

// Real PostgreSQL: root + 2 levels typically cached in shared_buffers
// Effective I/O cost for most queries: 1 disk read (only leaf fetch)

// Write cost: insert into B+Tree
// 1. Read root page (likely cached)
// 2. Traverse to leaf (cached internal pages)
// 3. Insert into leaf (1 write)
// 4. If leaf full → SPLIT: write 2 new leaves + update parent (cascade up)
// Splits are O(log n) in worst case — amortized O(1) in practice

Page Splits and Fragmentation

-- PostgreSQL: monitor index bloat from frequent splits
SELECT
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan, idx_tup_read, idx_tup_fetch,
  -- Bloat estimation
  round(100 * (1 - (SELECT reltuples FROM pg_class WHERE oid = indexrelid)
    / NULLIF(idx_tup_read, 0))::numeric, 2) AS bloat_ratio
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;

-- Fix fragmentation:
REINDEX INDEX CONCURRENTLY idx_orders_customer;
-- Or in PostgreSQL 12+: REINDEX CONCURRENTLY (no table lock!)

-- Use UUID v7 (time-ordered) instead of random UUID v4 for primary keys!
-- Random UUID v4: inserts anywhere in B+Tree → constant page splits → fragmentation
-- UUID v7: always inserts at rightmost leaf → minimal splits (like SERIAL/BIGSERIAL)

Hash Indexes — O(1) Equality Lookups

// Hash index: hash(key) → bucket → pointer to row
// Perfect for: equality (=), membership (IN)
// Useless for: range queries (<, >, BETWEEN, LIKE 'prefix%')

// PostgreSQL hash index:
CREATE INDEX idx_users_email_hash ON users USING hash(email);
-- Best for: WHERE email = 'alice@example.com'
-- Useless for: WHERE email LIKE 'alice%'
-- Useless for: ORDER BY email

// Internal structure (PostgreSQL hash index):
// Primary pages: fixed array of bucket pages
// Overflow pages: chained when bucket overflows
// Bitmap pages: track which overflow pages are free

// Collision handling: open addressing or chaining
// Load factor target: ~75% — beyond this, performance degrades
// Resize: double bucket count, rehash all entries (expensive!)

// Memory hash indexes (Redis, Memcached):
// Entire structure fits in RAM → true O(1) amortized
// Disk hash indexes: O(1) I/Os only if no overflow chain

LSM-Tree (Log-Structured Merge-Tree) — Write-Optimized Indexing

Used by RocksDB, LevelDB, Cassandra, ScyllaDB, HBase, ClickHouse. Designed for write-heavy workloads where B+Tree's random writes cause I/O bottlenecks:

LSM-Tree Architecture WRITES always go to MemTable (in-memory sorted structure) Write ──────────────────────────────────────────► ┌─────────────────────────────┐ │ WAL (Write-Ahead Log) │ ← Durability: written first │ /data/wal/000001.log │ Sequential disk write (fast) └──────────────┬──────────────┘ │ (also written) ┌──────────────▼──────────────┐ │ MemTable (Red-Black Tree │ ← In-memory sorted tree │ or Skip List, ~64MB) │ O(log n) inserts └──────────────┬──────────────┘ │ When full: flush to disk ┌──────────────▼──────────────┐ Level 0 │ SSTable (Sorted String Table)│ ← Immutable sorted file │ L0: 0001.sst 0002.sst │ Each file: bloom filter + index └──────────────┬──────────────┘ │ Compaction (background) ┌──────────────▼──────────────┐ Level 1 │ L1: larger sorted runs │ ← Merged, deduplicated └──────────────┬──────────────┘ │ Further compaction Level 2+ │ L2, L3... (exponentially │ ← Older, larger, sorted data │ larger at each level) │ └─────────────────────────────┘ Write path: WAL + MemTable insert = 2 sequential writes → very fast Read path: MemTable → L0 → L1 → ... → Ln = multiple I/Os → slower 
// SSTable (Sorted String Table) internal layout:
// ┌─────────────────────────────────────────────┐
// │ Data Blocks (compressed key-value pairs)     │
// │ Index Block (first key per data block)       │
// │ Bloom Filter (probabilistic key existence)   │
// │ Metadata (compression type, stats)           │
// │ Footer (offsets to index + bloom filter)     │
// └─────────────────────────────────────────────┘

// Bloom Filter — critical for read performance:
// Before reading an SSTable, check bloom filter:
// "Is key 'user:42' possibly in this file?"
// False positive: ~1% chance (configurable)
// False negative: NEVER (if bloom says NO → definitely not in file)
// Result: skip ~99% of SSTables on read — massive I/O reduction!

// Compaction — merging SSTables (tiered vs leveled strategy):

// Leveled Compaction (RocksDB default, Cassandra optional):
// Each level has size limit. When exceeded, pick one file, merge with
// ALL overlapping files in next level. Result: better read performance.
// Write amplification: ~10-30x (data written many times during compaction)

// Tiered Compaction (Cassandra default, STCS):
// When 4 same-size SSTables accumulate, merge into one larger SSTable.
// Better write throughput. Worse read performance (more files to check).
// Write amplification: ~4-5x

Composite (Multi-Column) Indexes — The Column Order Rule

The order of columns in a composite index is critical. The index is ordered by the first column, then the second within equal first-column values, etc. This governs which queries can use the index:

-- Table: orders(id, customer_id, status, created_at, total)
CREATE INDEX idx_composite ON orders(customer_id, status, created_at);

-- USES the index (matches leftmost prefix rule):
WHERE customer_id = 5                            ← uses customer_id prefix ✓
WHERE customer_id = 5 AND status = 'pending'     ← uses customer_id + status ✓
WHERE customer_id = 5 AND status = 'pending'     ←
  AND created_at > '2024-01-01'                  ← uses all 3 columns ✓

-- DOES NOT USE the index efficiently:
WHERE status = 'pending'                         ← skips customer_id → full scan ✗
WHERE created_at > '2024-01-01'                  ← skips first 2 columns ✗
WHERE customer_id = 5 AND created_at > '2024-01-01'
-- ↑ Uses customer_id prefix, but cannot use created_at
--   (status is skipped — breaks the index chain)
--   Filter on created_at applied AFTER index scan for customer_id=5

-- RULE: Put equality conditions first, range conditions last
-- RULE: Highest cardinality column FIRST for best selectivity
-- WRONG order: (status, customer_id) — status has 5 values, customer_id has millions
-- RIGHT order: (customer_id, status)  — prune by millions first, then by 5 values

Covering Index — Index-Only Scans

A covering index includes all columns needed by a query, so the database never touches the main table (heap). Eliminates the second I/O hop from index → heap:

-- Query that accesses both index and heap (two I/O hops):
SELECT total, created_at FROM orders WHERE customer_id = 5;
-- Step 1: B+Tree lookup on customer_id → get row pointers
-- Step 2: Fetch EACH row from heap pages (random I/O!) to get total, created_at
-- If 10,000 matching rows → 10,000 random heap reads → SLOW

-- Covering index: include all needed columns
CREATE INDEX idx_covering ON orders(customer_id) INCLUDE (total, created_at);
-- PostgreSQL INCLUDE syntax: extra columns stored in leaf, not part of key
-- MySQL: just add to index: (customer_id, total, created_at)

-- Now query can do INDEX-ONLY SCAN:
EXPLAIN SELECT total, created_at FROM orders WHERE customer_id = 5;
-- Index Only Scan using idx_covering ← NO heap access!
-- All data comes from index leaf nodes → sequential reads → FAST

-- Cost: larger index (more disk space, slower writes)
-- Benefit: reads become pure index scans
-- Ideal for: frequently queried columns on high-read tables

Partial Indexes — Index Only What You Query

-- Full index on status column: all 100M rows
CREATE INDEX idx_status ON orders(status);
-- But 99% of orders are 'completed' — never queried!
-- 99% of index space wasted. Index updates slow every write.

-- Partial index: only index rows matching WHERE clause
CREATE INDEX idx_pending_orders ON orders(created_at)
WHERE status IN ('pending', 'processing');
-- Only 1% of rows indexed → 100x smaller index → faster everything

-- Query MUST include the partial index condition to use it:
SELECT * FROM orders WHERE status = 'pending' AND created_at > NOW() - INTERVAL '7 days';
-- ✓ Planner uses partial index (condition matches WHERE clause)

SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days';
-- ✗ Cannot use partial index (might include completed orders)

-- Real-world partial index examples:
-- Unique partial index: enforce unique email only for active users
CREATE UNIQUE INDEX idx_unique_active_email ON users(email)
WHERE deleted_at IS NULL;
-- Two deleted users can have same email. Active users must have unique email.

-- Partial index for soft-deletes (never query deleted rows):
CREATE INDEX idx_active_orders ON orders(customer_id, created_at)
WHERE deleted_at IS NULL;
-- All queries with WHERE deleted_at IS NULL get tiny, fast index

ACID — What Each Letter Actually Means Internally

A — Atomicity: All or Nothing

A transaction is treated as a single indivisible unit. Either ALL operations within it succeed and are committed, or NONE of them take effect. If the database crashes mid-transaction, the partial work is completely rolled back on recovery.

-- Classic example: bank transfer (must be atomic)
BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;  ← debit Alice
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;  ← credit Bob
COMMIT;

-- If crash occurs between the two UPDATEs:
-- Without atomicity: Alice loses $500, Bob gets nothing (money destroyed!)
-- With atomicity:    WAL detects uncommitted transaction → rolls back on restart

-- HOW it works internally — Undo Log (InnoDB) / Rollback Segment:
// Before executing "balance = balance - 500":
// Write UNDO record: "account 1 had balance=1000 before this change"
// Apply change: balance = 500
// If ROLLBACK or crash: read undo log → restore balance = 1000
// Undo log stored in rollback segment (InnoDB) or pg_undo (PostgreSQL 14+)

C — Consistency: Database Invariants Always Hold

Consistency in ACID means that a transaction brings the database from one valid state to another valid state. This is primarily enforced by application logic and database constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY). Note: this is different from CAP's "Consistency" (which means linearizability).

-- Database-enforced consistency constraints:
CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),  ← FK: no orphan orders
  total       DECIMAL(10,2) CHECK (total > 0),           ← CHECK: no negative totals
  status      VARCHAR(20) NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','processing','completed','cancelled'))
);

-- Transaction that violates consistency is rejected entirely:
BEGIN;
  INSERT INTO orders(customer_id, total) VALUES (99999, -50.00);
  -- ERROR: new row violates check constraint "orders_total_check"
  -- OR: ERROR: insert or update on table "orders" violates foreign key
  -- Entire transaction rolled back. Database stays in consistent state.
ROLLBACK; -- (happens automatically on error)

-- Application-level consistency (enforced in transaction):
BEGIN;
  -- Business rule: order total must equal sum of line items
  DO $$
  DECLARE calculated_total DECIMAL;
  BEGIN
    SELECT SUM(quantity * unit_price) INTO calculated_total
    FROM order_items WHERE order_id = 123;

    IF calculated_total != (SELECT total FROM orders WHERE id = 123) THEN
      RAISE EXCEPTION 'Order total inconsistency detected';
    END IF;
  END $$;
COMMIT;

I — Isolation: Concurrent Transactions Don't Interfere

Isolation ensures that concurrent transactions execute as if they were run sequentially. The SQL standard defines four isolation levels with different trade-offs between correctness and performance:

*PostgreSQL's Repeatable Read also prevents phantom reads via MVCC snapshot — unlike MySQL InnoDB which needs gap locks.

// Anomalies illustrated:

// Dirty Read: T2 reads T1's uncommitted data
T1: UPDATE accounts SET balance = 0 WHERE id = 1;    ← not committed yet
T2: SELECT balance FROM accounts WHERE id = 1;        ← reads 0 (dirty!)
T1: ROLLBACK;                                          ← T2 used invalid data!

// Non-Repeatable Read: same query returns different data within one transaction
T1: SELECT balance FROM accounts WHERE id = 1;   ← returns 1000
T2: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
T1: SELECT balance FROM accounts WHERE id = 1;   ← returns 500 (changed!)

// Phantom Read: query returns different SET of rows
T1: SELECT COUNT(*) FROM orders WHERE status='pending';  ← returns 10
T2: INSERT INTO orders(status) VALUES('pending'); COMMIT;
T1: SELECT COUNT(*) FROM orders WHERE status='pending';  ← returns 11 (phantom!)

// Write Skew: each transaction reads data, makes decision, writes different data
// Doctor on-call example:
T1 (Dr. Alice): SELECT COUNT(*) FROM oncall WHERE on_duty=true; → 2 doctors
T2 (Dr. Bob):   SELECT COUNT(*) FROM oncall WHERE on_duty=true; → 2 doctors
T1: UPDATE oncall SET on_duty=false WHERE doctor='Alice';  ← goes off duty
T2: UPDATE oncall SET on_duty=false WHERE doctor='Bob';    ← goes off duty
// Both committed. Now 0 doctors on duty. Business rule violated!
// Fix: Serializable isolation or explicit SELECT FOR UPDATE

MVCC (Multi-Version Concurrency Control) — The Heart of Isolation

MVCC allows reads to not block writes and writes to not block reads by maintaining multiple versions of each row. Readers see a consistent snapshot of the database at transaction start time, regardless of concurrent modifications:

// PostgreSQL MVCC — every row has hidden system columns:
// xmin: transaction ID that created this row version
// xmax: transaction ID that deleted/updated this row (0 = still visible)
// ctid: physical location (page, offset)

-- See MVCC internals:
SELECT xmin, xmax, ctid, * FROM accounts WHERE id = 1;
--  xmin | xmax |  ctid  | id | balance
-- ------+------+--------+----+---------
--  1001 |    0 | (0,1)  |  1 |    1000   ← Current version (xmax=0 means live)

-- Transaction T2 (xid=1050) updates balance:
UPDATE accounts SET balance = 500 WHERE id = 1;

-- Now table has TWO versions of the same logical row:
--  xmin | xmax |  ctid  | id | balance
-- ------+------+--------+----+---------
--  1001 | 1050 | (0,1)  |  1 |    1000   ← Old version (xmax=1050, will be vacuumed)
--  1050 |    0 | (0,5)  |  1 |     500   ← New version (xmax=0, currently active)

-- Transaction T3 (xid=1030, started BEFORE T2 committed):
SELECT balance FROM accounts WHERE id = 1;
-- Sees xmin=1001 version (1001 < 1030 < 1050) → returns 1000
-- T3's snapshot: "I can see rows created by transactions < 1030
--                and not deleted by transactions < 1030"

-- Transaction T4 (xid=1060, started AFTER T2 committed):
SELECT balance FROM accounts WHERE id = 1;
-- Sees xmin=1050 version (1050 < 1060) → returns 500

MVCC Snapshot — How Transactions See the World

// PostgreSQL snapshot structure:
Snapshot = {
  xmin: 1030,           // Oldest active transaction at snapshot time
  xmax: 1055,           // Next transaction ID that will be assigned
  xip_list: [1035, 1042, 1048]  // Active (in-progress) txns at snapshot time
}

// Row version visibility rules (simplified):
function isVisible(row, snapshot) {
  // Row not yet created when snapshot taken:
  if (row.xmin >= snapshot.xmax) return false;
  // Row created by still-in-progress transaction:
  if (snapshot.xip_list.includes(row.xmin)) return false;
  // Row created by aborted transaction:
  if (isAborted(row.xmin)) return false;

  // Row deleted/updated check:
  if (row.xmax === 0) return true;                         // Not deleted
  if (row.xmax >= snapshot.xmax) return true;               // Deleted after snapshot
  if (snapshot.xip_list.includes(row.xmax)) return true;   // Deleter still in progress
  if (isAborted(row.xmax)) return true;                    // Deleter aborted

  return false; // Deleted by committed transaction before snapshot
}

VACUUM — Cleaning Up Dead MVCC Versions

// Dead row versions accumulate over time (UPDATE creates new version + marks old dead)
// VACUUM reclaims space from dead versions no longer needed by any snapshot

// PostgreSQL autovacuum monitors:
SELECT
  relname,
  n_dead_tup,          -- Dead tuple count
  n_live_tup,          -- Live tuple count
  round(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_pct,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Transaction ID Wraparound — the ultimate VACUUM deadline:
-- PostgreSQL uses 32-bit transaction IDs (4 billion values)
-- After 2 billion txns, IDs "wrap around" — old data appears to be in the FUTURE!
-- VACUUM FREEZE marks old rows with special "frozen" xmin (always visible)
-- Emergency VACUUM if age(datfrozenxid) > 2 billion → DB goes read-only!
-- Monitor: SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

D — Durability: Committed Data Survives Crashes

// Write-Ahead Log (WAL) / Redo Log — the durability mechanism
// Golden rule: WAL record must be flushed to disk BEFORE the data page

// PostgreSQL WAL flow for a single UPDATE:
// 1. Begin transaction
// 2. Fetch data page into shared_buffers (RAM)
// 3. Apply change to in-memory page (dirty page)
// 4. Write WAL record to WAL buffer (in RAM):
//    { lsn: 0/16B3210, xid: 1050, op: UPDATE, relation: accounts,
//      tuple: (0,1), old_values: {balance:1000}, new_values: {balance:500} }
// 5. COMMIT:
//    a. Write COMMIT WAL record
//    b. fsync() WAL to disk  ← CRITICAL: this is the durability guarantee
//    c. Return success to client
// 6. Background: checkpointer eventually writes dirty page to disk

// Crash recovery:
// On restart, find last checkpoint in pg_control
// Replay WAL records from checkpoint forward (REDO phase)
// Any uncommitted transactions → rolled back using undo information

// synchronous_commit settings (durability vs performance trade-off):
synchronous_commit = on          ← fsync WAL → guaranteed durable (default)
synchronous_commit = remote_write ← WAL sent to standby + OS buffer (not fsync'd)
synchronous_commit = local       ← only local WAL fsync (standby async)
synchronous_commit = off         ← no fsync → risk up to 200ms data loss on crash!
// off mode: ~3× faster writes. Risk: crash may lose last 200ms of commits.
// OK for: logging, analytics. NOT OK for: financial transactions.

Serializable Snapshot Isolation (SSI) — PostgreSQL's Implementation

// Serializable in PostgreSQL uses SSI (not 2-Phase Locking like MySQL InnoDB)
// SSI allows more concurrency than 2PL while providing full serializability

// SSI tracks "read-write anti-dependencies" (rw-antidependencies):
// If T1 reads data that T2 later writes, AND T2 reads data T1 later writes
// → Dangerous cycle → one transaction must be aborted (serialization failure)

SET default_transaction_isolation = 'serializable';

-- Back to doctor on-call example:
-- T1 reads oncall → creates rw-antidependency with T2's later write
-- T2 reads oncall → creates rw-antidependency with T1's later write
-- SSI detects cycle → aborts one transaction with:
-- ERROR: could not serialize access due to read/write dependencies among transactions
-- Application must retry the aborted transaction

-- Performance impact: ~10-15% overhead vs Repeatable Read
-- Much better than 2PL which holds locks for entire transaction duration

Why Replication — The Three Pillars

🛡️ High Availability
  • Primary fails → replica promoted in seconds
  • Eliminates single point of failure
  • Enables zero-downtime maintenance
  • Cross-AZ for hardware failure protection
📈 Read Scalability
  • Fan out reads across N replicas
  • N× read throughput without sharding
  • Analytical queries on replica (no impact on primary)
  • Geographic read replicas for low latency
💾 Durability
  • Data exists on multiple physical machines
  • Survive disk corruption, datacenter fire
  • Point-in-time recovery from WAL archive
  • Cross-region backup with async replication

WAL-Based Replication — How PostgreSQL Does It

Replication Modes — The Durability vs. Latency Spectrum

-- PostgreSQL synchronous_standby_names configurations:

-- 1. Fully Asynchronous (default)
synchronous_standby_names = ''
-- Primary commits immediately. Replica applies independently.
-- Risk: primary crash can lose last N WAL records not yet sent to replica
-- Typical lag: 10ms–seconds depending on network and replica load

-- 2. Synchronous — wait for ONE replica to ACK WAL write (not apply)
synchronous_standby_names = 'replica1'
-- Primary waits until replica1 has written WAL to its disk (not applied!)
-- Guarantees: WAL on at least 2 machines → safe against single disk failure
-- Does NOT guarantee: data applied (replica could crash after WAL write)
-- Added latency: 1 RTT to replica (e.g., same DC: +0.2ms, cross-AZ: +2ms)

-- 3. Remote Apply — wait for replica to APPLY (visible to queries)
synchronous_standby_names = 'FIRST 1 (replica1, replica2)'
-- application_name = 'replica1' with recovery_target_action = 'remote_apply'
-- Guarantees: data is QUERYABLE on replica before primary confirms commit
-- Use case: read-your-writes after writing to primary, reading from replica
-- Added latency: 1 RTT + replica apply time (~1–5ms)

-- 4. Quorum Synchronous (PostgreSQL 10+)
synchronous_standby_names = 'ANY 2 (replica1, replica2, replica3)'
-- Wait for any 2 of 3 replicas to ACK. Tolerates 1 replica failure.
-- Best balance of durability and availability

Replication Lag — Causes, Measurement, and Mitigation

-- Measure replication lag in PostgreSQL:
-- On PRIMARY:
SELECT
  application_name,
  state,
  sent_lsn,
  write_lsn,
  flush_lsn,
  replay_lsn,
  write_lag,        -- Time for replica to write WAL to disk
  flush_lag,        -- Time for replica to flush WAL to disk
  replay_lag,       -- Time for replica to apply WAL (data visible)
  sync_state        -- sync / async / potential / quorum
FROM pg_stat_replication;

-- On REPLICA:
SELECT
  now() - pg_last_xact_replay_timestamp() AS replication_delay,
  pg_is_in_recovery()                      AS is_replica,
  pg_last_wal_receive_lsn()                AS received_lsn,
  pg_last_wal_replay_lsn()                 AS replayed_lsn;

-- Causes of replication lag:
// 1. Network bandwidth: WAL stream saturates NIC (large bulk loads)
// 2. Replica I/O bound: replica disk can't keep up with WAL apply rate
// 3. Long-running queries on replica: hot standby conflicts
//    (replica must wait for standby_conflict_resolution timeout)
// 4. Large transactions: WAL for one txn can be GBs
// 5. Replica doing expensive index builds or autovacuum

// Mitigation strategies:
// - Dedicated replica NIC / network path
// - Faster replica disks (NVMe > SSD > HDD)
// - max_standby_streaming_delay: how long replica waits before canceling conflicting queries
// - hot_standby_feedback = on: replica tells primary what XIDs are active → prevents conflicts
// - Streaming replication slots: ensure primary retains WAL until replica catches up
// DANGER: replication slots without monitoring → WAL accumulates → disk full!

MySQL Binlog Replication — GTID-Based

-- MySQL replication uses Binary Log (binlog) instead of WAL
-- Three binlog formats:

-- 1. Statement-Based Replication (SBR):
-- Logs SQL statements. Compact. But non-deterministic functions (NOW(), RAND())
-- produce different results on replica!
-- DELETE FROM orders WHERE created_at < NOW() - INTERVAL 30 DAY
-- → Different rows deleted if NOW() differs by even 1 second!

-- 2. Row-Based Replication (RBR) — default since MySQL 5.7:
-- Logs actual row changes (before + after image). Deterministic.
-- Large updates produce large binlogs (UPDATE of 1M rows = 1M row images)

-- 3. Mixed: uses SBR for most statements, switches to RBR for unsafe ones

-- GTID (Global Transaction Identifier) — MySQL 5.6+:
-- Each transaction gets unique GTID: server_uuid:transaction_seq
-- Example: 3E11FA47-71CA-11E1-9E33-C80AA9429562:23

-- Benefits of GTID:
// - Automatic failover: new primary knows exactly which GTIDs each replica has
// - No binlog file + position needed: replicas auto-detect where to start
// - Circular replication detection: replica ignores its own GTIDs

-- GTID-based replication setup:
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='primary.db.internal',
  SOURCE_PORT=3306,
  SOURCE_AUTO_POSITION=1,     ← GTID auto-positioning (no file/pos needed!)
  SOURCE_SSL=1,
  SOURCE_CONNECT_RETRY=10;

START REPLICA;
SHOW REPLICA STATUS\G          ← shows Seconds_Behind_Source (lag metric)

Logical Replication — Fine-Grained Change Streaming

Physical replication (WAL shipping) replicates the entire database at the byte level. Logical replication decodes WAL into logical operations (INSERT/UPDATE/DELETE on specific tables), enabling selective replication and heterogeneous targets:

-- PostgreSQL Logical Replication — publisher/subscriber model:

-- On SOURCE database (publisher):
ALTER SYSTEM SET wal_level = logical;  ← Required: logical > replica > minimal

CREATE PUBLICATION my_pub
  FOR TABLE orders, customers, products;
-- OR: FOR ALL TABLES (entire database)
-- OR: FOR TABLE orders WHERE (status != 'archived')  ← row filter (PG 15+)

-- On TARGET database (subscriber):
CREATE SUBSCRIPTION my_sub
  CONNECTION 'host=source.db port=5432 dbname=myapp user=replicator password=secret'
  PUBLICATION my_pub
  WITH (
    copy_data = true,          ← Initial data sync (snapshot)
    synchronous_commit = off   ← Subscriber doesn't need to ack each WAL
  );

-- Use cases for logical replication:
// 1. Zero-downtime major version upgrade: PG 15 → PG 16 with logical rep
// 2. Selective table replication: replicate only orders table to analytics DB
// 3. Cross-database-engine: PostgreSQL → Kafka (Debezium CDC) → Elasticsearch
// 4. Multi-tenant: replicate tenant A's data to their dedicated database
// 5. Geographic distribution: replicate EU tables to EU database only

-- Change Data Capture (CDC) with Debezium (Kafka Connector):
// Debezium reads PostgreSQL logical replication slot
// Converts WAL records to Kafka messages (Avro or JSON):
{
  "op": "u",                    // u=update, c=create, d=delete, r=read(snapshot)
  "ts_ms": 1705000000000,
  "before": { "id": 123, "balance": 1000 },
  "after":  { "id": 123, "balance": 500  },
  "source": { "table": "accounts", "lsn": 23457890, "txId": 1050 }
}

Multi-Master Replication — Conflict Detection and Resolution

Multi-master (active-active) allows writes to multiple nodes simultaneously, enabling geographic write distribution. The critical challenge: the same row can be concurrently modified on two nodes — conflicts must be detected and resolved:

Multi-Master Conflict Scenario Node A (US-EAST) Node B (EU-WEST) │ │ T1: UPDATE products SET price=99 T2: UPDATE products SET price=89 WHERE id=42 WHERE id=42 │ │ │── replication ──────────────────► │ │ ◄─────────────────── replication──│ │ │ Both nodes detect CONFLICT for product id=42 Conflict: {node_a: price=99, node_b: price=89, same_xid_epoch} Resolution strategies: 1. Last-Write-Wins (LWW): compare timestamps → higher wins Risk: clock skew means wrong version wins 2. Application-defined: custom resolver function called on conflict 3. CRDT: data type designed to always merge correctly (counter, set) 4. Human review: conflict logged, manual resolution queue 
// Conflict resolution implementations:

// 1. Last-Write-Wins with Hybrid Logical Clocks (HLC)
// HLC = max(physical_time, logical_time) — monotonic even with clock skew
class HLC {
  tick() {
    const physical = Date.now();
    this.l = Math.max(physical, this.l + 1); // Ensure monotonic
    this.c = (this.l === physical) ? 0 : this.c + 1;
    return { l: this.l, c: this.c }; // (physical_ts, logical_counter)
  }
  receive(msg_ts) {
    this.l = Math.max(this.l, msg_ts.l, Date.now());
    this.c = (this.l === msg_ts.l) ? msg_ts.c + 1 : 0;
  }
}

// 2. Conflict-free Replicated Data Types (CRDTs)
// OR-Set (Observed-Remove Set) — concurrent add/remove of same element
class ORSet {
  // Each add gives element a unique tag
  // Remove: mark specific tags as removed
  // Concurrent add(x) on A + remove(x) on B:
  // B removes tags it knows about. A's new tags survive. → x remains.
  // "Add wins" semantics — predictable, conflict-free
}

// 3. Operational Transform (Google Docs approach)
// Each operation aware of concurrent operations
// Transform operation against concurrent ops before applying
// Insert(pos=5, char='a') concurrent with Delete(pos=3):
// Transform Insert → Insert(pos=4, char='a') after accounting for deletion

Read-Your-Writes Consistency — Routing Strategies

With async replication, a user writes to the primary and immediately reads from a replica — but the replica hasn't caught up yet. The user sees their own write disappear. Solutions:

// Strategy 1: Route reads to primary for 1 second after write
async function getUser(userId, context) {
  const lastWriteTime = context.getLastWriteTime(userId);
  const useReplica = !lastWriteTime ||
                     (Date.now() - lastWriteTime) > 1000; // 1s buffer

  return useReplica
    ? replicaPool.query('SELECT * FROM users WHERE id=$1', [userId])
    : primary.query('SELECT * FROM users WHERE id=$1', [userId]);
}

// Strategy 2: Send client a "read token" (LSN) after write
// Client includes token in subsequent reads
// Replica refuses to serve read if its LSN < token (waits or redirects)
// AWS Aurora PostgreSQL implements this as "read-your-writes" option

-- PostgreSQL: route read to specific replica only if it's caught up
-- After write, server returns current WAL LSN:
SELECT pg_current_wal_lsn();  -- Returns '0/16B3210'

-- Client sends LSN with next read request
-- Replica checks if it has applied at least this LSN:
SELECT pg_last_wal_replay_lsn() >= '0/16B3210'::pg_lsn;
-- If false: wait or redirect to primary

// Strategy 3: Monotonic reads — sticky sessions to same replica
// User always routed to same replica via session cookie or consistent hash(user_id)
// Replica lag affects all users equally but no backwards-in-time reads within session

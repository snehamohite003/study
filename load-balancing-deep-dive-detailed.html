1. What Load Balancing Means

Load balancing is the process of distributing incoming traffic or work across multiple resources so that the system uses capacity efficiently and avoids overloading a single backend. These resources may be web servers, API servers, worker nodes, cache nodes, or even databases in read-heavy scenarios.

At a practical level, load balancing is what allows many separate machines to behave like one larger service. Users do not need to know which backend machine handled their request, because the load balancer acts as the entry point and routing layer.

2. Why Load Balancing Matters

If traffic is not distributed properly, some instances become overloaded while others remain idle. This causes higher latency, request failures, poor capacity utilization, and reduced availability even though total infrastructure may still have unused resources.

Load balancing matters because horizontal scaling only becomes useful when traffic can actually be spread across the added capacity. Without it, adding more servers does not translate into real throughput improvement.

3. Core Idea Behind Load Balancing

The purpose of load balancing is not merely to split traffic equally, but to route work intelligently so that healthy resources are used well, overloaded resources are protected, and failed resources are avoided.

This idea is important because real systems do not receive uniform requests. Some requests are small and fast, while others are expensive and long-lived. Good load balancing must consider real traffic behavior, not just request count.

4. Problems Solved by Load Balancing

Load balancing solves several foundational problems in distributed systems. It prevents traffic concentration on one node, enables failover when servers die, allows systems to scale out by adding more instances, and hides backend complexity from clients.

It also makes traffic management policy-driven. Instead of clients manually choosing servers, the system can enforce routing strategies such as sending specific paths to specific services, preferring healthy instances, or steering traffic to low-latency regions.

5. Main Components of a Load Balancing System

5.1 Client

The client is the source of traffic, such as a browser, mobile app, or another backend service. The client usually sees only the public endpoint of the load balancer and does not need to know how many backend servers exist behind it.

5.2 Load Balancer

The load balancer is the control point that receives traffic and decides where it should go. It applies routing logic, checks backend health, and often handles additional tasks such as TLS termination, connection reuse, and observability.

5.3 Backend Servers

Backends are the actual servers or services doing the work. They may be application instances, web servers, API nodes, or even specialized services such as image processors or recommendation engines.

5.4 Health Check Mechanism

The health-check system determines whether a backend is fit to receive traffic. This is critical because a load balancer that cannot distinguish between healthy and unhealthy nodes will continue routing requests to failing instances.

5.5 Routing Policy / Algorithm

The routing policy determines how traffic is distributed. Different algorithms work better for different workloads, and the wrong algorithm can produce significant imbalance even when the infrastructure looks healthy on paper.

5.6 Connection Management

Load balancers often maintain and reuse connections to backends. This affects efficiency, latency, and traffic distribution, especially in protocols where one connection can carry many requests over time.

6. How Load Balancing Works Behind the Scenes

When a client sends traffic to a service, it usually connects to a single public endpoint exposed by the load balancer. The load balancer accepts the connection or request, identifies which backends are currently healthy, applies its balancing policy, and forwards the traffic accordingly.

Behind the scenes, this process is continuous rather than static. Backend health changes, traffic patterns shift, some nodes slow down, and some nodes recover. The load balancer must constantly make new decisions based on current system state.

  1. Client sends request to the load balancer endpoint.
  2. Load balancer receives the traffic and inspects the necessary metadata.
  3. Health-check state is consulted to filter out unhealthy backends.
  4. A balancing algorithm selects an eligible backend.
  5. Traffic is forwarded to that backend.
  6. Response returns through the balancer or directly depending on architecture.
  7. Metrics, failures, and latencies continue to update routing decisions over time.

7. Types of Load Balancing

7.1 Layer 4 Load Balancing

Layer 4 load balancing operates at the transport layer, which means it makes decisions using network-level information such as IP addresses, ports, and protocol type. It does not need to understand the internal structure of HTTP requests to forward traffic.

This makes Layer 4 balancing fast and efficient, especially for high-throughput systems or protocols other than HTTP. However, because it does not inspect application data, it cannot route based on URL path, headers, or cookies.

7.2 Layer 7 Load Balancing

Layer 7 load balancing operates at the application layer and understands protocol details such as HTTP method, path, host header, cookies, and custom headers. This allows the system to route different request types to different backend services.

For example, the balancer can send /images traffic to image servers and /checkout traffic to checkout servers. This flexibility makes L7 balancing very powerful, but it also increases CPU cost and implementation complexity.

7.3 DNS-Based Load Balancing

DNS-based load balancing distributes traffic by returning different IP addresses for the same domain name. This is often used for regional traffic steering, disaster recovery, and coarse global distribution.

Its limitation is that DNS responses are cached. Once a client or resolver caches an answer, the system loses real-time control over where that client will connect until the DNS TTL expires.

7.4 Global vs Local Load Balancing

Global load balancing decides which region or datacenter should receive the traffic. It is used for geographic routing, regional failover, and latency-aware traffic steering.

Local load balancing happens inside a region, cluster, or datacenter and distributes traffic among the servers available in that local environment. Both are often used together in large systems.

8. Core Load Balancing Algorithms

8.1 Round Robin

Round robin sends requests to backends in simple rotation. If there are three servers, requests are assigned A, then B, then C, then back to A again.

This algorithm is easy to implement and works reasonably well when backend capacity is similar and request cost is fairly uniform. It performs poorly when some requests are much more expensive than others.

8.2 Weighted Round Robin

Weighted round robin is an extension of round robin where stronger or more capable backends receive more traffic than weaker ones. For example, a server with twice the CPU and memory may be assigned a larger weight.

This is useful in mixed fleets where all servers are not equal. However, it still assumes traffic cost is predictable enough that weighted distribution will produce balanced resource usage.

8.3 Least Connections

Least-connections routing sends traffic to the backend that currently has the fewest active connections. This is often more effective than round robin when connection durations vary significantly.

The limitation is that the number of open connections is only a rough approximation of load. One connection may be idle while another may carry a heavy stream of expensive requests.

8.4 Least Response Time / Latency-Based Routing

This strategy prefers backends that are currently responding faster. The idea is that lower response time may indicate lower load or better health.

While useful, it can also create instability if the balancer reacts too aggressively to short-term spikes. Without smoothing or careful thresholds, traffic may oscillate rapidly between servers.

8.5 Hash-Based Routing

Hash-based routing uses a key such as client IP, session ID, or user ID to consistently map a request to a backend. This is useful when some level of locality or affinity is needed.

It can reduce cache misses and support session persistence, but it may also create hotspots if some keys receive disproportionately high traffic.

8.6 Random with Power of Two Choices

In this method, the balancer randomly selects two candidate backends and sends the request to the less loaded one. Although simple, this often performs much better than pure random selection.

This algorithm is respected in distributed systems because it achieves strong balancing behavior with low coordination cost and little complexity.

9. Session Persistence and Sticky Sessions

Sticky sessions mean that repeated requests from the same client are sent to the same backend. This is often done when the backend holds session state in local memory and would otherwise lose continuity across requests.

Although sticky sessions can simplify legacy systems, they usually hurt scalability and resilience. They create uneven traffic distribution, make failover harder, and couple specific users to specific machines.

In modern scalable systems, it is usually better to externalize shared state into Redis, a database, or a distributed session store so that any instance can handle any request.

10. Health Checks

Health checks allow the load balancer to determine whether a backend is fit to receive traffic. This is a critical function because traffic should not continue flowing to a server that is technically alive but practically broken.

There are different levels of health checks. A shallow check may only verify that a TCP connection can be opened, while a deeper check may confirm that the application can reach the database, cache, or other critical dependencies.

A common mistake is to rely on health checks that are too shallow. In that case, unhealthy instances continue to receive real traffic and user-visible failure persists despite “green” status in infrastructure dashboards.

11. TLS Termination

TLS termination at the load balancer means the balancer handles the TLS handshake, decrypts incoming HTTPS traffic, and then forwards the request to backends. This centralizes certificate management and reduces cryptographic overhead on application servers.

It also enables Layer 7 routing because the balancer can inspect HTTP request details only after the encrypted traffic has been decrypted. The tradeoff is that internal traffic may need re-encryption if the internal network is not fully trusted.

12. Traffic Distribution Challenges

Real traffic is rarely uniform. Some requests are cheap, some are expensive, some connections are short, some remain open for a long time, and some users generate far more traffic than others.

This means a load balancer cannot assume that “same number of requests” equals “same amount of work.” In production, imbalance often comes from request cost variation, connection reuse, traffic hotspots, retries, and skewed user behavior rather than from the algorithm alone.

13. Interview-Level Important Load Balancing Concepts Explained Deeply

13.1 Why Load Balancing Is Essential for Horizontal Scaling

Horizontal scaling means adding more backend instances so total system capacity can grow. However, this additional capacity is useful only if incoming traffic is actually distributed across those new instances.

Load balancing is the mechanism that converts multiple machines into one logical service. Without it, the architecture may look scalable in theory, but real traffic may still pile onto a few nodes and waste the rest of the infrastructure.

13.2 L4 vs L7 Load Balancing

Layer 4 balancing is connection-oriented and focuses on transport-level information such as IPs and ports. It is generally faster and simpler because it does not need to understand the full application payload.

Layer 7 balancing is request-aware and can make smarter routing decisions using HTTP metadata. It is more flexible and useful for modern API-based architectures, but comes with more parsing overhead and operational complexity.

13.3 Load Balancing Is Not Just Equal Distribution

A common misunderstanding is that good load balancing means every server gets the same number of requests. In real systems, that is often not the goal because request cost can vary wildly.

One server receiving fewer but very expensive requests may be more overloaded than another receiving many lightweight requests. Good load balancing tries to avoid overload and improve overall efficiency, not just equalize counters.

13.4 Request-Level vs Connection-Level Balancing

In some systems, each request can be routed independently, which gives the balancer fine-grained control over traffic distribution. In other systems, routing happens at connection level, so multiple requests continue using the same assigned backend.

This distinction matters because persistent connections can create imbalance. One connection may carry hundreds of requests while another carries only a few, so connection count alone may not reflect real backend load.

13.5 Health Checks and Why “Alive” Is Not Enough

A server process being alive does not mean it is healthy enough to serve user traffic. It may still be unable to access the database, overwhelmed by CPU saturation, or stuck in a degraded state where requests fail or time out.

That is why strong load balancer design includes meaningful health checks. Interviewers often look for this point because many real incidents happen when instances are technically up but operationally broken.

13.6 Sticky Sessions and Their Tradeoffs

Sticky sessions can make stateful applications easier to run because the same user keeps returning to the same backend instance. This reduces the need to externalize session state in the short term.

However, sticky sessions create fragility. They make traffic less even, reduce the effectiveness of autoscaling, complicate failover, and can create hotspots when some users are much heavier than others.

13.7 Load Balancing and Availability

Load balancing is a major availability mechanism because it allows failed or degraded backends to be removed from traffic flow while healthy ones continue serving users. In this way, one backend failure does not have to become a user-visible outage.

However, this works only if failure detection is good and healthy replacements exist. A load balancer cannot preserve availability if all backends are unhealthy or if the balancer itself becomes the new single point of failure.

13.8 TLS Termination and Architectural Impact

TLS termination at the balancer simplifies certificate management and allows centralized policy enforcement such as header inspection, routing rules, and security filtering. It also reduces cryptographic work on the application layer.

But it changes trust boundaries. Once traffic is decrypted at the balancer, engineers must decide whether to send plaintext internally or re-encrypt traffic to preserve security inside the infrastructure.

13.9 Overload Protection and Backpressure

A load balancer can do more than route traffic. It can also become part of the system’s overload-control mechanism by shedding load, capping concurrency, rejecting excess traffic, or prioritizing critical requests.

This is important because blindly forwarding all traffic to already struggling backends can make the whole platform collapse. In high-scale systems, controlled rejection is often better than uncontrolled failure.

13.10 Hotspots and Uneven Traffic

Some traffic patterns create hotspots even when the balancing policy is reasonable. A specific user, a specific path, or a specific session can generate disproportionately expensive or high-volume traffic and overload one part of the fleet.

This is why observability is essential. Engineers must measure request distribution, latency, and backend saturation rather than assuming that the balancing algorithm is working perfectly just because traffic is flowing.

13.11 Global Load Balancing

Global load balancing routes traffic across regions or datacenters rather than just across local servers. It is used to reduce geographic latency, improve resilience to regional failures, and spread traffic across major deployment zones.

Unlike local balancing, global balancing is often coarser and affected by DNS caching, anycast routing behavior, and WAN latency. It is powerful, but it offers less instant control than local request routing inside a datacenter.

13.12 Client-Side vs Server-Side Load Balancing

In server-side load balancing, a dedicated balancer chooses the backend and clients remain simple. This centralizes routing logic and is common in web architectures and managed infrastructure.

In client-side load balancing, the client or calling service chooses the backend from a discovered list of instances. This can reduce central bottlenecks and improve flexibility, but requires good service discovery and shifts more complexity to the caller.

13.13 Observability in Load Balancing

Good load balancing requires visibility into real traffic behavior. Teams need to know how requests are distributed, which backends have higher error rates, which servers are slow, and whether retries or connection patterns are causing hidden imbalance.

Without observability, a system may look healthy from a high level while one subset of servers is overloaded, one region is unhealthy, or one path is triggering expensive downstream behavior.

13.14 Load Balancer as a Potential Single Point of Failure

Although load balancers improve resilience behind them, the load balancer itself can become a critical failure point if not designed redundantly. If it is the only ingress path and it fails, the entire service may become unreachable.

That is why production systems usually use highly available managed load balancers, redundant balancer nodes, or global routing layers that can fail over between load-balancing endpoints.

13.15 Algorithm Selection Depends on Workload

There is no universally best load balancing algorithm. The best choice depends on whether requests are uniform, whether sessions are long-lived, whether backends differ in capacity, and whether locality or affinity matters.

In interviews, strong answers explain why a particular algorithm fits a given workload instead of just listing algorithm names. The “why” matters more than memorization.

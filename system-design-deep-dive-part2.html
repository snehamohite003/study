HTTP Internals — How a Request Actually Works

HTTP is a stateless, text-based application-layer protocol running over TCP. Every interaction follows a strict request/response cycle. The raw bytes on the wire for HTTP/1.1:

── Client → Server (Request) ──────────────────────────────────────
GET /api/users/42 HTTP/1.1\r\n
Host: api.example.com\r\n
Accept: application/json\r\n
Authorization: Bearer eyJhbGci...\r\n
Connection: keep-alive\r\n
\r\n                          ← Blank line = end of headers
                              ← (no body for GET)

── Server → Client (Response) ─────────────────────────────────────
HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Content-Length: 87\r\n
Cache-Control: max-age=300\r\n
X-Request-ID: abc-123\r\n
\r\n
{"id":42,"name":"Alice","email":"alice@example.com","role":"admin"}

── Problems with HTTP/1.1 ──────────────────────────────────────────
Head-of-line blocking: requests queue behind a slow response
No header compression: headers repeated verbatim on every request
6 parallel TCP connections per origin (browser workaround)
No server push: client must request every resource individually

HTTPS = HTTP + TLS — The TLS Layer

HTTPS doesn't change HTTP at all. It wraps the entire HTTP session inside a TLS (Transport Layer Security) tunnel. TLS provides three guarantees:

  • Confidentiality: All data encrypted with symmetric keys (AES-GCM). Eavesdroppers see only ciphertext.
  • Integrity: HMAC/AEAD ensures data wasn't modified in transit (no tampering).
  • Authentication: X.509 certificates prove the server is who it claims to be (via PKI chain of trust).

TLS 1.3 Handshake — Step by Step Internals

TLS 1.3 (RFC 8446, 2018) dramatically simplified the handshake from TLS 1.2's 2-RTT to 1-RTT (and 0-RTT for resumption):

TLS 1.3 Full Handshake (1-RTT) Client Server │ │ │──── ClientHello ─────────────────────────────►│ │ supported_versions: [TLS 1.3] │ │ supported_groups: [x25519, P-256] │ │ key_share: [x25519 public key ephemeral] │ │ cipher_suites: [AES_256_GCM_SHA384, ...] │ │ random: 32 bytes │ │ │ │◄─── ServerHello ──────────────────────────────│ │ selected_version: TLS 1.3 │ │ key_share: [x25519 server public key] │ │ selected_cipher: AES_256_GCM_SHA384 │ │ random: 32 bytes │ │ │ │ ← Both sides now compute shared secret via ECDH → │ shared_secret = x25519(client_priv, server_pub) │ = x25519(server_priv, client_pub) (same result!) │ Derive: handshake_key, application_key (HKDF) │ │ │◄─── {Certificate} ────────────────────────────│ ← Encrypted! │◄─── {CertificateVerify} ──────────────────────│ Sig over handshake │◄─── {Finished} ───────────────────────────────│ HMAC of transcript │ │ │──── {Finished} ─────────────────────────────►│ │ │ │◄═══ Encrypted Application Data (HTTP) ═══════►│ ← Only 1 RTT!

Key Exchange — Elliptic Curve Diffie-Hellman (ECDH) Internals

Neither party sends the session key over the wire. They exchange public keys, and each independently computes the same shared secret — a one-way mathematical operation based on elliptic curve discrete logarithm hardness:

// x25519 ECDH — conceptually:
// Curve25519: y² = x³ + 486662x² + x (mod 2²⁵⁵ - 19)

// Client generates:
client_private = random_256bit_scalar()       // Never sent!
client_public  = client_private × G           // G = curve base point

// Server generates:
server_private = random_256bit_scalar()       // Never sent!
server_public  = server_private × G

// Exchange public keys. Both compute:
shared_secret  = client_private × server_public
               = client_private × (server_private × G)
               = server_private × (client_private × G)
               = server_private × client_public
// Elliptic curve multiplication is associative → same result both sides
// Attacker sees client_public + server_public but cannot compute secret
// (Discrete log problem — computationally infeasible)

// Key derivation (HKDF — HMAC-based Extract-and-Expand):
handshake_secret = HKDF-Extract(early_secret, shared_secret)
client_handshake_key = HKDF-Expand(handshake_secret, "c hs traffic", 32)
server_handshake_key = HKDF-Expand(handshake_secret, "s hs traffic", 32)
application_key      = HKDF-Expand(master_secret,    "c ap traffic", 32)

Perfect Forward Secrecy (PFS)

TLS 1.3 mandates ephemeral key exchange (ECDHE). The server generates a new private key for every handshake and discards it after. Even if an attacker records all traffic today and obtains the server's long-term private key years later, they cannot decrypt past sessions — the ephemeral keys are gone.

🚨 TLS 1.2 Weakness — Why You Must Disable It TLS 1.2 allowed RSA key exchange (no PFS), weak cipher suites (RC4, 3DES, CBC mode — vulnerable to BEAST, LUCKY13, POODLE attacks), and required 2-RTT handshake. Always enforce TLS 1.3 minimum. TLS 1.0/1.1 are deprecated by all major browsers since 2020.

Mutual TLS (mTLS) — Two-Way Authentication

Standard TLS only authenticates the server. mTLS requires the client to also present a certificate, authenticating both parties. Used in service meshes (Istio), zero-trust networks, and B2B APIs:

// mTLS adds steps to standard handshake:
// Server sends: CertificateRequest (after ServerHello)
// Client sends: its Certificate + CertificateVerify
// Server validates client cert against its trusted CA list

// Nginx mTLS config:
server {
  ssl_client_certificate /etc/nginx/client-ca.crt; # CA that signed client certs
  ssl_verify_client on;                             # Require client cert
  ssl_verify_depth 2;                               # Allow intermediate CAs

  # Access client cert info in app:
  proxy_set_header X-Client-Cert-Subject $ssl_client_s_dn;
  proxy_set_header X-Client-Cert-Fingerprint $ssl_client_fingerprint;
}

HTTP/2 — Multiplexing Over a Single TCP Connection

HTTP/2 is a binary framing protocol. It solves HTTP/1.1's head-of-line blocking by multiplexing multiple logical streams over one TCP connection:

HTTP/1.1 vs HTTP/2 — Connection Model HTTP/1.1 (6 parallel TCP connections per origin): TCP-1: Request A ─────────────────────────► Response A TCP-2: Request B ─────────────────────────► Response B TCP-3: Request C ──────(slow)──────────────────► Response C TCP-4: Request D ─────────────────────────► Response D ← Each connection has TCP overhead, TLS overhead, HOL blocking within HTTP/2 (1 TCP connection, multiple streams): TCP-1: Stream 1: HEADERS frame → DATA frame(s) → Response A Stream 3: HEADERS frame → DATA frame(s) → Response B Stream 5: HEADERS frame ──────────────────────────────► Response C (slow, doesn't block others!) Stream 7: HEADERS frame → DATA frame(s) → Response D ← Frames interleaved on same connection. Each stream independent.

HTTP/2 Frame Types (Binary Protocol)

// HTTP/2 Frame structure (9-byte header):
+-----------------------------------------------+
|                Length (24 bits)               |
+---------------+---------------+---------------+
|  Type (8 bit) | Flags (8 bit) |
+-+-------------+---------------+
|R|          Stream ID (31 bit) |
+-----------------------------------------------+
|             Frame Payload                     |
+-----------------------------------------------+

// Frame Types:
// DATA        (0x0): HTTP body chunks
// HEADERS     (0x1): HTTP headers (HPACK-compressed)
// PRIORITY    (0x2): Stream dependency/weight for server prioritization
// RST_STREAM  (0x3): Abort a stream without closing connection
// SETTINGS    (0x4): Connection parameters (initial window size, max streams)
// PUSH_PROMISE(0x5): Server push — "I'll send /style.css before you ask"
// PING        (0x6): Keep-alive / RTT measurement
// GOAWAY      (0x7): Graceful connection shutdown
// WINDOW_UPDATE(0x8): Flow control — increase receive window

HPACK Header Compression

HTTP/2 compresses headers using HPACK (RFC 7541). Both client and server maintain a dynamic header table. Common headers (Host, Content-Type, Authorization) are sent as 1-byte index references instead of full strings:

// First request: send full headers, build table
:method: GET               → index 2  (static table)
:path: /api/users          → index 5 + literal "/api/users"
:authority: example.com    → index 1 + literal "example.com"
authorization: Bearer xyz  → literal (added to dynamic table at index 62)

// Second request to same server:
:method: GET               → 0x82   (1 byte! references index 2)
:path: /api/orders         → 0x85 + "orders"
:authority: example.com    → 0x41   (1 byte! cached in dynamic table)
authorization: Bearer xyz  → 0xBE   (1 byte! cached at index 62)
// Headers reduced from ~200 bytes to ~10 bytes!

HTTP/3 — HTTP over QUIC (UDP-based)

HTTP/2 still has TCP-level head-of-line blocking: if one TCP segment is lost, all HTTP/2 streams stall waiting for retransmission. HTTP/3 eliminates TCP entirely, using QUIC (Quick UDP Internet Connections):

Protocol Stack Comparison HTTP/1.1 & HTTP/2: HTTP/3: ┌─────────────────┐ ┌─────────────────┐ │ HTTP/1.1│HTTP/2│ │ HTTP/3 │ ├─────────────────┤ ├─────────────────┤ │ TLS 1.3 │ │ QUIC │ ← TLS 1.3 built-in! ├─────────────────┤ ├─────────────────┤ │ TCP │ │ UDP │ ├─────────────────┤ ├─────────────────┤ │ IP │ │ IP │ └─────────────────┘ └─────────────────┘ QUIC advantages: • 0-RTT connection on resumption (vs 3-RTT for TLS 1.2 over TCP) • Independent streams — packet loss only blocks one stream, not all • Connection migration: change IP (WiFi → 4G) without reconnecting (QUIC uses Connection ID, not IP:port tuple like TCP) • Built-in TLS 1.3 — no separate TLS handshake round trip

JWT Authentication — Internal Validation Flow

JSON Web Tokens (RFC 7519) are the most common API authentication mechanism. A JWT is three Base64URL-encoded sections separated by dots:

// JWT Structure: header.payload.signature
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9          ← Header
.eyJzdWIiOiJ1c3IxMjMiLCJyb2xlIjoiYWRtaW4iLCJleHAiOjE3MDA=  ← Payload
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature

// Decoded Header:
{ "alg": "RS256", "typ": "JWT", "kid": "key-id-2024" }

// Decoded Payload (claims):
{
  "sub": "usr123",          // Subject — user ID
  "iss": "auth.example.com",// Issuer
  "aud": "api.example.com", // Audience — intended recipient
  "exp": 1700000000,        // Expiry (Unix timestamp)
  "iat": 1699996400,        // Issued At
  "jti": "uuid-abc-123",    // JWT ID — for replay prevention
  "role": "admin",
  "scope": "read:users write:orders"
}

// Signature (RS256 = RSA + SHA-256):
signature = RSA_Sign(
  private_key,
  SHA256(base64url(header) + "." + base64url(payload))
)

// API Gateway validation (NO database call needed!):
async function validateJWT(token) {
  const [headerB64, payloadB64, sigB64] = token.split('.');
  const header = JSON.parse(base64UrlDecode(headerB64));

  // Fetch public key from JWKS endpoint (cached!)
  const publicKey = await jwksCache.getKey(header.kid);

  // 1. Verify signature (cryptographic)
  const valid = RSA_Verify(publicKey, sigB64, `${headerB64}.${payloadB64}`);
  if (!valid) throw new Error('Invalid signature');

  const payload = JSON.parse(base64UrlDecode(payloadB64));

  // 2. Validate claims
  if (payload.exp < Date.now() / 1000) throw new Error('Token expired');
  if (payload.iss !== 'auth.example.com') throw new Error('Wrong issuer');
  if (payload.aud !== 'api.example.com')  throw new Error('Wrong audience');

  return payload; // Trust established — no DB lookup needed!
}

Rate Limiting Algorithms — In Depth

Sliding Window Log Algorithm

// Stores timestamp of every request in a sorted set (Redis ZSET)
async function slidingWindowLog(clientId, limit, windowMs) {
  const key = `rl:${clientId}`;
  const now = Date.now();
  const windowStart = now - windowMs;

  // Atomic Redis operations via pipeline:
  await redis.pipeline()
    .zremrangebyscore(key, 0, windowStart)   // Remove expired timestamps
    .zadd(key, now, `${now}-${uuid()}`)      // Add current request
    .expire(key, windowMs / 1000)             // Auto-cleanup
    .exec();

  const count = await redis.zcard(key);       // Count in window

  if (count > limit) {
    const oldest = await redis.zrange(key, 0, 0, 'WITHSCORES');
    const retryAfter = (oldest[1] + windowMs - now) / 1000;
    throw { status: 429, retryAfter }; // HTTP 429 Too Many Requests
  }
  // Accurate but high memory — stores every request timestamp
}

Sliding Window Counter (Memory Efficient)

// Approximates sliding window using two fixed-window counters:
// current_window_count + (previous_window_count × overlap_ratio)

function slidingWindowCounter(clientId, limit, windowSec) {
  const now = Math.floor(Date.now() / 1000);
  const currWindow = Math.floor(now / windowSec);   // Current minute bucket
  const prevWindow = currWindow - 1;               // Previous minute bucket
  const elapsed = now % windowSec;                  // Seconds into current window
  const overlap = 1 - (elapsed / windowSec);       // Fraction of prev window in range

  const prevCount = await redis.get(`rl:${clientId}:${prevWindow}`) || 0;
  const currCount = await redis.incr(`rl:${clientId}:${currWindow}`);

  const estimated = prevCount * overlap + currCount;
  return estimated > limit; // true = rate limited
  // Only 2 integers in Redis vs. N timestamps. ~99% accurate.
}

Circuit Breaker

Why Circuit Breakers Exist — The Cascading Failure Problem

Without a circuit breaker, a slow downstream service causes threads/connections to pile up waiting. This exhausts the thread pool of the caller, making it slow too, causing its callers to pile up — a cascading failure that takes down the entire system:

Cascading Failure Without Circuit Breaker PaymentService DB is slow (800ms per query instead of 10ms) │ ▼ PaymentService threads fill up (all waiting for DB) PaymentService response time: 800ms+ → timeouts │ ▼ OrderService threads fill up (all waiting for PaymentService) OrderService response time: 800ms+ → timeouts │ ▼ API Gateway connection pool exhausted All requests to entire platform timeout │ ▼ 💥 Total outage — one slow DB brought down everything With Circuit Breaker: After threshold failures → Circuit OPENS OrderService gets instant error (0ms) → returns fallback response PaymentService gets breathing room to recover OrderService degraded (no payment) but operational ✓

Circuit Breaker State Machine — Deep Dive

Count-Based Sliding Window

class CircuitBreaker {
  constructor(config) {
    this.state = 'CLOSED';

    // Sliding window: ring buffer of last N call outcomes
    this.window = new RingBuffer(config.windowSize);  // e.g., 100 calls
    this.failureRateThreshold = config.failureRateThreshold; // e.g., 50%
    this.slowCallRateThreshold = config.slowCallRateThreshold; // e.g., 80%
    this.slowCallDurationThreshold = config.slowCallDuration; // e.g., 2000ms
    this.waitDurationInOpenState = config.waitDuration; // e.g., 30s
    this.permittedCallsInHalfOpen = config.halfOpenCalls; // e.g., 5
    this.minimumCalls = config.minimumCalls; // e.g., 10 (don't open on 1 failure)

    this.halfOpenCallCount = 0;
    this.openedAt = null;
  }

  async execute(fn, fallback) {
    switch (this.state) {
      case 'OPEN':
        if (Date.now() - this.openedAt > this.waitDurationInOpenState) {
          this.transitionTo('HALF_OPEN');
        } else {
          return fallback ? fallback() : Promise.reject(new Error('Circuit OPEN'));
        }
        // fallthrough to HALF_OPEN

      case 'HALF_OPEN':
        if (this.halfOpenCallCount >= this.permittedCallsInHalfOpen) {
          return fallback ? fallback() : Promise.reject(new Error('Circuit HALF_OPEN full'));
        }
        this.halfOpenCallCount++;
        break;

      case 'CLOSED': break;
    }

    const start = Date.now();
    try {
      const result = await fn();
      this.recordSuccess(Date.now() - start);
      return result;
    } catch (err) {
      this.recordFailure(Date.now() - start);
      throw err;
    }
  }

  recordSuccess(duration) {
    const isSlow = duration > this.slowCallDurationThreshold;
    this.window.push({ success: !isSlow, slow: isSlow });
    this.evaluate();
  }

  recordFailure(duration) {
    this.window.push({ success: false, slow: false });
    this.evaluate();
  }

  evaluate() {
    if (this.window.size() < this.minimumCalls) return; // Not enough data

    const stats = this.window.stats();
    const failureRate = stats.failures / stats.total * 100;
    const slowRate    = stats.slow / stats.total * 100;

    if (this.state === 'HALF_OPEN') {
      if (failureRate > this.failureRateThreshold || slowRate > this.slowCallRateThreshold) {
        this.transitionTo('OPEN');   // Still failing — reopen
      } else if (this.halfOpenCallCount >= this.permittedCallsInHalfOpen) {
        this.transitionTo('CLOSED'); // Recovered — close!
      }
    } else if (this.state === 'CLOSED') {
      if (failureRate > this.failureRateThreshold || slowRate > this.slowCallRateThreshold) {
        this.transitionTo('OPEN');   // Threshold breached — open!
      }
    }
  }

  transitionTo(newState) {
    this.state = newState;
    if (newState === 'OPEN')       { this.openedAt = Date.now(); this.window.reset(); }
    if (newState === 'HALF_OPEN')  { this.halfOpenCallCount = 0; this.window.reset(); }
    if (newState === 'CLOSED')     { this.halfOpenCallCount = 0; this.window.reset(); }
    metrics.emit('circuit_breaker_state', { state: newState });
  }
}

Bandwidth vs. Throughput vs. Latency — Precise Definitions

Bandwidth
  • Maximum theoretical data transfer rate of a link
  • A physical/layer-2 property of the medium
  • Measured in bits per second (Mbps, Gbps)
  • Example: 1 Gbps Ethernet NIC
  • You can never exceed this — it's the pipe diameter
Throughput
  • Actual data successfully transferred per unit time
  • Always ≤ bandwidth (overhead, retransmissions, protocol headers)
  • Affected by: packet loss, RTT, congestion, CPU limits
  • Example: 800 Mbps on a 1 Gbps link
  • This is what your application actually gets

Latency Components — Where Time Is Spent

Total Request Latency = Σ of all these components:

1. Propagation Delay   = distance / (speed_of_light × 0.66)
                       // Fiber: ~66% of light speed
                       // NYC → London (5570km): 5570000 / (3×10⁸×0.66) ≈ 28ms one-way

2. Transmission Delay  = packet_size / link_bandwidth
                       // 1500 byte MTU / 1Gbps = 12 microseconds

3. Processing Delay    = time to process packet at each hop (router lookup, NAT)
                       // Typically 1-10 microseconds per router

4. Queuing Delay       = time packet waits in router buffer
                       // 0 when uncongested, can be 100s of ms when congested!
                       // Bufferbloat: oversized router buffers cause enormous queuing delays

5. TLS Handshake       = 1 RTT (TLS 1.3) or 2 RTT (TLS 1.2)
6. DNS Resolution      = 0-200ms (depends on TTL, cache hit rate)
7. TCP Slow Start      = initial cwnd=10 segments, grows per RTT
8. Server Processing   = time to execute application code, query DB

TCP Congestion Control — The Bandwidth Manager

TCP automatically throttles transmission rate based on network congestion signals. Understanding this is critical for optimizing high-throughput services:

// TCP Congestion Window (cwnd) controls in-flight bytes
// Throughput = cwnd / RTT  (simplified)

// Phase 1: Slow Start
cwnd = 10 segments (initial window — IW10 since RFC 6928)
for each ACK received:
  cwnd += 1 MSS    // Exponential growth! Doubles each RTT
  // RTT 1: 10→20, RTT 2: 20→40, RTT 3: 40→80...

// When cwnd reaches ssthresh (slow start threshold):
// Phase 2: Congestion Avoidance
for each RTT:
  cwnd += 1 MSS    // Linear growth (additive increase)

// Congestion detected (packet loss or ECN signal):
// Cubic (Linux default since 3.2) vs Reno (classic):

// Reno on loss:
ssthresh = cwnd / 2
cwnd     = ssthresh    // Cut in half (multiplicative decrease)

// CUBIC on loss (more aggressive recovery):
ssthresh = cwnd × 0.7  // Only reduce to 70%
cwnd     = ssthresh
// CUBIC follows a cubic function of time since last loss
// Faster recovery, better utilization on high-BDP links

// BBR (Bottleneck Bandwidth and RTT) — Google's algorithm:
// Doesn't rely on packet loss as signal (loss = buffer full, too late!)
// Continuously probes for actual bottleneck bandwidth and min RTT
// Sets cwnd = BDP (Bandwidth-Delay Product)
BDP = bottleneck_bandwidth × min_RTT
// Result: maximizes throughput with minimal queuing delay

Queuing Theory — M/M/1 Queue Model

Queuing theory predicts system behavior under load. The M/M/1 model (Markovian arrivals, Markovian service, 1 server) is the foundation:

// Key variables:
λ (lambda) = arrival rate (requests/second)
μ (mu)     = service rate (requests/second a single server can handle)
ρ (rho)    = utilization = λ/μ  (must be < 1 for stable queue)

// Key formulas:
Average queue length:   Lq = ρ² / (1 - ρ)
Average wait time:      Wq = ρ / (μ × (1 - ρ))
Average response time:  W  = 1 / (μ - λ)   ← Little's Law form

// CRITICAL INSIGHT — the hockey stick effect:
// ρ=0.5 → Wq = 0.5/(μ×0.5) = 1/μ        (1× service time wait)
// ρ=0.8 → Wq = 0.8/(μ×0.2) = 4/μ        (4× service time wait!)
// ρ=0.9 → Wq = 0.9/(μ×0.1) = 9/μ        (9× service time wait!)
// ρ=0.95→ Wq = 0.95/(μ×0.05)= 19/μ      (19× service time wait!)

// Never design systems to operate above 70% utilization in production!
// The latency cliff is steep and response time becomes unpredictable
⚠️ Little's Law — Universal Throughput Formula L = λ × W (Average items in system = arrival rate × average time in system)
Example: 100 req/s arrive, average response time 200ms → 100 × 0.2 = 20 concurrent requests in flight at any moment. To handle 1000 req/s with 200ms response time, you need 1000 × 0.2 = 200 concurrent request slots (threads, async tasks, or goroutines).

Backpressure — Handling Overload Gracefully

When a consumer can't keep up with a producer, backpressure signals upstream to slow down rather than buffering indefinitely (which causes latency blowup and memory exhaustion):

// Without backpressure: producer fills unbounded queue → OOM or massive latency
// With backpressure: producer slows to match consumer rate

// TCP backpressure: built-in (receive window)
// When app doesn't read from socket, OS receive buffer fills
// TCP receiver advertises window=0 → sender must stop
// → Natural backpressure from DB all the way to client!

// Application-level backpressure (e.g., Reactive Streams / Project Reactor):
const stream = producer
  .pipe(
    bufferCount(100),        // Buffer up to 100 items
    concatMap(batch =>       // Process 1 batch at a time
      consumer.processBatch(batch)
    ),
    onBackpressureDrop()     // If still too fast: drop oldest items
  );

// Kafka backpressure:
// Consumer poll loop naturally throttles producer
// Consumer lag (topic offset - committed offset) = backpressure metric
// Consumer group lag > threshold → alert → scale out consumers

CDN Architecture — How Traffic Reaches the Nearest Edge

A CDN operates a global network of Points of Presence (PoPs) — data centers in 30–300+ cities. Traffic is routed to the nearest PoP via Anycast BGP: multiple PoPs announce the same IP prefix, and BGP's shortest-path routing selects the topographically closest one.

CDN Request Lifecycle — Internals

  1. DNS Resolution: Browser resolves cdn.example.com. CDN's authoritative DNS (e.g., Route 53, NS1) uses ECS (EDNS Client Subnet) to detect user's region and returns nearest PoP IP via Anycast.
  2. TCP + TLS to Edge: Connection goes to nearest PoP (3–30ms). PoP terminates TLS using certificates stored at edge (no round-trip to origin for TLS).
  3. Cache Lookup: Edge node checks local in-memory cache (L1) → disk cache (L2) → peer PoP cache (L3, via internal network) → origin shield → origin.
  4. Cache HIT: Response served directly from edge. Typical: 2–15ms total. Sets Age header = time since cached.
  5. Cache MISS: Edge makes request to origin (or shield). Caches response per Cache-Control headers. Returns to user. Sets X-Cache: MISS.
  6. Stale Response: If TTL expired but origin unreachable, serve stale + background revalidation (stale-while-revalidate).

Cache-Control Headers — The CDN's Instructions

Origin Shield — The Collapse Pattern

Without origin shield, a cache miss in Paris, Tokyo, and Sydney simultaneously sends 3 requests to the origin. With shield, all PoPs first check a designated "shield" PoP. Only the shield ever contacts the origin, collapsing N parallel origin requests to 1:

// Without origin shield (thundering herd on origin):
Tokyo   → MISS → Origin (request 1)  ←──┐
London  → MISS → Origin (request 2)  ←──┤ Same object!
Sydney  → MISS → Origin (request 3)  ←──┘ 3 origin hits

// With origin shield (request collapsing):
Tokyo  → MISS → Shield PoP → Origin (request 1)  ← Only 1 origin hit!
London → MISS → Shield PoP → (waits for inflight request)
Sydney → MISS → Shield PoP → (waits for inflight request)
// All 3 get response from 1 origin fetch — "request coalescing"

Cache Eviction Algorithms — Internals

LRU — Least Recently Used (O(1) Implementation)

// LRU = Doubly Linked List + HashMap
// List head = Most Recently Used (MRU)
// List tail = Least Recently Used (LRU) ← evict from here

class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();        // key → node (O(1) lookup)
    this.head = { key: null };   // dummy MRU sentinel
    this.tail = { key: null };   // dummy LRU sentinel
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  get(key) {
    const node = this.map.get(key);
    if (!node) return -1;          // Cache MISS
    this.moveToFront(node);         // Mark as recently used
    return node.val;
  }

  put(key, val) {
    if (this.map.has(key)) {
      const node = this.map.get(key);
      node.val = val;
      this.moveToFront(node);
    } else {
      if (this.map.size >= this.capacity) {
        const lru = this.tail.prev; // Least recently used
        this.remove(lru);           // O(1) — we have the pointer
        this.map.delete(lru.key);
      }
      const node = { key, val, prev: null, next: null };
      this.addToFront(node);
      this.map.set(key, node);
    }
  }
  // All operations O(1): HashMap lookup + linked list pointer manipulation
}

LFU — Least Frequently Used (O(1) with Frequency Buckets)

// LFU evicts the item with lowest access COUNT (not recency)
// Better for hot item preservation (e.g., homepage never evicted)
// O(1) implementation: frequency buckets + doubly linked list per bucket

// Data structure:
// minFreq  → pointer to lowest frequency bucket (for O(1) eviction)
// freqMap  → {frequency → DoublyLinkedList of nodes with that frequency}
// keyMap   → {key → node} for O(1) lookup

class LFUCache {
  get(key) {
    const node = keyMap.get(key);  // O(1)
    // Move from freq bucket N to freq bucket N+1
    freqMap.get(node.freq).remove(node);       // O(1)
    if (freqMap.get(node.freq).isEmpty() && node.freq === minFreq)
      minFreq++;                                  // O(1)
    node.freq++;
    freqMap.getOrCreate(node.freq).addToFront(node); // O(1)
    return node.val;
  }
  evict() {
    // Evict LRU item from minFreq bucket
    freqMap.get(minFreq).removeTail();           // O(1)
  }
}
// TinyLFU (Window-TinyLFU): used by Caffeine Java cache
// Uses Count-Min Sketch (probabilistic) to approximate frequency
// with O(1) space — no need to store exact count per item

Cache Warming Strategies

A cold cache (after deployment, restart, or flush) causes a cache stampede — all requests hit the database simultaneously. Cache warming pre-populates the cache before serving traffic:

Strategy 1: Eager Warming (Bulk Pre-load)

// Before deployment: pre-populate cache with hot data
async function warmCache() {
  // Query analytics to find top 10,000 most-requested items
  const hotKeys = await analytics.getTopKeys(10000);

  // Batch load from DB in parallel (rate-limited to not overload DB)
  await pMap(hotKeys, async key => {
    const value = await db.get(key);
    await cache.set(key, value, { ttl: 3600 });
  }, { concurrency: 50 }); // max 50 parallel DB queries

  console.log('Cache warm — ready for traffic');
  // Only then switch load balancer to new deployment
}

Strategy 2: Lazy Warming with Request Shadowing

// Route 1% of production traffic to new instance before full cutover
// Requests populate cache organically
// Monitor cache hit rate — when it reaches 80%+, cutover full traffic

// Nginx configuration for traffic shadowing:
location /api/ {
  proxy_pass http://production;

  # Mirror 1% to new instance (async, doesn't affect response)
  mirror /mirror;
  mirror_request_body on;
}
location /mirror {
  internal;
  proxy_pass http://new-instance;    # Warms new instance cache
}

Strategy 3: Probabilistic Early Expiry (Cache Stampede Prevention)

The most sophisticated strategy — prevents stampede before TTL expires by probabilistically refreshing ahead of time:

// XFetch Algorithm (probabilistic early expiry)
// Instead of all threads rushing to refresh when TTL hits exactly 0,
// each cache read independently decides whether to refresh early

async function xfetchGet(key, recomputeFn, beta = 1.0) {
  const cached = await cache.getWithMetadata(key);
  // cached = { value, ttl_remaining, last_compute_time }

  if (!cached) return await recompute(key, recomputeFn);

  // Probabilistic early refresh formula:
  // earlyExpiry = -last_compute_time × beta × log(random())
  const earlyExpiry = -cached.computeTime * beta * Math.log(Math.random());

  if (cached.ttl_remaining - earlyExpiry <= 0) {
    // Refresh NOW (before TTL=0) with probability based on compute time
    // Slower-to-compute items start refreshing earlier
    // Only ONE process triggers this (probabilistically) — others get cached value
    return await recompute(key, recomputeFn);
  }

  return cached.value;
}

Cache Invalidation Strategies

💬 Phil Karlton's Famous Quote "There are only two hard things in Computer Science: cache invalidation and naming things." — The reason: distributed systems have no global clock, no atomic multi-key updates, and race conditions between cache writes and DB writes are subtle and catastrophic.

TTL-Based Expiry (Simplest)

Items expire automatically after a fixed time. Simple but introduces eventual consistency windows. The application must tolerate stale data for up to TTL seconds.

Event-Driven Invalidation (Most Accurate)

// Pattern: write-through with event-driven cache invalidation

// Step 1: Update database
await db.update('products', { id: 123, price: 99.99 });

// Step 2: Publish change event (Kafka / SNS)
await eventBus.publish('product.updated', { id: 123, fields: ['price'] });

// Step 3: Cache invalidation consumer (async)
eventBus.subscribe('product.updated', async (event) => {
  await cache.delete(`product:${event.id}`);
  await cache.delete(`product:${event.id}:recommendations`);
  await cache.delete(`category:${event.categoryId}`); // dependent keys
});
// Problem: event processing lag = brief inconsistency window
// Problem: if consumer crashes, cache stays stale
// Solution: exactly-once consumer + idempotent invalidation

Cache-Aside with Version Stamps

// Store version alongside value — reject stale reads
async function versionedGet(key) {
  const cached = await cache.get(key);
  if (cached) {
    // Check version in DB (lightweight query)
    const currentVersion = await db.query(`SELECT version FROM products WHERE id=?`, key);
    if (cached.version === currentVersion) return cached.value; // Fresh!
    // Version mismatch → evict and fetch fresh
    await cache.delete(key);
  }
  const fresh = await db.query(`SELECT * FROM products WHERE id=?`, key);
  await cache.set(key, { value: fresh.data, version: fresh.version });
  return fresh.data;
}

Negative Caching — Cache the Absence

// Without negative caching:
// Attacker hits GET /users/nonexistent millions of times
// Every request hits DB (SELECT finds nothing → DB full table scan!)
// DB overwhelmed with guaranteed-miss queries

// With negative caching:
async function getUser(id) {
  const cached = await cache.get(`user:${id}`);
  if (cached === 'NOT_FOUND') return null; // Negative cache hit
  if (cached) return cached;

  const user = await db.findUser(id);

  if (!user) {
    // Cache the "not found" result for 60 seconds
    await cache.set(`user:${id}`, 'NOT_FOUND', { ttl: 60 });
    return null;
  }
  await cache.set(`user:${id}`, user, { ttl: 3600 });
  return user;
}

// Before querying DB or cache, check bloom filter (1MB can represent 10M IDs)
// Bloom says "maybe exists"? → check cache/DB
// Bloom says "definitely NOT exists"? → return 404 immediately
// False positive rate ~1% — configurable with filter size

TCP Connection Lifecycle — Every Byte on the Wire

Three-Way Handshake (Connection Establishment)

// TCP Segment structure (simplified):
// [SrcPort][DstPort][SeqNum][AckNum][Flags][Window][Checksum][Data]

Step 1 — SYN (Client → Server):
SrcPort=49152  DstPort=443
SeqNum=1000    AckNum=0
Flags=SYN
Window=65535   ← Receiver's initial buffer size
Options: MSS=1460, SACK permitted, WScale=7, Timestamps

Step 2 — SYN-ACK (Server → Client):
SeqNum=5000    AckNum=1001   ← Acknowledges client's SYN (seq+1)
Flags=SYN|ACK
Window=28960   ← Server's receive window
Options: MSS=1460, SACK permitted, WScale=9

Step 3 — ACK (Client → Server):
SeqNum=1001    AckNum=5001   ← Acknowledges server's SYN
Flags=ACK
← Connection ESTABLISHED. Client can send data immediately after this!

Total cost: 1 full RTT before first data byte is sent
TCP Fast Open (TFO): sends data in SYN packet on resumed connections
Reduces first-request latency by 1 RTT (like 0-RTT TLS resumption)

Connection Termination (Four-Way Handshake)

// TCP supports half-close: each side closes independently

Client: FIN → SeqNum=2000           ← "I'm done sending"
Server: ACK → AckNum=2001           ← "Got it" (may still send data)
Server: [sends remaining data...]
Server: FIN → SeqNum=6000           ← "I'm done too"
Client: ACK → AckNum=6001           ← "Got it"

// Client enters TIME_WAIT state for 2×MSL (Maximum Segment Lifetime)
// MSL = 60s typically → TIME_WAIT = 120 seconds!
// Purpose: ensure server receives final ACK if lost (would retransmit FIN)
// Problem: high-volume servers exhaust ephemeral ports (32768–60999)
// Solution: SO_REUSEADDR socket option, or TCP keepalive to avoid close

TCP Flow Control — Receiver Window

Prevents the sender from overwhelming the receiver's buffer. The receiver advertises how much buffer space it has (receive window). Sender may not have more than min(cwnd, rwnd) bytes unacknowledged:

// Receiver buffer fills up → advertises smaller window
Server → Client: ACK, Window=0    ← "Stop sending! My buffer is full!"
// Sender pauses — sends only ZWP (Zero Window Probe) to detect recovery

Server → Client: ACK, Window=8192 ← "Resume — I freed 8KB"
// Sender resumes

// Silly Window Syndrome: receiver advertises tiny windows
// Solution: Clark's algorithm — don't advertise window until ≥ MSS or ½ buffer

// Window Scaling (RFC 7323):
// 16-bit window field → max 65535 bytes
// For 100ms RTT link: max throughput = 65535 / 0.1 = 5.2 Mbps (bottleneck!)
// WScale option multiplies window by 2^scale (up to 2^14 = 16384)
// WScale=7: window up to 65535 × 128 = 8MB → enables high-speed transfers

TCP Head-of-Line Blocking — The Core Problem

// TCP delivers bytes IN ORDER to the application
// If packet 3 is lost in a sequence 1,2,3,4,5:

Network:    [1]  [2]  [X]  [4]  [5]     ← Packet 3 LOST
                       ↓
Receiver:  Receives 1,2 → delivers to app ✓
           Receives 4,5 → buffers (out of order, can't deliver yet!)
                           ↑ Waits for retransmission

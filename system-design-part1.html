Scalability

Scalability is the system's ability to handle a growing amount of work — requests, data, users, connections — by adding resources, without a proportional degradation in performance or an exponential increase in cost.

1. What Does "Scaling" Actually Mean Internally?

At its core, every system is bound by a set of resources: CPU cycles, RAM, disk I/O bandwidth, network I/O bandwidth, and connection handles. Scaling is the act of increasing those resources relative to load. The bottleneck shifts over time — first you hit CPU, then RAM, then disk, then network — so real scaling is an ongoing process of identifying and removing successive bottlenecks.

A single-server system serving 100 req/s might have: 4 vCPU @ 50% utilisation, 8 GB RAM @ 60%, 100 MB/s disk I/O @ 20%, 1 Gbps NIC @ 10%. When load grows 10×, every single one of those limits gets hit in sequence. Scalability engineering is about predicting and eliminating those limits before they hit production.

2. Vertical Scaling (Scale Up)

Vertical scaling means upgrading the machine: more cores, faster CPU clock, larger RAM, NVMe SSDs, faster NICs. Internally, this works because the OS scheduler can run more threads concurrently (more cores), allocate more memory pages without thrashing (more RAM), and sustain higher I/O throughput.

What happens inside the OS when you scale vertically?

  • More cores: The Linux kernel's CFS (Completely Fair Scheduler) can schedule more threads simultaneously on separate CPU run queues, reducing context switches and wake-up latency. A 32-core machine can literally run 32 threads of your app in true parallel at any instant.
  • More RAM: The page cache grows, keeping hot data in memory. The kernel's slab allocator can satisfy more object allocations without going to the swap device. GC-heavy runtimes (JVM, .NET) have more heap space → longer GC intervals → lower stop-the-world pauses.
  • Faster disk (SSD → NVMe): NVMe drives use PCIe lanes directly (not SATA controller bottleneck), providing 3–7 GB/s sequential throughput and sub-100µs latency, vs spinning disk's 100–200 MB/s and 5–10 ms latency. Database buffer pool misses become far cheaper.
⚠️ Vertical Scaling Ceiling
The largest available EC2 instance (u-24tb1.metal) has 448 vCPUs and 24 TB RAM. Beyond that ceiling, vertical scaling is impossible. Also: doubling compute doesn't double throughput — Amdahl's Law limits the parallel speedup to S = 1 / (1 - p + p/N) where p is the parallelisable fraction and N is core count. If 20% of your code is serial, max speedup is 5× regardless of infinity cores.

3. Horizontal Scaling (Scale Out)

Horizontal scaling adds more machines (nodes) to a pool and distributes work across them. This is the dominant pattern in modern cloud systems. Instead of one 128-core server, you run 128 single-core VMs, each handling a shard of the load.

Internal coordination challenges when scaling horizontally:

  • Shared state: If each instance has its own in-memory cache or session, they diverge. You need a centralised state store (Redis, Memcached) or sticky sessions.
  • Distributed consensus: When multiple nodes need to agree (e.g., who is leader), you need Raft or Paxos. This adds latency.
  • Network overhead: Data that previously moved via CPU bus (nanoseconds) now moves over Ethernet (microseconds–milliseconds). Chatty microservice calls compound this.
  • Clock skew: NTP keeps clocks within ~1–50 ms across nodes. If your logic depends on event ordering, you need logical clocks (Lamport timestamps, vector clocks).

4. The Scaling Dimensions — A Mental Model

Martin Kleppmann and the AKF Scale Cube define three dimensions of scaling:

X-Axis: Horizontal Duplication

Clone the entire service N times. Load balancer distributes traffic. Each clone has full capability. Simple but every node holds full dataset in memory.

Y-Axis: Functional Decomposition

Split by function — microservices. Order service, User service, Payment service. Each can scale independently based on its own load profile.

Z-Axis: Data Partitioning (Sharding)

Each node handles a subset of data/customers. Node A handles user IDs 0–1M, Node B handles 1M–2M. Reduces dataset per node, enables true horizontal DB scaling.

5. Stateless vs Stateful Scaling

Stateless services (REST APIs, GraphQL resolvers) scale trivially — any request can go to any instance because no per-session state is stored locally. The state is externalised to a database, Redis, or passed in the request (JWT token).

Stateful services (WebSocket connections, TCP sessions, game servers) are harder — the state lives on a specific node, so the LB must route a client to the same node (sticky sessions via IP hash or session cookie). If that node dies, the session is lost unless state is replicated.

# Nginx sticky session config — routes same client to same upstream
upstream app_servers {
    ip_hash;          # hash of client IP → deterministic node selection
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}

6. Database Scaling — The Hard Part

App servers are easy to scale. Databases are hard because they hold state. There are four main approaches:

a) Read Replicas

Primary handles writes. Replicas asynchronously receive the replication stream (WAL in Postgres, binlog in MySQL) and serve reads. Internally, MySQL binlog replication works as: Primary writes event to binlog → Replica I/O thread fetches binlog events → Replica SQL thread applies them to its local data files. Replication lag is the delay between primary write and replica commit — typically 10 ms–seconds under heavy write load.

b) Connection Pooling (PgBouncer, ProxySQL)

PostgreSQL forks a backend process per connection (~5 MB RAM each). At 10,000 connections, that's 50 GB RAM just for connection processes. PgBouncer maintains a small pool of real DB connections (say 100) and multiplexes thousands of app connections onto them. In transaction mode, a connection is borrowed for the duration of a single transaction, then returned to the pool.

c) Sharding

Split data into shards by key (user_id % N). Each shard is an independent DB server. Cross-shard joins are impossible natively — the application layer must aggregate. Resharding when you add nodes is painful (consistent hashing mitigates this).

d) CQRS + Event Sourcing

Separate the write model (commands) from the read model (queries). The read store is optimised for queries (denormalised, indexed differently). Scales read load independently from write load.

8. Amdahl's Law — Why You Can't Scale Infinitely

If your workload has a serial fraction s (e.g., global locks, single-threaded queue), the maximum speedup achievable with N processors is:

Speedup(N) = 1 / (s + (1 - s) / N)

Example: s = 0.10 (10% serial code)
N = 2  → speedup = 1.82×
N = 8  → speedup = 4.7×
N = ∞  → speedup = 10×  (hard ceiling!)

Implication: reducing serial bottlenecks (locks, single-leader writes)
is MORE valuable than adding more nodes after a point.

9. Real-World Scalability Patterns

  • Auto-scaling groups (AWS ASG): CloudWatch alarm (CPU > 70%) triggers launch of new EC2. ALB health check detects new instance. Traffic flows in ~90 seconds. Scale-in waits for connection draining (default 300s).
  • Kubernetes HPA (Horizontal Pod Autoscaler): Queries metrics-server every 15s. Computes desired replicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue). Applies a cooldown (--horizontal-pod-autoscaler-downscale-stabilization, default 5 min) to prevent thrashing.
  • Database connection pool scaling: PgBouncer pool_size = (DB_max_connections - superuser_reserve) / number_of_pgbouncer_instances. Overshooting causes "sorry, too many clients already".
  • Event-driven async scaling: SQS queue depth triggers Lambda concurrency or ECS task count. Works because consumers are stateless and idempotent.
✅ Key Takeaway
Scalability is not a single decision — it's a continuous process. Start with vertical scaling for simplicity, introduce horizontal scaling when you hit limits, shard data only when necessary (it adds massive complexity), and always measure bottlenecks before scaling to avoid premature optimisation.

Availability

Availability is the fraction of time a system is operational and serving requests correctly. It is the ratio of uptime to total time. Engineering high availability means designing systems that continue working despite hardware failures, software bugs, network partitions, and operator errors.

1. The Mathematics of Availability

Availability (A) = Uptime / (Uptime + Downtime) = MTBF / (MTBF + MTTR)

  • MTBF (Mean Time Between Failures): average time the system runs before failing. Increase by improving software quality, hardware redundancy.
  • MTTR (Mean Time To Recovery): average time to detect, diagnose, and restore service after failure. Decrease by improving monitoring, automation, and runbooks.

⚠️ SLA vs SLO vs SLI
SLI (Service Level Indicator): a measurable metric, e.g., "fraction of successful requests in last 5 min". SLO (Service Level Objective): the target you internally commit to, e.g., "99.9% of requests succeed". SLA (Service Level Agreement): the contractual commitment with penalty clauses. SLO should be stricter than SLA to give you a buffer (error budget).

2. Serial vs Parallel Availability — How Redundancy Works Mathematically

Components in Series (all must work for system to work):

A_total = A1 × A2 × A3 × ... × An

Example: 3 services each at 99.9%:
A_total = 0.999 × 0.999 × 0.999 = 0.997 = 99.7%

Adding components in series REDUCES availability!
This is why you want fewer hops in your critical path.

Components in Parallel (any one working = system works):

A_total = 1 - (1 - A1) × (1 - A2) × ... × (1 - An)

Example: 2 servers each at 99% availability:
A_total = 1 - (1 - 0.99) × (1 - 0.99)
        = 1 - 0.01 × 0.01
        = 1 - 0.0001 = 99.99%

Redundancy improves availability exponentially!

3. Failure Modes — What Actually Causes Downtime

Hardware Failures

Disk failure (MTTF ~3–5 years), NIC failure, RAM bit-flip (ECC corrects single-bit, can't fix multi-bit), power supply failure, rack switch failure. Google reports ~0.5% of drives fail per year at scale.

Software Bugs

Memory leaks (gradual OOM), deadlocks (threads wait on each other forever), race conditions, off-by-one errors in buffer allocation causing crashes under specific load.

Network Partitions

BGP route flaps, misconfigured ACLs, NIC firmware bugs causing packet loss, datacenter link saturation causing TCP retransmits and timeout cascades.

Operator Errors

Misconfigured deployment (wrong env var), accidental deletion (DROP TABLE), failed migration (schema change locks table), capacity exhaustion (disk full → log writes fail → service crash).

Dependency Failures

Third-party API (payment, email) outage, DNS resolver timeout, certificate expiry, cloud provider regional failure (AWS us-east-1 incidents).

Overload / Traffic Spikes

Thundering herd on cache miss, DDoS, viral traffic event, poorly batched cron job that queries full table simultaneously with prod traffic.

4. High Availability Architecture Patterns

a) Active-Active

Multiple nodes serve traffic simultaneously. Load balancer distributes across all. If one fails, the others absorb its share. Both nodes process writes, so conflict resolution or consensus is needed (e.g., last-write-wins, vector clocks, or Paxos). Used by: Cassandra, CockroachDB, global anycast DNS.

b) Active-Passive (Hot Standby)

One primary serves all traffic. The standby is fully up-to-date via synchronous replication but serves no traffic. On primary failure, health check detects it (within 10–30 seconds typically) and the standby is promoted. Failover time = detection time + DNS TTL propagation + standby initialisation. Used by: PostgreSQL streaming replication, MySQL with MHA.

c) Active-Passive (Cold Standby)

Standby is not running. Must be booted, restored from backup, and started. RTO (Recovery Time Objective) is minutes to hours. Much cheaper but higher downtime. Used for non-critical tier-2 systems.

5. Health Checks — How LBs Detect Failure

Health checks are the mechanism that enables automatic failover. There are three types:

  • TCP health check: LB opens a TCP connection to the backend port. If 3-way handshake completes, node is "up". Does NOT verify application logic — a crashed app with SO_REUSEADDR holding port open would pass.
  • HTTP health check: LB sends GET /health HTTP/1.1 and expects 200 OK within a timeout. The /health endpoint should verify DB connectivity, cache connectivity, and critical dependencies. A returning 200 when DB is unreachable is a bad health endpoint — it lies.
  • Deep health check: The endpoint performs a lightweight DB query (SELECT 1), checks cache ping, verifies disk space, and returns JSON with each component's status. Used for debugging but not always as the LB probe (too slow).
// Example robust health endpoint (Node.js / Express)
app.get('/health', async (req, res) => {
  const checks = await Promise.allSettled([
    db.query('SELECT 1'),
    redis.ping(),
  ]);
  const healthy = checks.every(c => c.status === 'fulfilled');
  res.status(healthy ? 200 : 503).json({
    status: healthy ? 'ok' : 'degraded',
    db: checks[0].status,
    redis: checks[1].status,
    uptime: process.uptime(),
  });
});

6. Geo-Redundancy and Multi-Region Availability

For five-nines availability, a single region is insufficient — AWS regions themselves have had multi-hour outages. You need multi-region deployment:

  1. Global Load Balancer (Route 53, Cloudflare): Uses DNS-based routing (latency-based, geolocation, failover policies) to direct users to the nearest healthy region.
  2. Data replication across regions: Async replication (low overhead, risk of data loss on failover) vs sync replication (no data loss, high latency penalty). Most systems use async with RPO (Recovery Point Objective) of <1 minute.
  3. Global Accelerator / Anycast: Traffic enters AWS backbone at the nearest PoP and traverses the private backbone (lower latency, avoids public internet jitter) to the serving region.
  4. Chaos Engineering: Netflix Chaos Monkey randomly terminates production instances. Chaos Kong terminates entire regions. This validates that your HA mechanisms actually work under real conditions.

7. Graceful Degradation

When a dependency fails, rather than returning an error to the user, the system returns a degraded but functional response. Example: YouTube's recommendation engine is down → show popular videos instead of personalised recommendations. The user gets a worse experience but the service is still "available".

✅ Key Takeaway
Availability engineering is a trade-off between cost and downtime tolerance. True high availability requires: redundancy at every layer (app, DB, network, datacenter), fast failure detection (health checks, alerts), fast recovery (automated failover, runbooks), and regular testing (chaos engineering, game days). No single component should be a single point of failure (SPOF).

Load Balancing

A load balancer is a device or software that distributes incoming network traffic across multiple backend servers to maximise throughput, minimise response time, avoid overload of any single server, and increase reliability through redundancy.

1. The Core Problem Load Balancers Solve

Without a load balancer, your single server is both a performance bottleneck and a SPOF. With a load balancer, you get: traffic distribution (no single server drowns), health-based routing (dead servers are bypassed), SSL termination (offload TLS handshake cost), and a single public endpoint (backend topology is hidden).

2. L4 vs L7 Load Balancing — The Deep Difference

Layer 4 (Transport Layer) Load Balancing

Operates on TCP/UDP packets. The LB looks at IP address + TCP port and makes routing decisions without reading the HTTP payload. It performs NAT (Network Address Translation) or IP tunnelling to forward packets.

How it works internally (NAT mode):

  1. Client establishes TCP connection to LB VIP (Virtual IP): 10.0.0.100:443.
  2. LB's kernel netfilter/iptables or DPDK-based dataplane selects a backend (10.0.0.5:8080) using its algorithm.
  3. LB rewrites the destination IP/port in the packet header (DNAT) and forwards. Source IP may also be rewritten (SNAT) so the backend sends return traffic back through the LB, or the LB uses DSR (Direct Server Return) to let the backend reply directly to the client.
  4. Connection table entry is kept so all packets of the same TCP flow go to the same backend (connection affinity).

Pros: Extremely fast (kernel bypass with DPDK: millions of packets/sec), works with any protocol (MySQL, Redis, SMTP), minimal overhead. Cons: Can't route based on HTTP Host header, URL path, or cookie — it can't read layer-7 content.

Layer 7 (Application Layer) Load Balancing

Terminates the TCP connection at the LB, reads the full HTTP/2 or gRPC request, and makes intelligent routing decisions based on content, then opens a new connection to the backend.

How it works internally:

  1. Client's TCP connection terminates at the LB. TLS is decrypted here (SSL termination).
  2. LB reads HTTP headers: Host: api.example.com, GET /users/123, Cookie: session=abc.
  3. Routing rules evaluated: if path starts with /api/v2, route to v2 cluster; if X-Beta-User: true, route to canary cluster.
  4. LB opens a new TCP connection to selected backend (from its connection pool). Forwards the request, receives response, sends back to client.

Pros: Content-based routing, A/B testing, rate limiting per endpoint, WebSocket upgrades, circuit breaking. Cons: Higher CPU cost per connection (full HTTP parse), added latency hop, requires TLS private key access.

3. Load Balancing Algorithms — Internal Mechanics

a) Round Robin

Requests are distributed sequentially: 1→Node1, 2→Node2, 3→Node3, 4→Node1... Internally, the LB maintains a circular pointer. Fast, zero overhead. Problem: doesn't account for backend capacity difference or current load. A slow request on Node1 doesn't affect routing of future requests to Node1.

b) Weighted Round Robin

Nodes get weights: Node1(weight=3), Node2(weight=1). In every 4 requests, 3 go to Node1 and 1 to Node2. Used when nodes have different hardware specs (larger VM gets more weight). Implemented as a GCD-based algorithm or interleaved pointer.

c) Least Connections

New request goes to the backend with fewest active connections. LB maintains a connection count per backend (incremented on open, decremented on close). Best for workloads with variable request duration (some requests take 1ms, others take 5s — round robin would pile requests on a slow backend). Requires synchronisation if LB is distributed (shared counter or approximate local counts).

d) Least Response Time

Routes to the backend with the lowest combination of: active connections × average response time. Requires the LB to measure and track backend response latency (EWMA — Exponentially Weighted Moving Average). Used by Envoy's LEAST_REQUEST policy with random selection among the two least-loaded upstreams (power-of-two-choices algorithm).

e) IP Hash (Source IP Affinity)

Hash of client IP → modulo N backends. The same client always goes to the same backend (sticky session without a cookie). Problem: if a backend dies, the hash changes for all clients whose modulo lands differently after N shrinks. Consistent hashing solves this.

f) Random

Uniformly random backend selection. With enough requests, converges to equal distribution (Law of Large Numbers). Envoy's power-of-two-choices: pick 2 random backends, route to the one with fewer active requests. Much better than pure random, nearly as good as least connections, without requiring a global counter.

g) Resource-Based (Adaptive)

Backends periodically report their CPU/memory utilisation. LB routes to the least-loaded backend. Requires a side-channel (e.g., gRPC metadata, custom headers) for backends to report metrics. Used in some service mesh implementations.

4. Health Checking in Load Balancers

LBs continuously probe backends:

  • Probe interval: every 5–30 seconds.
  • Unhealthy threshold: N consecutive failures (e.g., 3) before marking down. Prevents flapping on transient failures.
  • Healthy threshold: M consecutive successes (e.g., 2) before marking up after recovery.
  • Probe timeout: If backend doesn't respond within 2 seconds, count as failure.

During the window between a backend dying and the LB detecting it (up to 3 × 10s = 30 seconds at worst), traffic still flows to the dead backend → those requests fail. This is why application-level retries and circuit breakers exist as a complement to LB health checks.

5. SSL/TLS Termination

TLS handshake is expensive: it involves asymmetric cryptography (RSA or ECDH key exchange), certificate validation (chain traversal, OCSP stapling), and session establishment. Offloading this to the LB means:

  • Backends receive plain HTTP — no TLS overhead per request.
  • LB can reuse TLS sessions (session ticket resumption) — a returning client's TLS overhead drops from ~5 round trips to 1.
  • Certificate management is centralised (one cert on the LB, not on every backend).
  • Risk: Traffic between LB and backend is unencrypted. In a shared datacenter or cloud, this may violate compliance. Solution: use TLS between LB and backend too (end-to-end encryption) but accept slightly higher overhead.

6. Connection Draining (Graceful Backend Removal)

When you deploy a new version, you remove the old backend from the LB. If you do this abruptly, in-flight requests are killed. Connection draining: LB stops sending new requests to the backend being removed but allows existing connections to complete (up to a drain timeout, e.g., 30 seconds). After the timeout, the LB forcefully closes remaining connections.

7. Global vs Local Load Balancing

Local LB (L4/L7 in-datacenter)

HAProxy, Nginx, Envoy, AWS ALB/NLB. Routes traffic within a single region/datacenter. Sub-millisecond overhead. Handles SSL, health checks, content routing.

Global LB (DNS-based / Anycast)

AWS Route 53, Cloudflare, GCP Global LB. Routes traffic across regions based on latency, geography, or health. DNS TTL must be short (30–60s) for fast failover. Anycast routes to nearest PoP via BGP.

8. Real-World LB Tools Internals

HAProxy

Single-process, event-driven architecture. Uses epoll on Linux (or kqueue on BSD) to handle tens of thousands of concurrent connections with a small thread pool. Each thread runs an event loop. No thread-per-connection overhead. HAProxy's stick tables implement shared state for per-IP rate limiting and sticky sessions in clustered mode using a peer protocol.

Nginx (as LB)

Master process + N worker processes (one per CPU core). Each worker uses epoll event loop. Upstream module maintains connection pools to backends. keepalive directive enables persistent connections to backends, amortising TCP + TLS handshake cost over many requests.

Envoy Proxy

C++ L7 proxy used as the data plane in Istio service mesh. Features: hot restart (zero-downtime config reloads), xDS API (dynamic configuration from control plane), WASM filter plugins, native HTTP/2 and gRPC support, built-in circuit breaking, outlier detection (automatic backend ejection based on error rate), and distributed tracing.

✅ Key Takeaway
Use L4 LB for raw throughput and protocol-agnostic scenarios. Use L7 LB for HTTP/gRPC workloads where you need content routing, canary deployments, or rate limiting. Always enable health checks with appropriate thresholds, and connection draining for zero-downtime deploys. At scale, layer global DNS-based routing on top for multi-region resilience.

Reliability

Reliability is the probability that a system performs its intended function correctly, without failure, for a specified period under stated conditions. Unlike availability (which measures uptime), reliability measures correctness — the system is up AND produces correct results AND meets its performance SLOs.

1. Reliability vs Availability — The Critical Distinction

A system can be available but unreliable: imagine a banking API that returns 200 OK but occasionally returns the wrong account balance due to a race condition. It's "up" but corrupting data. Reliability requires both: functional correctness (right answer) and performance correctness (within SLO). Availability without reliability is worse than downtime — silent data corruption goes undetected and is hard to remediate.

🔴 Example: The Danger of Silent Data Corruption
In 2012, Knight Capital's trading software sent wrong orders due to a bug in a code deployment. The system was fully "available" — responding to market data — but executing incorrect trades. Lost $440 million in 45 minutes before detection. Reliability failure, not availability failure.

2. Reliability Engineering — Core Principles

a) Fault Tolerance vs Fault Avoidance

Fault avoidance: Write bug-free code, use formal verification, rigorous testing. Asymptotically approaches but never reaches zero bugs. Fault tolerance: Assume faults will happen (hardware WILL fail, bugs WILL ship) and design the system to continue operating correctly despite them. Modern distributed systems rely on fault tolerance because fault avoidance at scale is impossible.

b) Redundancy

Every critical component is duplicated. Types:

  • Hardware redundancy: RAID disks (parity), dual power supplies, dual NICs (bonding), redundant switches.
  • Software redundancy: Multiple service replicas, replicated databases.
  • Geographic redundancy: Multi-region, multi-AZ deployments.
  • Temporal redundancy: Retry failed operations (with backoff). If a request fails once, try again — the failure may be transient.

c) Idempotency

Operations that can be retried safely without double-effects. A payment API that deduplicates on a client-generated idempotency key (UUID) — if the same request is retried, the second attempt is recognised by the key and returns the original result without charging again. This enables safe retries, which are essential for reliability.

3. Failure Detection — How Systems Know They're Failing

Timeouts

Without timeouts, a slow dependency can hold your threads/connections indefinitely, exhausting your connection pool and causing cascading failure. Timeouts should be set based on p99 response time of the dependency + buffer. Too short → spurious failures under normal load. Too long → slow failures cascade.

# Good timeout strategy: connect timeout < read timeout < overall request timeout
connect_timeout = 100ms   # TCP handshake should be fast
read_timeout    = 500ms   # backend p99 + buffer
total_timeout   = 1000ms  # absolute ceiling including retries

Heartbeats

Nodes periodically send heartbeat messages to a coordinator or each other. If heartbeat is missing for N intervals, node is presumed failed. Used in: ZooKeeper (session timeout), Kafka (broker heartbeats to controller), Kubernetes (kubelet heartbeat to API server every 10s, eviction after 40s default). Problem: heartbeat absence could mean node failure OR network partition — both look the same from outside. This is the fundamental problem in distributed systems.

4. The Reliability Hierarchy — What to Fix First

  1. On-call & monitoring: You can't fix what you can't detect. Implement structured logging, distributed tracing, and alerting before anything else.
  2. Incident response: Runbooks, escalation paths, post-mortems with blameless culture. Each incident should produce an action item that prevents recurrence.
  3. Testing: Unit tests, integration tests, contract tests, load tests, chaos tests. Each layer catches different classes of bugs.
  4. Release engineering: Feature flags, canary deployments, automated rollbacks. Reduce blast radius of bad deploys.
  5. Capacity planning: Ensure you have headroom (30% free capacity) so that loss of one node doesn't overload remaining nodes.

5. Testing for Reliability

Chaos Engineering

Deliberately inject failures into production (or staging) to validate reliability assumptions. Principles (from Netflix Simian Army):

  • Hypothesis-driven: "We believe the system will maintain p99 < 200ms even if one AZ is unavailable."
  • Blast radius control: Start small (1% of traffic, 1 instance), expand if hypothesis holds.
  • Automated experiments: Run continuously. If a result diverges from the hypothesis, halt and alert.

Tools: Netflix Chaos Monkey (kills EC2 instances), Chaos Mesh (Kubernetes), Gremlin (commercial), AWS Fault Injection Simulator.

Property-Based Testing

Instead of writing specific test cases, you define properties that must always hold and the test framework generates thousands of random inputs to try to falsify them. Example: "for any two users, their account balances after a transfer should sum to the same total as before." Tools: Hypothesis (Python), QuickCheck (Haskell/Erlang), jqwik (Java).

6. Error Budgets

Google SRE introduced the concept: if your SLO is 99.9% availability, your error budget is 0.1% of requests (or 43.8 min/month). This budget is shared between planned downtime (deployments), unexpected failures, and risky changes. When the error budget is exhausted, the development team must freeze feature work and focus on reliability improvements. This creates alignment between engineering velocity and reliability.

Error Budget = 1 - SLO
Monthly error budget = (1 - 0.999) × 30 × 24 × 60 = 43.8 minutes

If last 30 days had 50 min of downtime:
  Budget consumed = 50/43.8 = 114% → budget exhausted → freeze features

7. Data Reliability — Durability

Durability is reliability applied to data: once written, it stays written. Mechanisms:

  • Write-ahead logging (WAL): All changes are written to a sequential log on durable storage before being applied to data files. On crash, the WAL is replayed. Used by PostgreSQL, MySQL InnoDB, RocksDB.
  • Fsync: fsync() system call flushes OS page cache to disk (calls disk controller's write-back cache flush if the disk supports it). Without fsync, a crash after write acknowledgement could lose data sitting in OS buffer. PostgreSQL calls fsync per WAL segment. Disabling fsync is a dangerous "performance" option.
  • Checksums: Data pages in PostgreSQL (since v9.3, enabled optionally) store a checksum. On read, checksum is verified. Detects bit-rot (disk data corruption that happens silently over time).
  • Replication: Synchronous replication ensures a write is confirmed only after it's written to the WAL of at least N replicas (configurable). Protects against single-node hardware failure losing data.
✅ Key Takeaway
Reliability = correct behaviour under failure conditions. It requires fault tolerance (not just fault avoidance), comprehensive testing (especially chaos engineering), observability, and cultural practices (blameless post-mortems, error budgets). Data reliability specifically requires WAL, fsync, and synchronous replication for strong durability guarantees.

Proxy Servers

A proxy server is an intermediary that sits between clients and servers. It intercepts requests/responses and performs additional functions: caching, authentication, load balancing, security filtering, traffic routing, logging, and protocol translation.

1. Forward Proxy vs Reverse Proxy — Fundamental Difference

Forward Proxy

Sits in front of clients. Clients know about the proxy and direct requests to it. The proxy forwards to the internet. The origin server sees the proxy's IP, not the client's. Use cases: corporate internet filtering, privacy (VPN-like), bypassing geo-restrictions, caching outbound requests.

Reverse Proxy

Sits in front of servers. Clients don't know about it — they think they're talking to the origin. The proxy routes to backend servers. Use cases: load balancing, SSL termination, caching, WAF, CDN edge, hiding backend topology. Nginx, HAProxy, Envoy, Cloudflare are all reverse proxies.

┌──────────────────────────────────────────────────────────────────┐ │ FORWARD PROXY vs REVERSE PROXY │ │ │ │ FORWARD PROXY: │ │ Client (knows proxy) ──▶ Forward Proxy ──▶ Internet/Origin │ │ Origin sees: Proxy IP │ │ Used for: Privacy, filtering, caching outbound │ │ │ │ REVERSE PROXY: │ │ Client (unaware) ──▶ Reverse Proxy ──▶ Backend servers │ │ Client sees: Proxy IP (thinks it's the server) │ │ Used for: LB, SSL termination, caching inbound, WAF │ └──────────────────────────────────────────────────────────────────┘

2. How a Reverse Proxy Works Internally

  1. Client DNS resolution: api.example.com resolves to the proxy's IP (not backend IPs, which are private/internal).
  2. TCP connection + TLS handshake: Client connects to proxy on port 443. Proxy terminates TLS (has the private key), decrypts the HTTP request.
  3. Request inspection: Proxy reads Host header, URL path, headers. Applies WAF rules (block SQLi/XSS patterns), rate limiting (count requests per IP in sliding window), authentication (validate JWT or API key).
  4. Backend selection: Based on URL routing rules, select backend cluster. Use LB algorithm (least connections, round robin) to pick specific instance. Add/modify headers: X-Forwarded-For: <client-ip>, X-Request-ID: uuid.
  5. Connection to backend: From a connection pool (persistent HTTP/2 connections). Forwards request to backend over plaintext HTTP or TLS (re-encryption).
  6. Response path: Backend response returns to proxy. Proxy may cache it (check Cache-Control headers), compress it (gzip/br), then forwards to client over the original encrypted connection.

3. Proxy Protocols and Headers

X-Forwarded-For (XFF)

When the proxy forwards the request, it adds the client's IP to the XFF header. If multiple proxies are involved, each appends: X-Forwarded-For: client-ip, proxy1-ip, proxy2-ip. The backend reads this to get the true client IP for logging, rate limiting, and geo-blocking. Security concern: A client can spoof XFF by sending their own header value. Trust only the last N hops (N = number of trusted proxies in your infrastructure).

PROXY Protocol (HAProxy)

Unlike XFF (HTTP-level), PROXY protocol operates at TCP level. The proxy prepends a binary or text header to the TCP stream before any application data: PROXY TCP4 192.168.1.1 10.0.0.5 54321 80\r\n. The backend must support PROXY protocol parsing. This allows the backend to know the real client IP even for non-HTTP protocols (MySQL, Redis).

4. Caching in Reverse Proxies

Varnish and Nginx can cache backend responses. The cache decision is based on HTTP cache semantics:

  • Cacheable: Cache-Control: public, max-age=3600 → proxy stores the response for 3600 seconds. Subsequent requests are served from cache without hitting the backend.
  • Not cacheable: Cache-Control: private, no-store → always fetches from backend.
  • Conditional requests: If the cached response has an ETag, the proxy sends If-None-Match: <etag> to the backend. Backend returns 304 Not Modified if unchanged — proxy serves cached copy, saving bandwidth.

Internally, the cache stores responses keyed by URL (+ Vary headers). On hit, it checks TTL. If expired but valid (stale), it can serve stale while revalidating in background (stale-while-revalidate directive). Varnish stores cache in shared memory (mmap'd) — extremely fast, orders of magnitude faster than disk.

5. Transparent Proxy

Intercepts traffic without client configuration — the client doesn't know a proxy exists. Implemented at network level using iptables REDIRECT rules that intercept TCP connections on port 80/443 and redirect to the proxy process. Used by ISPs for content filtering, corporate networks for monitoring all employee traffic. HTTPS traffic can't be content-inspected (end-to-end encrypted) unless the proxy does TLS interception with a root CA installed on client devices (SSL inspection / MITM).

6. SOCKS Proxy

SOCKS (Socket Secure) is a general-purpose proxy protocol at layer 5 (session layer). Unlike HTTP proxy (which understands HTTP), SOCKS proxies work at TCP/UDP level — they tunnel any protocol. Client sends CONNECT hostname:port command; SOCKS server opens a TCP connection to the target and relays bytes. Used by: SSH tunnels (ssh -D 1080 creates a local SOCKS5 proxy), Tor network (routes through multiple SOCKS nodes for anonymity).

7. Service Mesh as Proxy

In Kubernetes service mesh (Istio, Linkerd), an Envoy sidecar proxy is injected into every pod. All inbound/outbound traffic flows through the sidecar without the application knowing. This enables: mTLS between services, distributed tracing, per-service rate limiting, traffic splitting (for canary), and circuit breaking — all without changing application code. The control plane (Istiod) pushes configuration to sidecars via xDS API (gRPC long-poll).

✅ Key Takeaway
Proxies are the traffic cops of distributed systems. Forward proxies protect clients; reverse proxies protect and scale servers. At the network level they perform NAT/routing; at the application level they cache, authenticate, rate-limit, and route intelligently. Modern service meshes make proxying ubiquitous and transparent — every service becomes a proxy consumer.

DNS — Domain Name System

DNS is the distributed, hierarchical system that translates human-readable domain names (api.example.com) into IP addresses (93.184.216.34) that machines use to route packets. It is the phone book of the internet — and its internals are far more complex and critical than most engineers appreciate.

1. The DNS Hierarchy — How it's Structured

DNS is a tree structure with the root at the top:

. (Root) │ ┌─────────────┼─────────────┐ com org io │ example.com │ api.example.com www.example.com

Each level is managed by different authoritative servers:

  • Root servers (13 logical clusters, anycast to 1000+ physical servers): Know where the TLD servers are. They don't know your domain — they only know: "for .com, ask these servers".
  • TLD servers (Verisign for .com, PIR for .org): Know which authoritative server manages a specific domain. "For example.com, ask ns1.cloudflare.com".
  • Authoritative DNS servers (Cloudflare, Route 53, your own BIND): Have the actual DNS records (A, AAAA, CNAME, MX, TXT, etc.) for your domain. The final source of truth.

2. Full DNS Resolution — Step by Step (What Actually Happens)

  1. Browser cache check: Browser checks its own DNS cache (Chrome: chrome://net-internals/#dns). If cached and not expired (TTL not elapsed), done.
  2. OS resolver cache check: nscd or systemd-resolved on Linux. If found, return immediately.
  3. OS stub resolver → Recursive resolver: The OS sends a UDP (or TCP) query to the configured recursive resolver (your ISP's resolver, or 8.8.8.8, 1.1.1.1). This is the server that does the actual work of querying the hierarchy.
  4. Recursive resolver → Root server: Sends: "What is the IP of api.example.com?" Root responds: "I don't know, but .com TLD servers are at these IPs."
  5. Recursive resolver → .com TLD server: Asks same question. TLD responds: "I don't know, but example.com's authoritative servers are ns1.cloudflare.com, ns2.cloudflare.com."
  6. Recursive resolver → Authoritative server (Cloudflare/Route 53): Asks for api.example.com. Gets back: "A record: 93.184.216.34, TTL: 300".
  7. Recursive resolver caches and responds: Caches the answer for 300 seconds (the TTL). Returns the IP to the OS. OS caches it. Browser caches it.
┌─────────────────────────────────────────────────────────────────────┐ │ FULL DNS RESOLUTION FLOW │ │ │ │ Browser ──①──▶ OS Cache ──②──▶ Recursive Resolver (8.8.8.8) │ │ │ │ │ ③ Query Root (.): "api.example.com?" │ │ ◀─ Referral: ".com NS: a.gtld-servers.net" │ │ │ │ │ ④ Query .com TLD: "api.example.com?" │ │ ◀─ Referral: "NS: ns1.cloudflare.com" │ │ │ │ │ ⑤ Query Cloudflare NS: "api.example.com?" │ │ ◀─ Answer: A: 93.184.216.34, TTL: 300 │ │ │ │ │ Browser ◀── OS ◀── Recursive ──⑥── Cached + returned to client │ └─────────────────────────────────────────────────────────────────────┘

3. DNS Record Types — Internals

4. DNS Caching and TTL — The Hidden Complexity

TTL (Time-To-Live) is set on each DNS record by the domain owner. It controls how long resolvers cache the record. Trade-offs:

  • High TTL (3600s - 86400s): Less DNS query load, faster resolution (usually from cache), but IP changes take up to TTL time to propagate globally. Good for stable infrastructure.
  • Low TTL (30s - 60s): Fast propagation of IP changes (useful for failover), but every cache expiry requires a fresh recursive query — higher DNS load and slightly more latency. Required for active-active multi-region failover.

TTL propagation reality: When you change an A record, the new value propagates as caches expire. With TTL=300s, within 5 minutes most clients use the new IP. But some broken resolvers ignore TTL and cache forever. Some ISPs have aggressive caching. Budget 10× TTL for full propagation in practice.

5. DNS and Load Balancing

DNS Round Robin

Return multiple A records for the same name. The resolver returns all of them; the OS picks one (usually the first) and caches per TTL. Clients get different IPs on different queries, distributing load. Problem: If one server is down, DNS still returns its IP (DNS has no concept of health checking). Clients must handle the failure in their application layer.

Geo-DNS / Latency-Based Routing (Route 53)

The authoritative DNS server returns different A records based on the source IP of the recursive resolver (as a proxy for client location). A resolver from Singapore gets the Singapore PoP IP; a resolver from Virginia gets the US-East IP. This achieves geographic routing at the DNS level. Limitation: resolver IP ≠ client IP (CGNAT, corporate proxies); EDNS Client Subnet (ECS) extension passes a /24 prefix of the client IP to the authoritative server for more accurate routing.

6. DNSSEC — DNS Security Internals

Standard DNS is unauthenticated — an attacker can inject forged responses (DNS cache poisoning / Kaminsky attack). DNSSEC adds cryptographic signatures:

  • Each zone signs its records with a private key (ZSK — Zone Signing Key). The signature is stored in RRSIG records.
  • The ZSK's public key is stored in DNSKEY record. Its hash is stored as DS record in the parent zone, creating a chain of trust from root down.
  • A resolver verifying DNSSEC fetches RRSIG, verifies against DNSKEY, verifies DNSKEY against parent DS, all the way to the root (which has a well-known public key).
  • Doesn't encrypt DNS (responses are still in plaintext). Only authenticates. DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT) add encryption.

7. DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT)

DoT (RFC 7858): DNS queries sent over TLS on port 853. Encrypts the DNS query, preventing ISP snooping and man-in-the-middle injection. The resolver is still known (you're connecting to a specific IP:853).

DoH (RFC 8484): DNS queries sent as HTTPS requests (POST /dns-query with application/dns-message content type). Indistinguishable from regular HTTPS traffic to a network observer. Supported by Cloudflare (1.1.1.1), Google (8.8.8.8), and natively in Firefox (using Cloudflare by default). Centralises resolver choice — moves trust from ISP to DoH provider.

8. Internal DNS in Kubernetes

Kubernetes runs CoreDNS as its cluster-internal DNS server. Every service gets a DNS name: service-name.namespace.svc.cluster.local. When a pod queries this name:

  1. Pod's /etc/resolv.conf points to CoreDNS ClusterIP (10.96.0.10).
  2. CoreDNS receives query, checks its Kubernetes plugin which queries the API server's etcd for Service endpoints.
  3. Returns ClusterIP of the Service (for ClusterIP services) or the pod IPs (for Headless services — clusterIP: None).
  4. Pod connects to ClusterIP → kube-proxy (iptables/ipvs rules) performs DNAT to one of the backing pod IPs.
✅ Key Takeaway
DNS is the first hop in every network connection — its performance and reliability directly impact user experience. Understand TTLs to plan failover strategy, use low TTLs when you need fast IP changes, DNSSEC for integrity, DoH/DoT for privacy. In Kubernetes, CoreDNS is the critical internal DNS — a misconfigured or overloaded CoreDNS breaks all service-to-service communication.

HTTP vs HTTPS

HTTP (HyperText Transfer Protocol) is the application-layer protocol for transferring web data. HTTPS is HTTP secured by TLS (Transport Layer Security) — every byte of HTTP data is encrypted, authenticated, and integrity-checked. The difference is not just a lock icon — it's a fundamentally different security architecture.

1. HTTP Internals — How it Works

HTTP is a stateless, text-based, request-response protocol over TCP. Every request contains: Method + URL + HTTP version, headers (key:value pairs), optional body. Every response contains: status line, headers, optional body.

HTTP/1.0 — One Request Per Connection

TCP connection opens → one request sent → response received → connection closes. TCP's slow-start means the first few roundtrips have reduced throughput. Closing and reopening for every request is enormously wasteful.

HTTP/1.1 — Persistent Connections and Pipelining

Keep-alive: Connection stays open after response. Subsequent requests reuse the TCP connection. Default in HTTP/1.1. Head-of-line blocking: Requests are still serialised on one connection — response 1 must complete before response 2 is sent (even if response 2 is ready first). Pipelining: Client can send multiple requests without waiting for responses, but server must respond in order — still has HOL blocking. Workaround: open 6 parallel TCP connections per domain (browsers do this).

HTTP/2 — Binary Framing and Multiplexing

HTTP/2 redesigns the wire format from text to binary frames. Key mechanisms:

  • Streams: Each request/response pair is a stream with an ID (odd for client-initiated, even for server-initiated). Multiple streams are multiplexed over one TCP connection simultaneously. No HOL blocking at HTTP layer.
  • HPACK header compression: HTTP headers are repetitive (same headers sent with every request). HPACK uses a static table (61 common headers), a dynamic table (context-specific headers built during connection), and Huffman encoding. Reduces header overhead by 85%.
  • Server Push: Server proactively sends resources (CSS, JS) before client requests them. Client can reject pushed resources if already cached (RST_STREAM).
  • Remaining problem: HTTP/2 solves HTTP-layer HOL blocking but TCP-layer HOL blocking remains. One lost TCP packet blocks all streams until retransmit. Solution: HTTP/3.

HTTP/3 — QUIC (UDP-based)

HTTP/3 runs over QUIC (Quick UDP Internet Connections, RFC 9000) instead of TCP. QUIC is implemented in user space (not kernel), runs over UDP, and provides its own reliability, flow control, and congestion control. Benefits:

  • No TCP HOL blocking — packet loss affects only one QUIC stream, not all streams.
  • 0-RTT connection establishment — if client has previously connected, it can send data immediately (resuming session ticket). 1-RTT for new connections (vs TCP+TLS 1.3's 1-RTT for new and TCP's 1.5-RTT overhead).
  • Connection migration — QUIC connections are identified by a connection ID, not IP:port. Mobile users switching from WiFi to cellular maintain the same QUIC connection.

2. TLS — The Engine Behind HTTPS

TLS (Transport Layer Security) provides three services: Confidentiality (encryption — nobody can read the data), Authentication (server's identity is verified via certificate), Integrity (data hasn't been tampered with — MAC/AEAD).

TLS 1.3 Handshake — Step by Step (What Happens in Microseconds)

  1. ClientHello: Client sends: TLS version, random nonce (32 bytes), cipher suites supported (e.g., TLS_AES_256_GCM_SHA384), supported key exchange groups (X25519, P-256), extensions (SNI, ALPN, session ticket).
  2. ServerHello: Server responds: chosen cipher suite, chosen key exchange group, server's key share (public Diffie-Hellman value).
  3. Key derivation: Both sides independently compute the session keys using ECDH (Elliptic Curve Diffie-Hellman). The client's key share + server's key share → shared secret → HKDF (HMAC-based Key Derivation Function) → multiple symmetric keys (handshake key, data key, IV).
  4. Server sends: Encrypted certificate (server's identity), CertificateVerify (proves server holds the private key — digital signature over the handshake transcript), Finished (MAC over entire handshake).
  5. Client verifies: Certificate chain → trusted root CA → not expired → subject matches domain. Verifies digital signature. Sends own Finished.
  6. Encrypted data exchange begins. All HTTP bytes are now AES-GCM or ChaCha20-Poly1305 encrypted.
┌────────────────────────────────────────────────────────────────────┐ │ TLS 1.3 HANDSHAKE │ │ │ │ Client Server │ │ │──── ClientHello (key_share, ciphers, SNI) ──────▶│ │ │ │◀─── ServerHello (key_share) ────────────────────│ │ │ │ ◀── {EncryptedExtensions} ──────────────────│ │ │ │ ◀── {Certificate} ───────────────────────────│ │ │ │ ◀── {CertificateVerify} ────────────────────│ │ │ │ ◀── {Finished} ─────────────────────────────│ │ │ │ │ │ │ [Both sides derive same session keys via ECDH] │ │ │ │ │ │──── {Finished} ─────────────────────────────────▶│ │ │ │ │ │ │════ Encrypted HTTP/2 or HTTP/1.1 data ═══════════│ │ │ │ │ Total: 1 round trip (vs TLS 1.2's 2 round trips) │ └────────────────────────────────────────────────────────────────────┘

3. Certificates — The Trust Infrastructure

A certificate is an X.509 document containing: subject domain name, public key, issuer (CA name), validity period, serial number, signature by issuer's private key. The browser trusts a certificate if it was signed by a CA in its trust store (Mozilla, Apple, Microsoft, Google each maintain their own trust stores — ~150 CAs).

Certificate Chain

Root CA (self-signed, in browser trust store) → Intermediate CA (signed by Root CA) → Server Certificate (signed by Intermediate CA). Root CAs are kept offline (air-gapped). Intermediate CAs do the actual signing. If an Intermediate CA is compromised, it can be revoked without touching the Root CA.

Certificate Revocation

  • CRL (Certificate Revocation List): A signed list of revoked serial numbers. Downloaded periodically. Can be stale (hours old). Large for big CAs.
  • OCSP (Online Certificate Status Protocol): Real-time query to CA's OCSP server for cert status. Adds latency. Privacy issue (CA knows which certs you're checking).
  • OCSP Stapling: Server fetches OCSP response from CA, attaches it to the TLS handshake (staples it). Client gets fresh proof of cert validity without contacting CA. Best of both worlds. Server must refresh staple periodically (before it expires).

4. HSTS (HTTP Strict Transport Security)

Server sends header: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload. Browser stores this domain in its HSTS list. For the next year, the browser will never send HTTP to this domain — it automatically upgrades to HTTPS before making any connection. Prevents SSL-stripping attacks (where an attacker intercepts the first HTTP request before the redirect to HTTPS).

The preload directive submits the domain to the HSTS preload list — hardcoded in browsers before they even visit the site. Chrome's list has 80,000+ domains.

5. Perfect Forward Secrecy (PFS)

In older TLS (RSA key exchange), the server's private key is used to encrypt the session key. If an attacker records all traffic and later steals the private key, they can decrypt ALL past sessions. With ECDH key exchange (used in TLS 1.3 exclusively), the session key is derived from ephemeral DH parameters that are discarded after the handshake. Even if the server's private key is stolen later, past sessions cannot be decrypted because the ephemeral keys are gone.

✅ Key Takeaway
HTTPS is not optional — it provides confidentiality (no eavesdropping), integrity (no tampering), and authentication (correct server). TLS 1.3 has eliminated most performance overhead vs TLS 1.2. HTTP/2 requires TLS in practice (all browsers enforce this). HTTP/3/QUIC eliminates TCP-layer head-of-line blocking. Use HSTS + preloading, OCSP stapling, and ECDH cipher suites for modern HTTPS best practices.

API Gateway

An API Gateway is the single entry point for all client requests to a microservices system. It acts as a reverse proxy that routes requests, aggregates responses, and enforces cross-cutting concerns (authentication, rate limiting, logging, SSL) at the perimeter — so individual services don't need to implement them.

1. Why API Gateways Exist — The Problem They Solve

Without an API Gateway, every microservice needs to implement: auth token validation, rate limiting, SSL termination, CORS, logging, tracing, and request transformation. This duplicates logic across hundreds of services, creates inconsistency, and makes changes require updating every service. The gateway centralises all of this.

2. Core Functions of an API Gateway

a) Request Routing

The gateway inspects the incoming request (URL path, HTTP method, headers) and routes it to the correct downstream microservice. This is L7 routing. Config example:

# Kong / KrakenD style route config
routes:
  - path: /api/v1/users/**
    upstream: http://user-service:8080
  - path: /api/v1/orders/**
    upstream: http://order-service:8080
  - path: /api/v2/users/**
    upstream: http://user-service-v2:8080
    canary_weight: 10  # 10% traffic to v2

b) Authentication and Authorization

The gateway validates credentials before the request reaches any service. Mechanisms:

  • JWT validation: Decode and verify the JWT signature using the issuer's public key (fetched from JWKS endpoint). Check expiry, issuer, audience claims. If valid, forward request with decoded claims as headers (X-User-ID, X-User-Roles) to downstream services so they don't need to re-validate.
  • OAuth 2.0 token introspection: Forward the bearer token to the authorisation server's introspect endpoint. Slower (network call per request) but authoritative. Can be cached (with short TTL) by the gateway.
  • API Key validation: Check API key against a lookup store (Redis hash: key→customer metadata). Inject customer context into request headers.

c) Rate Limiting

Implemented at the gateway to protect downstream services. Algorithms (see Rate Limiting topic for deep dive): Token Bucket, Leaky Bucket, Fixed Window, Sliding Window. Gateway stores rate limit counters in Redis (for distributed rate limiting across multiple gateway instances). Per-key (API key), per-IP, per-user, or global limits.

// Sliding window rate limit check (pseudocode in gateway)
function isAllowed(userId, limit=100, windowMs=60000):
  key = `rate_limit:${userId}`
  now = Date.now()
  // Remove old entries outside the window
  redis.zremrangebyscore(key, 0, now - windowMs)
  count = redis.zcard(key)
  if count >= limit: return 429 Too Many Requests
  redis.zadd(key, now, now)  // score=timestamp, member=timestamp
  redis.pexpire(key, windowMs)
  return 200 OK

d) Request/Response Transformation

The gateway can modify requests before forwarding and responses before returning to clients:

  • Add headers: X-Request-ID, X-Trace-ID, X-Correlation-ID, X-Forwarded-For
  • Strip sensitive headers before forwarding: Authorization (replace with decoded user context)
  • Request body transformation: convert REST request to gRPC protobuf for downstream service
  • Response aggregation (Backend for Frontend / API composition): call User Service + Order Service + Inventory Service, merge responses into one JSON response for the mobile client

e) SSL/TLS Termination

Same as described in Load Balancing. The gateway holds the TLS certificate and decrypts traffic. Backend services communicate over plaintext HTTP within the private network (or re-encrypted with mTLS in a zero-trust setup).

f) Observability

The gateway has visibility into every request crossing the perimeter. It generates:

  • Access logs: method, path, status, upstream, latency, bytes, client IP, user ID
  • Metrics: RPS per route, error rate per route, upstream latency percentiles, rate limit rejections
  • Distributed traces: Injects trace context (W3C Trace-Context header: traceparent: 00-traceId-spanId-flags) into every request so traces flow through downstream services into Jaeger/Zipkin/Tempo

3. API Gateway Architecture — Request Lifecycle

4. Backend for Frontend (BFF) Pattern

A single generic API Gateway can become a bottleneck when serving radically different clients (mobile app needs small payloads, web app needs full data, IoT device needs binary protocol). BFF creates specialised gateways per client type:

  • Mobile BFF: Aggregates data, reduces payload size, optimises for mobile bandwidth.
  • Web BFF: Returns richer data, handles server-side rendering concerns.
  • Partner API BFF: Exposes limited, versioned, heavily rate-limited APIs to external partners.

6. Popular API Gateway Implementations

Kong Gateway

Built on Nginx + OpenResty (Lua scripting on Nginx). Plugin architecture — each function (auth, rate limit, logging) is a plugin executed in a specific phase of the request lifecycle (access, header_filter, body_filter, log). Plugins run in Lua coroutines within Nginx worker processes. Config stored in PostgreSQL or distributed via declarative YAML (deck).

AWS API Gateway

Managed service. Routes to Lambda, HTTP endpoints, or AWS services. Two types: REST API (feature-rich, more expensive) and HTTP API (simpler, cheaper, faster). Stage variables enable environment-specific routing. Usage plans + API keys for partner rate limiting. Throttling at account level (default 10,000 RPS) and per-API level.

Envoy + Ambassador / Emissary-ingress

Envoy as the data plane, Kubernetes CRDs as the control plane configuration. Declarative routing config in YAML. Native gRPC support, HTTP/3, WASM plugin extensions.

✅ Key Takeaway
An API Gateway is the essential perimeter layer in microservices — it centralises auth, rate limiting, routing, logging, and transformation. Design it to be stateless (state in Redis), horizontally scalable, and fast (plugin pipeline should add <5ms). Consider BFF for multi-client systems. Don't confuse with service mesh — use both: gateway for north-south, mesh for east-west.

Circuit Breaker

The Circuit Breaker is a stability pattern that prevents cascading failures in distributed systems. When a downstream service is failing, instead of continuously trying and failing (consuming threads, connections, and time), the circuit breaker "trips" — it immediately rejects calls to the failing service, protecting the caller from slow degradation and giving the downstream time to recover.

1. The Problem: Cascading Failure Without a Circuit Breaker

Imagine Service A calls Service B. Service B is slow (p99: 10 seconds instead of 100ms). Service A's thread pool has 50 threads. Each thread is blocked waiting for B for 10 seconds. Within seconds, all 50 threads are waiting for B. New requests to Service A queue up, then fail. Service A is now as dead as Service B, even though Service A's own code is fine. This is cascading failure — one slow service kills the entire call chain.

┌──────────────────────────────────────────────────────────────────┐ │ CASCADE FAILURE WITHOUT CIRCUIT BREAKER │ │ │ │ Client → Service A → Service B (SLOW: 10s response) │ │ │ │ Time 0: A has 50 threads. 10 threads waiting on B. │ │ Time 5s: 30 threads waiting on B. A queuing new requests. │ │ Time 10s: 50 threads all blocked on B. A is completely stuck. │ │ Time 15s: Clients see A timing out. A is effectively DOWN. │ │ Service C which calls A is also now failing. │ │ │ │ Root cause: B (slow) → A (stuck) → C (failing) → cascade │ └──────────────────────────────────────────────────────────────────┘

2. Circuit Breaker States — The State Machine

The circuit breaker has three states, implemented as a state machine:

CLOSED (Normal Operation)

All requests pass through to the downstream service. The circuit breaker monitors results (success/failure). A sliding window of the last N calls (or last N seconds) tracks the failure rate. When the failure rate exceeds a threshold (e.g., 50% of last 100 calls fail), the breaker trips to OPEN.

OPEN (Failing Fast)

All calls to the downstream service are immediately rejected with an error (no actual network call made). This instantly frees up threads/connections in the caller. The caller gets immediate failure (instead of waiting for timeout), can use a fallback, and the downstream gets relief from traffic. A timer starts (e.g., 60 seconds). When the timer expires, the breaker transitions to HALF-OPEN.

HALF-OPEN (Probing Recovery)

A limited number of requests are allowed through to test if the downstream has recovered. If these test requests succeed → breaker closes (service recovered). If they fail → breaker opens again (service still broken) and resets the timer. This prevents premature re-opening.

┌──────────────────────────────────────────────────────────────────┐ │ CIRCUIT BREAKER STATE MACHINE │ │ │ │ ┌──────────┐ │ │ ┌──────────│ CLOSED │──────────┐ │ │ │ Success └──────────┘ Failure │ │ │ │ (normal ops) rate > │ │ │ │ threshold │ │ │ │ ▼ │ │ │ ┌──────────┐ │ │ │ Timer expires │ OPEN │ │ │ │ ◀────────────────│ │ │ │ │ │ (reject) │ │ │ │ └──────────┘ │ │ │ │ │ │ │ Timer expires │ │ │ ▼ │ │ │ ┌───────────────┐ │ │ │ Probe succeeds │ HALF-OPEN │ │ │ └────────────────────────│ │ │ │ │ (allow few) │ │ │ └───────────────┘ │ │ │ Probe fails │ │ ▼ │ │ OPEN again │ └──────────────────────────────────────────────────────────────────┘

3. Implementation — Internal Mechanics

Sliding Window (Count-Based)

Track the last N call outcomes in a circular buffer. Each entry is SUCCESS or FAILURE. Failure rate = failures / N. If failure rate ≥ threshold AND minimum calls in window ≥ minimum (e.g., 10 calls minimum to avoid tripping on cold start), trip the breaker.

Sliding Window (Time-Based)

Track outcomes in the last T seconds (e.g., last 60 seconds). Use a bucket structure: divide window into sub-buckets (e.g., 60 buckets of 1 second each). Each second, add a new bucket and discard the oldest. Sum successes/failures across buckets. More accurate for bursty traffic patterns.

// Resilience4j Circuit Breaker configuration (Java)
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
  .slidingWindowType(COUNT_BASED)
  .slidingWindowSize(100)            // last 100 calls
  .failureRateThreshold(50)           // 50% failure → OPEN
  .slowCallRateThreshold(80)          // 80% slow calls → OPEN
  .slowCallDurationThreshold(Duration.ofSeconds(2)) // "slow" = >2s
  .waitDurationInOpenState(Duration.ofSeconds(60)) // 60s open timer
  .permittedNumberOfCallsInHalfOpenState(10)  // 10 probes in half-open
  .minimumNumberOfCalls(10)           // need 10 calls before evaluating
  .build();

4. Slow Call Detection

An important nuance: a circuit breaker shouldn't only trip on outright failures (exceptions, 5xx). A service that responds in 30 seconds is just as harmful as one that returns 500. Resilience4j supports a slowCallRateThreshold — calls exceeding slowCallDurationThreshold are counted as "slow calls" and contribute to breaker evaluation independently of the failure rate. This catches degraded services before they cause thread pool exhaustion.

5. Fallback Strategies

When the circuit is OPEN, the caller needs a fallback to provide partial functionality:

  • Return cached data: Return the last known good response from local cache. "Here are yesterday's product recommendations."
  • Return default/empty response: "No recommendations available right now." Graceful degradation.
  • Fail fast with specific error: Return 503 Service Unavailable immediately instead of timing out after 30 seconds. Caller handles this error properly.
  • Use a secondary service: Primary payment processor down → route to secondary. Primary recommendation engine down → use simpler rules-based fallback.
// Circuit breaker with fallback (Resilience4j + Java)
CircuitBreaker cb = CircuitBreaker.of("paymentService", config);

String result = Decorators
  .ofSupplier(() -> paymentService.charge(order))
  .withCircuitBreaker(cb)
  .withFallback(CallNotPermittedException.class,
               e -> "Payment queued for retry")  // CB is OPEN fallback
  .withFallback(Exception.class,
               e -> secondaryPaymentService.charge(order))
  .get();

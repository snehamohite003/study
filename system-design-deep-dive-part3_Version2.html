Throughput & Latency

The two fundamental performance axes — measurement, percentiles, tail amplification, and system models

Precise Definitions — What They Are and Are Not

⚡ Throughput
  • Work completed per unit time (req/s, MB/s, tx/s)
  • A rate measured at the system output
  • Maximized by parallelism, batching, pipelining
  • Bounded by the slowest stage (bottleneck)
  • Governed by Amdahl's Law for parallel sections
  • Example: 50,000 req/s on an API server
🕰️ Latency
  • Time for one operation to complete (ms, µs, ns)
  • A duration measured per individual request
  • Minimized by reducing hops, caching, co-location
  • Has an absolute floor: speed-of-light propagation
  • Distributions matter far more than means
  • Example: p99 = 45ms on an API endpoint
⚠️ The Fundamental Tension Throughput and latency trade off against each other. Batching increases throughput (amortizes fixed overhead across many items) but increases latency (items wait to fill the batch). TCP's Nagle algorithm coalesces small packets for better throughput at the cost of up to 200ms of added latency. Disable with TCP_NODELAY for latency-sensitive services (Redis, trading systems, real-time APIs).

Why Averages Are Lies — The Case for Percentiles

The arithmetic mean (average) hides the most important information in a latency distribution. A bimodal distribution (90% of requests: 1ms, 10% of requests: 1000ms) yields a mean of ~101ms — which describes neither population accurately. Percentiles expose the truth:

// Realistic latency sample set — 1000 requests (milliseconds)
// 890 requests:  2ms   ← cache hit fast path
// 95  requests: 50ms   ← DB read (index scan)
// 10  requests: 200ms  ← DB read (full table scan / lock wait)
// 4   requests: 800ms  ← downstream service slow
// 1   request: 5000ms  ← GC stop-the-world pause

mean   = (890×2 + 95×50 + 10×200 + 4×800 + 1×5000) / 1000 = 14.5ms
// ↑ Completely hides the 5-second outlier. Nobody experienced 14.5ms!

p50  (median) =   2ms   ← half of users faster than this
p90           =  10ms
p95           =  50ms   ← 1 in 20 requests at this latency
p99           = 300ms   ← 1 in 100 requests at this latency
p99.9         = 5000ms  ← 1 in 1000 requests — at 1000 req/s: 1 per second!

// Golden Rule: Always set SLOs on percentiles, never on means.
// Good SLO: "p99 latency ≤ 200ms measured over a 5-minute window"
// Bad SLO:  "average latency ≤ 50ms"

Tail Latency Amplification — The Hidden Killer at Scale

When a single user-facing request fans out to multiple downstream services in parallel, the observed latency equals the maximum of all dependency latencies. What looks like a rare p99 event at the service level becomes a near-certain experience at the user level:

// Fan-out to N independent services, each with p99 = 1% slow
// P(user request is fast) = P(ALL services fast)

P(all fast | N=1)   = 0.99^1   = 99.0%  → 1.0% slow
P(all fast | N=10)  = 0.99^10  = 90.4%  → 9.6% slow
P(all fast | N=50)  = 0.99^50  = 60.5%  → 39.5% slow
P(all fast | N=100) = 0.99^100 = 36.6%  → 63.4% slow ← majority experience tail!

// Solution 1: Hedged Requests (Google "The Tail at Scale", Dean & Barroso 2013)
async function hedgedRequest(primaryBackend, hedgeBackends, key) {
  // Send to primary; if no response within p95 latency, also send to hedge
  const p95Threshold = 20; // ms

  return new Promise((resolve, reject) => {
    let resolved = false;

    const tryBackend = (backend) => {
      backend.get(key).then(result => {
        if (!resolved) { resolved = true; resolve(result); }
      });
    };

    tryBackend(primaryBackend);

    // After p95 threshold, fire hedge to second backend
    setTimeout(() => {
      if (!resolved) tryBackend(hedgeBackends[0]);
    }, p95Threshold);
  });
  // Cost: ~5% extra backend load. Benefit: p99 → near p95 latency for user
}

// Solution 2: Tie-breaking — send to 2 backends simultaneously,
// cancel slower one when first responds (used by Cassandra speculative execution)

Coordinated Omission — The Load Testing Fallacy

The most dangerous and least understood performance measurement mistake. When a system is slow, a naive load tester slows down too — it waits for the previous response before sending the next request. This means the tester doesn't measure the experience of requests that would have been queuing during that slow period:

// Naive load test — WRONG (coordinated omission):
for (;;) {
  const start = Date.now();
  await http.get('/api');            // Waits for response before next req
  record(Date.now() - start);
}
// If server stalls for 30s, tester records 1 request at 30s
// Reality: 30,000 real users would have been queuing during that 30s!

// Correct load test — scheduled arrivals (HdrHistogram + wrk2 / Gatling):
const targetRPS = 1000;
const intervalMs = 1000 / targetRPS; // 1ms between requests

let nextSendTime = Date.now();
while (running) {
  const scheduledStart = nextSendTime;
  nextSendTime += intervalMs;         // Advance clock regardless of completion

  // Send asynchronously — don't wait for response before scheduling next
  http.get('/api').then(res => {
    // Record against SCHEDULED start time, not actual send time
    histogram.record(Date.now() - scheduledStart);
  });

  await sleepUntil(nextSendTime);
}
// Now if server stalls 30s, histogram records 30,000 requests each at 30s

Little's Law — The Universal System Capacity Formula

// L = λ × W
// L = average number of items in system (concurrent requests in flight)
// λ = arrival rate (requests per second)
// W = average time in system (response time in seconds)

// Example 1: Capacity Planning
// Target: 10,000 req/s with p99 latency of 100ms
L = 10000 × 0.1 = 1000  ← must support 1000 concurrent requests
// If each thread handles 1 concurrent request: need 1000 threads
// If async (Node.js event loop): 1 thread can handle all 1000

// Example 2: Database Connection Pool Sizing
// DB query rate: 500 qps, average query time: 20ms
L = 500 × 0.02 = 10  ← 10 concurrent DB connections needed
// Set pool size = 10–15 (with buffer). Don't set 100+ — wastes resources
// and causes context switching overhead on DB server

// Example 3: Why latency increases under load (queuing effect)
// Service capacity: 1000 req/s. Arrival rate: 900 req/s (90% utilization)
// M/M/1 queue: W = 1/(μ-λ) = 1/(1000-900) = 10ms service time becomes 10ms wait
// Arrival rate: 990 req/s (99% utilization)
// W = 1/(1000-990) = 100ms ← 10x latency increase for 10% more load!

Universal Scalability Law (USL) — Modeling Concurrency Limits

Neil Gunther's USL extends Amdahl's Law with a coherency penalty — the cost of keeping distributed state consistent. It predicts throughput degradation as concurrency rises:

// USL Formula: X(N) = N / (1 + α(N-1) + βN(N-1))
// X(N) = throughput with N workers/nodes
// α    = contention coefficient (serialization — Amdahl component)
// β    = coherency coefficient (cross-node coordination cost)

// Three regimes:
// β = 0, α = 0: Perfect linear scaling X(N) = N
// β = 0, α > 0: Amdahl — saturates at 1/α
// β > 0, α > 0: USL — throughput PEAKS then DECREASES (retrograde scalability!)

// Real example: Database cluster benchmark
// At N=1:  X=1000 tps
// At N=8:  X=6200 tps  (fits USL with α=0.02, β=0.001)
// At N=16: X=9800 tps  (still growing)
// At N=32: X=8500 tps  ← DEGRADES! Coherency cost exceeds parallelism gain
// At N=64: X=5200 tps  ← Worse than 8 nodes!

// Why: at high node counts, cache coherency protocols (MESI), distributed
// locking, and gossip overhead consume more CPU than the work itself
// USL lets you predict the optimal node count BEFORE running expensive tests

Measuring Latency Correctly — HDR Histogram

// HDR Histogram (High Dynamic Range) — stores values with fixed relative error
// Standard histograms: fixed bucket width → poor precision at high values
// HDR: logarithmic bucket sizing → 1% relative error at ALL scales

// Stores values from 1µs to 1 hour in ~3600 bytes
// Can represent 1ms and 1,000,000ms with equal relative precision
// Supports non-destructive merging: combine histograms from multiple nodes

// Usage in Java (HdrHistogram library):
Histogram h = new Histogram(3600000000L, 3); // max=1hr, 3 sig figs
h.recordValue(latencyMicros);

// Retrieve percentiles:

h.getValueAtPercentile(99.0)   // p99
h.getValueAtPercentile(99.9)   // p99.9
h.getValueAtPercentile(99.99)  // p99.99

// Key insight: report percentiles over SHORT windows (1min)
// A single 5s GC pause averaged over 24h looks like 3ms/req

Observability vs. Monitoring — The Critical Distinction

Monitoring tells you when something is wrong (threshold alerts on known metrics). Observability lets you understand why something is wrong by asking arbitrary questions of your system without prior instrumentation. Observability is a property of the system; monitoring is something you do with it.

📐 The Three Pillars Metrics: Numeric aggregations over time (CPU%, req/s, error rate). Cheap to store, great for alerting and dashboards.
Logs: Timestamped records of discrete events. Expensive at scale, essential for debugging specific incidents.
Traces: Causal chains of operations across services. Answer "why was this request slow?" with full call graph.

Cardinality — The Prometheus Killer

// Cardinality = number of unique time series = Cartesian product of label values

// Safe labels (low cardinality):
http_requests_total{method, route, status_code}
// methods=5, routes=50, status=10 → 5×50×10 = 2,500 series ✓

// DANGEROUS labels (high cardinality):
http_requests_total{user_id="usr_123456"}  ← 1M users = 1M series ✗
http_requests_total{session_id="abc"}      ← unbounded ✗
http_requests_total{trace_id="xyz"}        ← each request unique ✗

// High cardinality kills Prometheus:
// Each series = ~3KB RAM in Prometheus
// 1M series = 3GB RAM for just this one metric!
// Solution: use logs/traces for high-cardinality dimensions
// Or: use Prometheus exemplars to link metric → trace for p99 samples

Distributed tracing propagates a context (trace ID + span ID) through every hop of a request, allowing reconstruction of the full call graph after the fact:

// Trace context propagation (W3C Trace Context standard):
// HTTP header: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
//                           ver-traceId(128bit)-parentSpanId(64bit)-flags

// OpenTelemetry SDK — instrumenting a service:
const { trace, context } = require('@opentelemetry/api');
const tracer = trace.getTracer('order-service', '1.0.0');

async function processOrder(req) {
  // Start a new span — automatically propagates trace context from incoming request
  const span = tracer.startSpan('processOrder', {
    attributes: {
      'order.id':      req.body.orderId,
      'order.amount':  req.body.amount,
      'http.method':   req.method,
      'http.route':    '/api/orders',
    }
  });

  try {
    await context.with(trace.setSpan(context.active(), span), async () => {
      await validateInventory(req.body);  // Child spans created inside
      await chargePayment(req.body);      // Each fn creates its own span
      await updateDatabase(req.body);
    });
    span.setStatus({ code: SpanStatusCode.OK });
  } catch (err) {
    span.recordException(err);           // Attach exception to span
    span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
    throw err;
  } finally {
    span.end();  // Export to Jaeger/Tempo/Zipkin via OTLP
  }
}

How distributed systems agree on a single value despite failures — Paxos, Raft, leader election, log replication

The Consensus Problem — Why It's Hard

Consensus means: given N nodes, all nodes must agree on the same value, even if some nodes crash or messages are lost/delayed. The FLP Impossibility Theorem (Fischer, Lynch, Paterson 1985) proves that no deterministic algorithm can guarantee consensus in an asynchronous system with even ONE faulty process. Real-world systems work around this by assuming partial synchrony (messages eventually arrive) and using timeouts.

🚨 Split-Brain — The Worst Failure Mode A network partition creates two isolated groups, both believing themselves to be the legitimate leader. Both accept writes independently — the data diverges. When the partition heals, you have conflicting histories with no clear winner. Consensus algorithms prevent split-brain by requiring a quorum (majority) for any decision. With N nodes, quorum = ⌊N/2⌋ + 1. Only one partition can ever have a majority.

Paxos — The Original Consensus Algorithm

Paxos (Lamport 1989/1998) is the theoretical foundation for all practical consensus algorithms. It runs in two phases and guarantees safety (never chooses two different values) but doesn't guarantee liveness (may loop forever in adversarial message ordering):

Paxos — Two-Phase Protocol (single value consensus) Roles: Proposer (initiates), Acceptors (vote), Learners (observe) Quorum (majority) required: N=5 nodes → quorum=3 Phase 1: PREPARE Proposer → All Acceptors: Prepare(n=5) ← n = proposal number (globally unique) Each Acceptor responds: If n > highest_seen_proposal: Promise: "I won't accept proposals < n" Return: (highest_accepted_proposal, highest_accepted_value) Phase 2: ACCEPT Proposer (after receiving quorum of promises): value = highest previously accepted value (if any), else own value Proposer → Quorum of Acceptors: Accept(n=5, value="v") Each Acceptor: If n >= promised: Accept and store (n, value). Reply Accepted(n, value) If n < promised: Reject (Proposer must retry with higher n) Proposer receives quorum of Accepted → VALUE CHOSEN Proposer → Learners: Decided(value="v")

Multi-Paxos — Efficient Repeated Consensus (Log Replication)

// Single-shot Paxos = 2 round trips per value = too slow for logs
// Multi-Paxos optimization: once a leader is established with a stable ballot,
// skip Phase 1 for subsequent log entries — only run Phase 2

// This is how Google Chubby, Apache Zookeeper (ZAB), and etcd work internally
// ZAB (Zookeeper Atomic Broadcast) is a Paxos variant that ensures:
// 1. All committed updates delivered in order to all followers
// 2. Leader broadcasts propose → followers ack → leader commits → followers apply

Leader state machine:
  log[1] = "SET x=1" → Propose to quorum → Quorum ACK → Commit → Apply
  log[2] = "SET y=2" → Propose to quorum → Quorum ACK → Commit → Apply
  log[3] = "DEL z"   → Propose to quorum → Quorum ACK → Commit → Apply
// Each entry needs only 1 RTT (Phase 2 only) while leader stable

Raft — Paxos Made Understandable

Raft (Ongaro & Ousterhout 2014) decomposes consensus into three independent subproblems: leader election, log replication, and safety. Designed to be more understandable and implementable than Paxos. Used in etcd (Kubernetes), CockroachDB, TiKV, Consul:

Raft Leader Election — Full Mechanism

// Node states: Follower → Candidate → Leader
// Terms: monotonically increasing logical clock (like Paxos ballot numbers)

// Normal operation: Leader sends heartbeats every 150ms
// Election timeout: each follower picks random timeout 150–300ms
// If no heartbeat received before timeout → start election

class RaftNode {
  startElection() {
    this.state       = 'CANDIDATE';
    this.currentTerm++;           // Increment term
    this.votedFor    = this.id;   // Vote for self
    this.votesReceived = 1;

    // Send RequestVote to all peers
    for (const peer of this.peers) {
      peer.requestVote({
        term:         this.currentTerm,
        candidateId:  this.id,
        lastLogIndex: this.log.length - 1,
        lastLogTerm:  this.log.at(-1)?.term  ← Log completeness check!
      }).then(resp => this.handleVoteResponse(resp));
    }

    // Reset election timer (random 150-300ms)
    this.resetElectionTimer();
  }

  handleVoteRequest({ term, candidateId, lastLogIndex, lastLogTerm }) {
    // Grant vote ONLY if:
    // 1. Candidate's term >= our current term
    // 2. We haven't voted yet this term (or voted for this candidate)
    // 3. Candidate's log is AT LEAST as up-to-date as ours
    //    (prevents node with stale log from becoming leader)
    const logUpToDate =
      lastLogTerm  > this.log.at(-1)?.term ||
      (lastLogTerm === this.log.at(-1)?.term &&
       lastLogIndex >= this.log.length - 1);

    const canVote = (this.votedFor === null || this.votedFor === candidateId);

    if (term >= this.currentTerm && canVote && logUpToDate) {
      this.votedFor = candidateId;
      return { voteGranted: true, term: this.currentTerm };
    }
    return { voteGranted: false, term: this.currentTerm };
  }

  handleVoteResponse({ voteGranted, term }) {
    if (term > this.currentTerm) {  // Discover higher term → revert to follower
      this.currentTerm = term;
      this.state = 'FOLLOWER';
      return;
    }
    if (voteGranted) {
      this.votesReceived++;
      if (this.votesReceived > Math.floor(this.peers.length / 2)) {
        this.state = 'LEADER';  // Won majority → become leader
        this.sendHeartbeats();   // Immediately assert leadership
      }
    }
  }
}

Raft Log Replication — Keeping Followers In Sync

// Leader receives client write → appends to local log → replicates
async function appendEntries(entries) {
  // Append to leader's log (not committed yet)
  this.log.push(...entries.map(e => ({ ...e, term: this.currentTerm })));

  // Send AppendEntries RPC to all followers in parallel
  const promises = this.peers.map(peer =>
    peer.appendEntries({
      term:         this.currentTerm,
      leaderId:     this.id,
      prevLogIndex: this.nextIndex[peer.id] - 1,   // Consistency check
      prevLogTerm:  this.log[this.nextIndex[peer.id]-1]?.term,
      entries:      entries,
      leaderCommit: this.commitIndex  // Tell follower what's safe to apply
    })
  );

  // Wait for QUORUM acknowledgment
  const acks = await waitForQuorum(promises);

  // Once quorum acks: COMMIT (advance commitIndex)
  this.commitIndex = this.log.length - 1;
  this.stateMachine.apply(entries);  // Apply to state machine

  // On next heartbeat, followers learn commitIndex → apply themselves
  return 'success';
}

// Follower consistency check (prevLogIndex + prevLogTerm must match):
// If mismatch → reject → leader sends earlier entries → follower overwrites

CAP Theorem

The fundamental distributed systems trade-off — consistency, availability, and partition tolerance in depth

Consistency ModelsAvailabilityPartition Tolerance PACELCEventual ConsistencyLinearizability Read-Your-WritesTunable Consistency

CAP Theorem — The Formal Statement

Eric Brewer (2000) / Gilbert & Lynch (2002): A distributed data store can only guarantee two of three properties simultaneously during a network partition:

C — Consistency
  • Every read receives the most recent write or an error
  • All nodes see the same data at the same time
  • NOT the "C" in ACID (which means data integrity)
  • CAP-C = Linearizability (strongest consistency model)
A — Availability
  • Every request receives a (non-error) response
  • No guarantee the response contains the latest data
  • System stays responsive despite node failures
  • Does NOT mean "highly available" in SLA terms
📌 Partition Tolerance Is Not Optional Network partitions happen in any distributed system — cables cut, switches fail, BGP route flaps. You cannot choose to sacrifice P. The real choice is: during a partition, do you sacrifice C (stay available with potentially stale data) or sacrifice A (refuse requests until partition heals)?

The Partition Scenario — What Actually Happens

// 5-node cluster. Network partition splits into:
// Partition A: Node1, Node2 (minority — 2 nodes)
// Partition B: Node3, Node4, Node5 (majority — 3 nodes, quorum)

// CP System (e.g., etcd, ZooKeeper, HBase) behavior:
// Partition A (minority): refuses ALL writes and reads (no quorum)
//   → Returns "503 Service Unavailable" or "No quorum" error
// Partition B (majority): continues normally (has quorum)
// Result: Partition A users experience full downtime during partition
// Guarantee: no stale data ever returned. One consistent truth.

// AP System (e.g., Cassandra, DynamoDB, CouchDB) behavior:
// Partition A (minority): accepts reads AND writes (responds to all)
//   → Returns potentially stale data (last known value)
// Partition B (majority): accepts reads AND writes
// Both partitions diverge. When partition heals → conflict resolution needed
// Cassandra: last-write-wins (LWW) by timestamp, or application-level merging
// DynamoDB: version vectors + application conflict resolution

CAP's "consistency" is binary, but real systems offer a spectrum of consistency guarantees:

Conflict Resolution in AP Systems

// Cassandra: Last-Write-Wins (LWW) with client timestamps
// Risk: clock skew means "later" timestamp isn't necessarily "later" write
// Mitigation: Hybrid Logical Clocks (HLC) — monotonic, yet physical-time-aware

// CRDTs (Conflict-free Replicated Data Types) — mathematically merge-safe
// G-Counter: grow-only counter — each node has own counter, value = sum of all

class GCounter {
  constructor(nodeId, numNodes) {
    this.nodeId   = nodeId;
    this.counters = new Array(numNodes).fill(0);
  }
  increment() { this.counters[this.nodeId]++; }
  value()     { return this.counters.reduce((a, b) => a + b, 0); }

  // Merge with another node's state — take max per element
  merge(other) {
    this.counters = this.counters.map((v, i) => Math.max(v, other.counters[i]));
  }
  // No matter what order merges happen, result is always correct! ✓
  // Used in: shopping cart (add-only), likes/views, distributed metrics
}

// Vector Clocks — track causality between events
// Each node maintains a counter per node in the system
// On event: increment own counter. On send: attach vector. On receive: merge vectors.
// If V1[i] ≥ V2[i] for all i AND V1[j] > V2[j] for some j: V1 happened-after V2
// If neither dominates: concurrent events → conflict → application resolves

Failure Domains — Isolating Blast Radius

A failure domain is a set of components that share a single point of failure. Designing independent failure domains ensures that a failure in one domain cannot cascade into another:

AWS Failure Domain Hierarchy Region (us-east-1) ← Independent geographic location Availability Zone (us-east-1a) ← Independent power, cooling, networking Data Center ← Physical building Rack ← Shared top-of-rack switch + PDU Server ← Shared motherboard, CPU, RAM Process ← Shared OS kernel, memory space Thread ← Shared heap, GC Design rule: Replicate across failure domains at the right level for your SLA: 99.9% → Multi-server (same AZ) 99.99% → Multi-AZ (same region, independent power/network) 99.999%→ Multi-region (independent geography, BGP routing) Anti-pattern: "Multi-AZ" deployment where all AZs share one RDS primary → RDS primary failure takes down all AZs simultaneously! Fix: Active-active with independent primaries in each AZ

Timeout Strategy — Setting Timeouts Correctly

// Every network call MUST have a timeout — no exceptions!
// Without timeouts: one slow dependency holds threads forever → cascades

// Timeout anatomy:
const timeoutConfig = {
  connectTimeout: 1000,   // TCP handshake: 1s (fast failure if server unreachable)
  requestTimeout: 5000,   // Full request-response cycle: 5s
  socketTimeout:  30000,  // Idle connection timeout: 30s (keep-alive cleanup)
  readTimeout:    10000,  // Time to receive response headers: 10s
};

// Timeout budget / deadline propagation (critical for microservices):
// Client sets total budget (e.g., 500ms). Each hop deducts its elapsed time.
// Prevents: A calls B with 5s timeout, B calls C with new 5s timeout
// → A times out after 5s but B→C is still running, wasting resources

async function handleRequest(req) {
  const deadline = req.startTime + 500; // 500ms total budget from client

  const remainingA = deadline - Date.now(); // Remaining budget for service A
  const resultA = await serviceA.call({ timeout: remainingA });

  const remainingB = deadline - Date.now(); // Remaining budget after A
  if (remainingB <= 0) throw new Error('Deadline exceeded before calling B');
  const resultB = await serviceB.call({ timeout: remainingB });
  // gRPC context deadlines do this automatically with context propagation
}

// Timeout formula for dependent services:
// upstream_timeout = sum(downstream_p99_latencies) + processing_time + buffer
// If ServiceB p99 = 100ms, ServiceC p99 = 200ms, processing = 50ms:
// ServiceA timeout = 100+200+50 + 100ms_buffer = 450ms

Saga Pattern — Distributed Transaction Fault Tolerance

In microservices, you cannot use ACID transactions across services. The Saga pattern breaks a distributed transaction into a sequence of local transactions, with compensating transactions for rollback:

Saga Pattern — Order Placement (Choreography style) OrderService PaymentService InventoryService ShipmentService │ │ │ │ │──CreateOrder────────►│ │ │ │ │ │ │ │◄─OrderCreated────────│ │ │ │ │──ChargeCard──────►│ │ │ │ │ │ │ │◄─PaymentOK───────│ │ │ │ │──ReserveItems─────►│ │ │ │ │ │ │ │◄─ItemsReserved────│ │ │ │──ShipOrder──────────►│ Failure scenario: ShipmentService fails after payment taken ShipmentService publishes: OrderShipmentFailed InventoryService compensates: ReleaseItems (compensating tx) PaymentService compensates: RefundCard (compensating tx) OrderService compensates: CancelOrder (compensating tx) ← Each compensating tx must be idempotent (safe to retry) 
// Orchestration Saga — central coordinator controls flow
// (Simpler to reason about, but coordinator is a coupling point)

class OrderSagaOrchestrator {
  async execute(orderId) {
    const saga = await sagaStore.create(orderId); // Persist saga state

    try {
      await this.step(saga, () => paymentService.charge(orderId),
                           () => paymentService.refund(orderId));

      await this.step(saga, () => inventoryService.reserve(orderId),
                           () => inventoryService.release(orderId));

      await this.step(saga, () => shipmentService.create(orderId),
                           () => shipmentService.cancel(orderId));

      await saga.markCompleted();
    } catch (err) {
      await saga.rollback(); // Execute compensating txs in reverse order
    }
  }

  async step(saga, action, compensate) {
    const result = await action();
    saga.addCompensation(compensate); // Register rollback for this step
    await sagaStore.save(saga);       // Persist before proceeding!
    return result;
    // If orchestrator crashes, can resume from persisted saga state
  }
}

REST — The Six Architectural Constraints

REST (Representational State Transfer, Roy Fielding 2000) is an architectural style, not a protocol. Many APIs called "REST" violate its constraints. The six actual constraints:

  1. Client-Server: Separation of UI from data storage. Server doesn't know UI state.
  2. Stateless: Each request contains ALL information needed. Server holds no client session state.
  3. Cacheable: Responses must declare themselves cacheable or not (Cache-Control headers).
  4. Uniform Interface: Resources identified by URIs. Manipulated via representations. Self-descriptive messages. HATEOAS (links to related resources in response).
  5. Layered System: Client doesn't know if it's talking directly to server or a load balancer/proxy/CDN.
  6. Code on Demand (optional): Server can send executable code (JavaScript) to client.
// Well-designed REST API — resource-oriented, stateless, cacheable

// Resources, not actions in URLs:
GET    /orders                    ← List orders (cacheable)
GET    /orders/123                ← Get specific order (cacheable)
POST   /orders                    ← Create order (not cacheable, not idempotent)
PUT    /orders/123                ← Replace order (idempotent)
PATCH  /orders/123                ← Partial update (may not be idempotent)
DELETE /orders/123                ← Delete order (idempotent)

// Bad REST (RPC-style, ignores HTTP semantics):
POST /getUser                     ← Verb in URL, uses POST for read
GET  /updateOrderStatus?id=123    ← Mutation via GET (not cacheable!)
POST /order/cancel/123            ← Mixed verb + noun

gRPC — Remote Procedure Calls over HTTP/2

gRPC (Google, 2015) is a high-performance RPC framework. It uses Protobuf for serialization and HTTP/2 for transport. Every aspect is designed for efficiency and strong contracts:

Protobuf Encoding — How Binary Serialization Works

// Service definition (contract-first in .proto file):
syntax = "proto3";

service OrderService {
  rpc GetOrder      (GetOrderRequest) returns (Order);                    // Unary
  rpc ListOrders    (ListOrdersRequest) returns (stream Order);            // Server stream
  rpc CreateOrders  (stream OrderRequest) returns (OrderSummary);          // Client stream
  rpc SyncOrders    (stream OrderUpdate) returns (stream OrderStatus);     // Bidirectional
}

message Order {
  int64  id        = 1;   ← field number (NOT value!)
  string customer  = 2;
  double amount    = 3;
  OrderStatus status = 4;
  repeated OrderItem items = 5;
}

// Protobuf binary encoding — TLV (Tag-Length-Value) format:
// Field tag = (field_number << 3) | wire_type
// Wire types: 0=varint, 1=64bit, 2=length-delimited, 5=32bit

// Encoding { id: 123, customer: "Alice", amount: 99.99 }:
// id=123 (field 1, varint):   08 7B
//   tag=0x08 = (1<<3)|0, value=0x7B=123
// customer="Alice" (field 2, length-delimited): 12 05 41 6C 69 63 65
//   tag=0x12 = (2<<3)|2, len=5, UTF-8 bytes of "Alice"
// amount=99.99 (field 3, 64-bit double): 19 8F C2 F5 28 5C BF 58 40
//   tag=0x19 = (3<<3)|1, 8-byte IEEE 754 double

// Total: ~16 bytes vs JSON {"id":123,"customer":"Alice","amount":99.99} = 42 bytes
// 2.6× smaller. Also ~5-10× faster to serialize/deserialize than JSON

gRPC Interceptors — Middleware for RPC

// gRPC interceptors = middleware for all RPC calls
// Applied to every incoming (server) or outgoing (client) call

// Server-side interceptor (Go example):
func authInterceptor(ctx context.Context, req interface{},
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {

  // 1. Extract token from gRPC metadata (equivalent to HTTP headers)
  md, _ := metadata.FromIncomingContext(ctx)
  token := md.Get("authorization")[0]

  // 2. Validate JWT
  claims, err := validateJWT(token)
  if err != nil {
    return nil, status.Error(codes.Unauthenticated, "invalid token")
  }

  // 3. Add claims to context for handler
  ctx = context.WithValue(ctx, "user", claims)

  // 4. Call actual handler
  return handler(ctx, req)
}

// Chain multiple interceptors:
server := grpc.NewServer(
  grpc.ChainUnaryInterceptor(
    loggingInterceptor,      // Log all requests
    tracingInterceptor,      // Inject OpenTelemetry spans
    authInterceptor,         // Validate JWT
    rateLimitInterceptor,    // Apply rate limiting
    recoveryInterceptor,     // Recover from panics → gRPC error
  ),
)

GraphQL Core Concepts — How It Actually Works

GraphQL is a query language for APIs and a runtime for executing those queries. Clients specify exactly what data they need; the server returns exactly that — no more, no less. This solves REST's over-fetching and under-fetching problems:

// REST: Under-fetching — need 3 round trips for user + orders + products

// GraphQL: Exactly the data needed, 1 round trip
query GetUserDashboard($userId: ID!) {
  user(id: $userId) {             ← only the fields we ask for
    name
    email
    orders(last: 5) {             ← nested — no separate request
      id
      total
      status
      items {
        product { name, price }   ← deeply nested — still 1 request
        quantity
      }
    }
  }
}
// Response contains EXACTLY the fields requested — nothing more
// Mobile client gets lean payload. Desktop client can request more fields.

Resolver Execution — How GraphQL Processes a Query

GraphQL resolves queries as a tree. Each field has a resolver function. The runtime traverses the query tree, calling resolvers depth-first, and assembles the result:

// Resolver map (Apollo Server / graphql-js):
const resolvers = {
  Query: {
    // Root resolver — gets initial data
    user: (parent, { id }, context, info) => {
      // parent = null (root query)
      // id = query argument
      // context = { db, currentUser, dataloaders }
      // info = field info, query AST
      return context.db.findUser(id);
    }
  },

  User: {
    // Field resolver — called for each User object returned
    orders: (user, args, context) => {
      // parent = User object from Query.user resolver
      return context.db.findOrdersByUserId(user.id, args);
    },
    // If no resolver defined → default resolver: parent[fieldName]
    // So User.name, User.email auto-resolve from the user object ✓
  },

  Order: {
    items: (order, args, context) => {
      return context.db.findItemsByOrderId(order.id);
    },
    customer: (order, args, context) => {
      // ⚠️ N+1 PROBLEM! Called once per order → N DB queries for N orders
      return context.db.findUser(order.customerId);
    }
  }
};

// Resolver execution order for:
// { user { orders { items { product { name } } } } }
// 1. Query.user() → returns User
// 2. User.orders() → returns [Order, Order, Order]
// 3. Order.items() × 3 → returns [[Item...], [Item...], [Item...]]
// 4. Item.product() × N → returns [Product...]
// Parallelism: siblings are resolved concurrently (Promise.all)

The N+1 Problem — GraphQL's Critical Performance Issue

When a query returns a list of N items and each item requires a separate resolver call (e.g., fetching the author of each post), you get N+1 database queries: 1 to fetch the list + N individual lookups.

// Query: { orders { customer { name } } }
// 1 query: SELECT * FROM orders LIMIT 10          → 10 orders
// 10 queries: SELECT * FROM users WHERE id = ?    → per-order user lookup!
// Total: 11 DB queries for what should be 2
// At scale: 1000 orders = 1001 DB queries → disaster

// Solution: DataLoader (Facebook) — batches and caches per request
const DataLoader = require('dataloader');

// Create per-request DataLoader (never share across requests!)
function createLoaders(db) {
  return {
    userLoader: new DataLoader(async (userIds) => {
      // Called ONCE with all accumulated IDs from a tick
      // userIds = [1, 5, 7, 12, 43] — all orders' customer IDs
      const users = await db.query(
        `SELECT * FROM users WHERE id = ANY($1)`, [userIds]
      );
      // DataLoader requires results in SAME ORDER as input keys!
      return userIds.map(id => users.find(u => u.id === id));
    }, {
      cache: true,    // Same user ID in same request → returns cached
      maxBatchSize: 100 // Max IDs per batch query
    })
  };
}

// Updated resolver — uses DataLoader instead of direct DB call:
Order: {
  customer: (order, args, context) => {
    // context.loaders created fresh per request
    return context.loaders.userLoader.load(order.customerId);
    // DataLoader defers this call until end of current event loop tick
    // Accumulates all customer IDs from all Order resolvers
    // Fires ONE batch query: SELECT * FROM users WHERE id IN (1,5,7,12,43)
  }
}
// Result: 11 queries → 2 queries! (1 orders + 1 batched users)

DataLoader Internals — The Batching Mechanism

// DataLoader uses microtask queue (Promise.then) for batching:
// Resolver tick:
//   order1.customer → loader.load(userId=1)  → queued
//   order2.customer → loader.load(userId=5)  → queued
//   order3.customer → loader.load(userId=7)  → queued
// End of tick: loader fires batchFn([1, 5, 7]) → 1 DB query

Apollo Federation — Distributed GraphQL Graph

Federation allows multiple teams to own separate GraphQL services (subgraphs) that compose into a single unified schema. The Apollo Router (Rust-based) orchestrates query planning and execution across subgraphs:

Apollo Federation Architecture Client ──Query──► Apollo Router (query planner) │ ┌────────────┼────────────────┐ ▼ ▼ ▼ Users Subgraph Orders Subgraph Products Subgraph (Team Auth) (Team Commerce) (Team Catalog) ┌──────────┐ ┌──────────────┐ ┌──────────────┐ │ User │ │ Order │ │ Product │ │ id │ │ id │ │ id │ │ name │ │ total │ │ name │ │ email │ │ status │ │ price │ └──────────┘ │ customer→User│ │ inventory │ │ items→Product│ └──────────────┘ └──────────────┘ Query: { orders { customer { name } items { product { price } } } } Router query plan: 1. Fetch orders from Orders subgraph 2. Extract customerIds from orders 3. Batch fetch users from Users subgraph (using @key directive) 4. Extract productIds from order items 5. Batch fetch products from Products subgraph 6. Merge results → single response to client
